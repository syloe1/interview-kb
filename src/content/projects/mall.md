# Outbox 模式一句话解决

## **把 “发消息” 和 “数据库事务” 绑在一起，要么全成功，要么全失败！**

```go
订单入库时，顺便往 outbox 表插一条消息记录（和订单在同一个事务里）
数据库事务成功 → 消息记录一定存在
后台异步任务读取 outbox 表，发送 MQ
发送成功 → 把消息标记为已发送

 强一致性
发消息和业务在同一个数据库事务
订单成功 → 消息一定有
订单失败 → 消息一起回滚
2. 无风险
不会丢消息
不会重复发（有状态控制）
MQ 挂了，重试就行，数据不会乱
```

秒杀场景走 Redis + Lua。

核心思路是先把秒杀活动库存初始化到 Redis，然后购买时用 Lua 脚本原子判断和扣减：

`判断库存是否足够

Lua 脚本在 Redis 里是原子执行的，所以高并发下不会出现多个请求同时读到同一个库存值再一起扣的问题。

普通订单创建时，订单、订单明细、库存扣减在一个 MySQL 事务里完成。

核心思想：

`BEGIN
  校验商品
  条件扣库存
  创建订单
  创建订单明细
  清理购物车
COMMIT`

**Outbox 保证 MySQL 到 Kafka 的一致性**

商品数据同步 ES 时，没有在商品创建/更新/删除时直接写 ES，而是这样做：

`商品表变更 + product_outboxes 事件表
放在同一个 MySQL 事务里`

也就是：

`BEGIN
  更新商品
  插入 outbox 事件
COMMIT`

然后 worker 轮询 product_outboxes，把事件发送到 Kafka。

这样解决了一个经典问题：

`MySQL 提交成功了，但 Kafka 发送失败怎么办？`

因为事件已经存在 outbox 表里，所以 worker 后续可以继续重试，不会丢消息。

**afka Consumer 到 ES 是最终一致**

商品搜索不是直接查 MySQL，而是查 ES。

同步链路是：

`MySQL 商品变更
 -> product_outboxes
 -> Worker Publisher
 -> Kafka
 -> Worker ES Consumer
 -> Elasticsearch`

这里不是强一致，而是最终一致。

Kafka consumer 的关键点是：

`先写 ES
成功后再提交 Kafka offset`

如果 ES 写失败，offset 不提交，消息会被重新消费。

重试多次失败后，会写入死信表：

`product_event_dead_letters`

这样既能保证消息不悄悄丢失，也方便后台排查。

- 缺点：**数据倾斜**（新表热、老表冷）

- 缺点：**扩容要重新分片**（最常用）

**3. 地理分片**

- 按地区 / 运营商分
- 适合：本地生活、O2O

**4. 枚举分片**

- 按状态 / 类型分
- 适合：固定分类业务

- **ZSet（有序集合）**：key = 排行榜名，member = 用户 ID，score = 积分 / 分数
- Redis 会**自动按 score 排序**，时间复杂度 O (logN)

```go
# 添加/更新积分
ZADD rank 1000 user1
ZADD rank 2000 user2

# 查询前10名（正序，从大到小）
ZREVRANGE rank 0 9 WITHSCORES

# 查询某个用户的排名
ZREVRANK rank user1

# 查询某个用户的分数
ZSCORE rank user1
```

## 为什么用 ZSet？（必背）

1. **天然排序**：不用自己写排序算法
2. **高性能**：千万数据级查询毫秒级
3. **原子更新**：高并发下不冲突
4. **支持排名 / 分数 / 范围查询**
5. **内存存储**：比 MySQL 快 100 倍

# 过期策略

1. **惰性删除**（查询时才删）
2. **定期删除**（定时抽查删）
3. **内存淘汰**（内存满了才删）

**面试标准答案：Redis 使用 惰性删除 + 定期删除 结合的策略，保证性能和内存平衡。**

为什么不使用 “立即删除”？ 定时删除。

- 立即删除需要**定时器**，大量 key 时占用 CPU 极高
- 高并发下会**严重拖慢 Redis**
- Redis 是单线程，不能浪费 CPU 在定期扫描上

**Redis 过期 key 会不会一直不删？**

会！
如果一个 key

**过期 + 从不查询 + 没被定期抽查到 + 内存没满**

，就会暂时残留。

**问：Redis 怎么保证删除最终一致？**

依靠定期删除不断抽查，最终一定会被清理。

# 队头阻塞（HOL Blocking）

一句话：**队列里前面的请求卡住了，后面所有请求都跟着排队等待，无法执行**，分**应用层队头阻塞**和**TCP 层队头阻塞**两类。

HTTP/1.1 单条 TCP 连接中，**请求可以批量发，但响应必须严格按请求顺序返回**。

- 举例：同连接依次发 请求 A、请求 B、请求 C
- 若 **请求 A 处理 / 传输缓慢**，哪怕 B、C 早已完成响应，也必须排队等 A 先返回
- 后续请求全部被 “排头” 的慢请求堵住

# 为什么网络编程不用多进程？（3 个致命缺点）

## 1. **太笨重，开销太大**

- 一个进程就要占用**独立内存空间**
- 1000 个并发 = 1000 个进程 = 服务器直接卡死
- 网络连接成千上万，进程根本扛不住

## 2. **创建销毁慢**

网络请求

**毫秒级、短连接**

进程创建速度跟不上。

## 3. **切换成本极高**

进程切换需要：

- 切换页表
- 刷新 TLB
- 保存 / 恢复上下文**一次切换成本 = 几千行指令**
  高并发下直接把 CPU 吃满。

网络编程是 I/O 密集型，不是 CPU 密集型。
多进程太重、开销大、切换慢，不适合高并发；

**TLB = 快表（Translation Lookaside Buffer）**，是 CPU 内部一块**高速缓存**，专门用来加速**虚拟地址 → 物理地址**的转换。

虚拟地址 → 查页表 → 得到物理地址 → 访问内存。

页表存在 ** 主存（内存）** 里，查表本身就是一次内存访问，速度偏慢。

## 三、TLB 的作用

CPU 把**最常用的页表项**缓存到内部高速硬件 TLB 中：

- 地址转换时，**先查 TLB**：
  - 命中（TLB Hit）：直接拿到物理地址，极快；
  - 未命中（TLB Miss）：再去内存查完整页表，速度大幅下降。

## 为什么进程切换会「刷新 TLB」？

每个进程都有

**独立的虚拟地址空间**

，对应

**独立页表**

。
当发生

**进程切换**

：

1. 旧进程暂停，切换到新进程；
2. 两个进程的虚拟地址映射完全不一样；
3. TLB 里缓存的全是旧进程的地址映射，全部失效；
4. 操作系统必须**清空 / 刷新 TLB**。

刷新后，新进程第一次地址访问几乎都是 TLB 未命中，要反复读内存页表，**CPU 性能陡降**。

- **只对联合索引生效**，单个字段的索引用不上它。
- **范围查询后面的条件，没法下推**
  举例：索引`(班级,年龄)`，查询 `班级=一班 and 年龄>18年龄>18` 是范围，后面如果还有字段，就不能在索引里过滤了。
