# #5 Group.peers 数据竞争

## 一句话

用一个 per-Group `RWMutex` 保护 `peers` / `defaultTTL`：读路径锁内只取快照，网络 I/O 放在锁外。

## 现象与复现

`RegisterPeers()` 写 `Group.peers`，缓存 miss 时 `load()` 读它，两者没有同步。
`go test -race` 能稳定报 `DATA RACE`；普通 `go test` 看不出来。

复现：创建 Group 后，用 channel 栅栏同时启动 1 个 `RegisterPeers` 和 N 个使用不同 key 的 `Get`。

## 根因

- 包级 `mu` 只保护全局 `groups` map，不保护 `Group` 自身的字段。
- `Group.peers` 发布后仍可写，读写之间没有 happens-before。
- `if g.peers != nil { panic }` 是 check-then-act：并发重复注册可能都通过检查、静默覆盖。

## 方案取舍

- **A. per-Group RWMutex + 锁内快照（选）**：实现简单，读写语义清晰，也顺带覆盖同类字段 `defaultTTL`。
- B. `atomic.Value` / CAS 实现“写一次”：读更轻，但“第二次调用 panic”需要额外状态，且解决不了 TTL。
- C. 只文档化“服务前注册”：无法强制，race 仍然存在。

## 实现要点

- `RegisterPeers` 持写锁，把“检查 + 赋值”变成原子操作。
- `load` 在 `RLock` 内取 `p := g.peers`，立刻解锁；`PickPeer` 和网络请求都在锁外。
- `DefaultTTL` 改为未导出的 `defaultTTL`，新增 `TTL()` 访问器：**导出的可变字段无法被内部锁保护**。

## 验证

- 新增 `TestGroupRegisterPeersConcurrentWithLoad`、`TestGroupRegisterPeersConcurrentDuplicatePanicsOnce`、`TestGroupSetTTLConcurrentWithGet`、`TestGroupTTL`。
- 把并发测试放到未修改的 `dev` 上，确认会报 `DATA RACE` / 断言失败。
- `go vet ./...`、`go test ./...`、`go test -race ./...` 通过；关键测试重复 10 次无 flake。

## 收获

1. 并发修复先写一个能在 `-race` 下失败的测试，再动代码。
2. 锁只保护内存状态，不持锁做 `PickPeer` / 网络 I/O。
3. check-then-act 要么原子化，要么接受它只是“大多数时候正确”。
4. `gofmt -l .` 会列出仓库里早已存在的未格式化文件，不要顺手格式化，避免 diff 污染。

## 面试怎么讲

- 发现：普通测试测不出，`-race` 稳定复现。
- 取舍：为什么不用 `atomic.Value`（写一次语义 + panic 状态更复杂）。
- 细节：锁内只拷贝指针，I/O 在锁外；导出字段改成访问器。
- 结果：PR #50 合并；#6 的同类 race 一并修掉，但语义问题单独处理。

# #6 SetTTL 只对新写入生效

## 一句话

TTL 在写入时固化为 `expiresAt`，因此 `SetTTL` 定义为**前瞻生效**；需要立即清理旧条目时显式调用 `Purge()`。

## 现象与复现

1. 新建 Group，默认 TTL 为 0，`Get("a")` 写入的条目永不过期。
2. 调用 `SetTTL(50ms, 0)`。
3. 等待后再次访问 `"a"`，仍然命中。

## 根因

TTL 在 `lru.Add` 时被换算成绝对时间 `expiresAt`，之后不再重新计算。
`SetTTL` 只更新 Group 的 `defaultTTL`，不会重新评估已有条目。

## 方案取舍

- **A. 追溯生效**：`SetTTL` 时遍历所有存活条目重算 `expiresAt`。
  - 优点：符合“配置立即对全量生效”的直觉。
  - 缺点：从“现在”还是“原写入时刻”起算有歧义；重复调用会不断延长寿命；需要在锁内全量扫描。
- **B. 前瞻生效 + 显式 `Purge()`（选）**：行为可预测、实现小；代价是调用方需要主动清理。

## 实现要点

- `lru.Cache.Purge()` 重置链表、map 和字节计数；**不触发 `OnEvicted`**，因为手动清理不是容量淘汰。
- `cache.purge()` 处理 LRU 懒初始化：`c.lru == nil` 时直接返回。
- `Group.Purge()` 清空本机该 Group 的本地缓存（包括未过期条目），不影响远程节点，不计入 eviction 指标。
- 推荐顺序：**先 `SetTTL` 再 `Purge`**。反过来，两者之间完成的并发加载会带着旧 TTL 回填。
- 注意非原子性：`Purge` 不等待在途加载，严格一致需要调用方自行协调。

## 验证

- `TestPurge`：条数与字节清零；Purge 不触发 `OnEvicted`；之后正常容量淘汰仍会触发回调。
- `TestGroupPurgeBeforeAnyAdd`：LRU 未初始化时 Purge 不 panic。
- `TestGroupSetTTLIsForwardLookingAndPurge`：旧条目保留零过期时间、新条目按新 TTL 过期、Purge 后重新加载生效。
- `TestGroupPurgeConcurrentWithGet`：`-race` 通过。
- 相关测试 `-race -count=20` 无 flake。

## 收获

1. 先确定方法属于哪一层：第一版在 `lru` 包里 import 自己，造成 import cycle。
2. 懒初始化字段在公开方法里必须处理 `nil`。
3. 注释要和实现一致：最初写“只清理过期条目”，实际清的是全部。
4. “先 A 后 B”的顺序可能本身就是语义的一部分，要分析中间窗口。

## 面试怎么讲

- 问题：配置变了，但数据带着旧快照。
- 取舍：追溯到“现在”还是“写入时刻”说不清，所以选择预测性更强的方案。
- 配套：显式 `Purge`，并说明推荐顺序和并发窗口。
- 结果：PR #51 合并，issue 关闭。
