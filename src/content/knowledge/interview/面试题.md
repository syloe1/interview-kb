## MySQL MVCC 作用，怎么实现

- 实现数据库**读不加锁**，提升并发；实现 RC、RR 隔离级别；快照读，读写不阻塞。
- **undo log**：保存数据历史版本，形成版本链，旧数据不会立刻删除。
- **read‑view 读视图**：快照读瞬间生成，保存活跃事务集合，用来判断版本链上哪个版本对当前事务可见

```
RR可重复读 级别：**同一个事务内所有快照读共用同一个 read‑view**；
RC读已提交 级别：**每一次 select 快照读都重新生成 read‑view**。
```

- **RC 读已提交**：每次快照读生成新 read‑view，可以读到别的事务已经提交的数据；会出现**不可重复读**；
- **RR 可重复读**：事务第一次快照读生成 read‑view，整个事务复用；同一个事务多次读取结果一致；MySQL InnoDB 默认级别；解决不可重复读；MySQL 通过 MVCC+next‑key lock 解决幻读。

### TCP 三次握手，为什么不能是两次 / 四次

**三次握手流程**

1. 客户端发 SYN；
2. 服务端回复 SYN+ACK；
3. 客户端回复 ACK，连接建立。

- **为什么不能两次握手**：
  两次握手：服务端收到 SYN 就直接建立连接。会产生**半连接问题**：客户端 SYN 网络延迟，客户端早已断开，服务端收到旧 SYN 直接建立连接，白白占用服务端资源。三次握手客户端最后一次 ACK 确认，服务端收到 ACK 才真正打开连接，避免无效连接。
- **为什么不需要四次**：
  服务端的 SYN 和 ACK 可以合并成一个报文，不需要分开发送，因此三次足够；四次是挥手（关闭连接），关闭方向两边可以独立关闭。

## 用户态和内核态有什么区别，如何发生切换？

### 区别

1. **权限级别**
   - **用户态**：应用程序运行的级别，权限受限，不能直接操作硬件、访问内核内存，只能执行非特权指令。Java 应用、业务代码都跑在用户态。
   - **内核态**：操作系统内核运行级别，拥有最高权限，可以操作硬件、访问全部内存、执行特权指令。
2. **内存空间**：用户态只能访问用户空间内存；内核态可以访问内核空间 + 用户空间。
3. **目的**：隔离保护，防止用户程序随意破坏操作系统。

### 切换发生场景（从用户态→内核态）

1. **系统调用**：应用调用操作系统能力，如 read、write、socket。
2. **硬件中断**：时钟中断、IO 设备中断，硬件触发进入内核处理。
3. **异常（陷阱）**：程序发生缺页、除零等异常，CPU 自动陷入内核。

> 用户态→内核态叫**陷入 (trap)**；内核处理完成后，恢复寄存器回到用户态执行。切换会有一定开销，频繁系统调用会影响性能。

## 内核线程和用户线程区别

1. **用户线程**：运行在用户态，内核感知不到；调度完全由用户空间库实现；切换**不需要陷入内核**；一个进程内全部用户线程阻塞，整个进程阻塞。
2. **内核线程**：操作系统内核管理调度；内核有 TCB；线程切换要陷入内核；一个线程阻塞，不影响同进程其他线程。

## 虚函数的实现原理是什么

依靠**虚指针 vptr + 虚函数表 vtable**实现动态多态：

1. 只要类包含虚函数，该类的每个实例对象开头会多一个虚指针`vptr`；
2. `vptr`指向本类的虚函数表（vtable），虚表是函数指针数组，存放虚函数的地址；
3. 基类指针 / 引用指向派生类对象时，运行时通过对象的`vptr`找到派生类虚表，调用对应函数；
4. 普通函数编译期静态绑定；虚函数运行期动态绑定。

> 虚表存放在只读数据段，不属于对象本身，所有同类对象共享一张虚表。

## 进程和线程有什么区别与联系

1. **进程是资源分配的最小单位**；线程是 CPU 调度的最小单位。
2. 进程拥有独立虚拟地址空间；同一个进程内多个线程**共享进程地址空间（堆、全局变量、打开的文件描述符）**。
3. 线程有自己私有：栈、寄存器、线程局部存储 TLS。
4. 进程切换：要切换页表，开销很大；线程切换在同一进程内，不用切换页表，开销更小。 **切换开销**：进程切换需要切换页表，刷新 TLB，开销很大；线程在同一进程切换，开销小很多。
5. 一个进程至少有一个主线程；一个线程只属于一个进程；进程崩溃会杀掉内部所有线程；一个线程崩溃会导致整个进程崩溃。
6. **进程**：操作系统**资源分配的最小单位**。每个进程拥有独立虚拟地址空间、文件描述符、堆、信号等资源；进程之间天然隔离。进程切换开销大，需要切换页表、刷新 TLB。进程间通信 IPC：管道、socket、共享内存、消息队列。一个进程崩溃不会影响其他进程。
7. **线程**：操作系统**CPU 调度最小单位**。线程隶属于进程；**同一个进程内多个线程共享进程全部资源（虚拟地址空间、全局变量、打开的文件）**；每个线程私有：栈、寄存器、程序计数器。线程切换开销小，只切换上下文寄存器。线程读写共享变量需要加锁同步；一个线程崩溃会导致整个进程直接崩溃。

### 一个线程崩溃会导致整个进程崩溃。

> Linux 下，**信号是发给整个进程的**：

1. 一个子线程访问空指针、数组越界，内核向**该进程**发送 `SIGSEGV` 段错误信号；
2. 默认信号处理动作：**终止整个进程**，所有线程一起死掉；

## 野指针： 指针变量存了一个内存地址，但这个地址上已经没有有效的对象了。

重点区分三个概念：

1. **空指针 nullptr**：指针的值是 0，表示「不指向任何有效内存」
2. **有效指针**：指向一块已经分配、还没释放的内存
3. **野指针**：指针保存一个地址，但这块内存**已经被释放 / 销毁**；指针变量本身**不是 nullptr**

## 野指针怎么产生（3 种最常见场景）

### 场景 1：delete 之后没置空（刚才 DCL destroy 的场景）

```cpp
Singleton* p = new Singleton();
delete p;   // 堆内存释放，对象销毁
// p 里面仍然存着原来那块内存的地址！
// p != nullptr，此时 p 就是野指针
p = nullptr;// 把p置空，消除野指针
```

### 场景 2：局部变量出作用域，指针指向栈上已销毁对象

```
int* get_ptr() {
    int a = 10; // 栈变量，函数结束就销毁
    return &a;
}
int* p = get_ptr();
// p拿到a的地址，但函数返回后a已经销毁 → p是野指针
```

### 场景 3：指针未初始化

```
int* p; // 局部指针，默认是随机垃圾值，指向未知内存 → 野指针
```

## 死锁 4 个必要条件 + 追问：互斥是什么意思

**4 个必要条件，必须全部满足才会死锁**

1. **互斥**：资源同一时刻只能被一个线程持有；
2. **持有并等待**：线程拿到资源 A，等待资源 B，不释放 A；
3. **不可剥夺**：资源不能被其他线程强行抢走；
4. **循环等待**：线程互相持有对方需要的资源，形成环。

> 追问【互斥是什么意思】：
> 临界资源一次只能给一个线程使用。比如互斥锁，一个线程拿到锁之后，其他线程必须阻塞等待，不能同时进入临界区。

## C++ 多态怎么实现？virtual 有什么作用？底层逻辑

## poll 和 poll 区别；LT、ET 区别

### epoll vs poll

1. poll：每次调用需要传入全部 fd 集合；内核遍历全部 fd O (n)；用户态内核态每次拷贝全部 fd；无 fd 上限。
2. epoll：内核维护红黑树保存 fd；就绪事件回调通知；`epoll_wait`只返回就绪 fd；大量空闲 fd 场景性能远优于 poll。

> API：epoll_create 创建实例；epoll_ctl 增删 fd；epoll_wait 等待事件。

### LT 水平触发 vs ET 边沿触发

- **LT 水平触发（默认）**：只要 fd 还有未读完数据，每次 epoll_wait 都会持续通知；简单不容易丢事件；可能多次重复触发。
- **ET 边沿触发**：**只有状态发生变化瞬间才通知一次**；读完数据前不会再次通知；必须一次性把缓冲区数据读完；性能更好，但编码容易漏事件，一般搭配非阻塞 IO。

### TCP 三次握手

1. 客户端 → 服务端：SYN（请求连接）
2. 服务端 → 客户端：SYN+ACK（同意连接，同时确认客户端 SYN）
3. 客户端 → 服务端：ACK（确认服务端 SYN），连接建立。

> 核心目的：双向确认收发能力；防止过期 SYN 报文建立无效连接。

## MySQL 隔离级别，默认级别

InnoDB 四个隔离级别，从低到高：

1. **读未提交 Read Uncommitted**：能读到其他事务未提交数据，脏读、不可重复读、幻读都存在。
2. **读已提交 Read Committed（RC）**：只能读到已提交数据；**存在不可重复读、幻读**；Oracle 默认。
3. **可重复读 Repeatable Read（RR）**：**MySQL InnoDB 默认隔离级别**；MVCC 实现，解决脏读、不可重复读；MySQL 通过 MVCC+Next-Key Lock 解决幻读。
4. **串行化 Serializable**：最高级别，所有读加共享锁；完全避免并发问题，性能最差。

```
RC 规则：**每次快照读（select），都会生成一个全新的 ReadView**。

1. 事务 A 开启，第一次`select`查询，拿到一份数据；
2. 事务 B 修改同一条记录，并且**提交事务**；
3. 事务 A**不提交，继续在本事务内，再执行一次完全一样的 select**；
4. RC：第二次 select 会**新建 ReadView**，能看到事务 B 已经提交的新数据。
```

## redo log /undo log /binlog 作用

- **redo log（重做日志，InnoDB 特有）**
  作用：**崩溃恢复**。事务修改数据时，先写 redo log 再刷盘；数据库宕机，重启依靠 redo log 把已经提交但没刷到磁盘的数据重做，保证事务持久性。是 WAL 机制核心。
- **undo log（回滚日志，InnoDB 特有）**
  作用：①事务回滚，失败时恢复数据；②**MVCC 快照读**，保存数据历史版本，形成版本链，实现无锁读。
- **binlog（二进制日志，Server 层，所有引擎都可以）**
  作用：①**主从复制**，主库把 binlog 发给从库同步数据；②**数据备份恢复**。记录 SQL 逻辑变更（statement/row/mixed 三种格式）。

> redo log：**宕机恢复，保证持久化**；
> undo log：**回滚 + MVCC 版本链**；
> binlog：**主从同步、数据备份**。

## 缓存穿透、击穿、雪崩

- **缓存穿透**：查询**不存在的数据**，缓存永远不命中，请求直接打到 DB。例：查询 id=-1。

## 布隆过滤器，为什么解决缓存穿透

3. 不存在的请求直接拦截，不会访问 Redis、DB，解决穿透。

### 线程和协程有什么区别

1. **线程：OS 内核调度**，有完整栈，切换要陷入内核态，切换开销较大；线程数量受系统限制。
2. **协程：用户态调度**，切换不用进内核，开销很小；轻量，可以大量创建；一个线程内可以跑成千上万个协程；
3. 线程抢占式调度；协程需要用户主动让出（Go 是 M‑P‑G 抢占式协程）；
4. 线程之间栈独立；协程共享同一个线程的内核资源。

### 线程、协程区别；goroutine；GMP 模型

1. 线程：操作系统内核调度，创建销毁开销大，切换需要陷入内核；协程用户态调度，开销极小。Go 的 goroutine 是 Go 运行时实现的协程。
2. GMP：G (goroutine 协程)、M (内核线程)、P (逻辑处理器，持有调度队列)；M 必须绑定 P 才能执行 G；M/P/G 三者协作实现 goroutine 调度。

### 什么是内存对齐

编译器会按照一定规则给结构体 / 类成员分配内存，不是简单连续紧密排布，在成员之间、结构体末尾填充 padding 空闲字节，就是内存对齐。

> 可以用`#pragma pack(n)`修改对齐系数（n 为对齐字节，取 min (n, 成员自身 size)）。

### 为什么要对齐

> 目的：CPU 读取内存块更高效，减少跨内存块读取的硬件开销；不是节省内存。

1. CPU 访问内存按对齐块读取；未对齐需要两次内存读取，性能下降；
2. 部分硬件架构不支持直接访问未对齐内存，直接崩溃。

## socket 的发送缓冲区满时，调用一次 send 会发生什么？

分 socket 是否阻塞模式（默认阻塞）：

1. **阻塞 socket（默认）**
   send 会**阻塞挂起当前线程**，休眠等待内核发送缓冲区腾出空间；等到有足够空间，把用户数据拷贝一部分 / 全部到缓冲区之后 send 才返回。
2. **非阻塞 socket (O_NONBLOCK)**
   缓冲区满，send 不会阻塞；直接返回 **-1，errno 设置为 EAGAIN / EWOULDBLOCK**，代表当前缓冲区没有空间，稍后重试。

## 设计一个多生产者单消费者（MPSC）任务队列，你会怎么设计？

> MPSC：多个生产者线程 push 任务，**只有一个消费者线程 pop**。z
> 生产队列简易有限长度。 如果无限，生产者速度持续大于消费者，任务不断堆积，内存持续上涨最终 OOM。
> 队列满时，生产者可选策略：

1. **返回失败（非阻塞）**：push 直接返回 false，上层自己决定怎么处理（推荐，业务可控）；
2. **阻塞等待**：生产者 wait 直到队列有空位；缺点：生产者线程被卡住，如果大量生产者阻塞，线程资源耗尽；
3. **丢弃旧任务**：弹出队尾 / 队头旧任务，放入新任务（适合允许丢任务场景，日志、监控）；
4. **降级策略**：把任务落盘，放到备用缓冲（流量削峰）。

```cpp
// 类模板
template<typename T>
class MpscQueue{
private:
  std::queue<T> q;
  mutable std::mutex mtx;
  std::condition_variable cv;
  size_t cap; //有限队列
public:
  explicit MpscQueue(size_t max_cap) : cap(max_cap) {}
  bool push(T&& task) {
    std::lock_guard<std::mutex> lock(mtx);
    if(q.size() >= cap) {
      return false; //限流
    }
    q.push(std::move(task));
    cv.notify_one(); //唤醒消费者
    return true;
  }
  // consumer get task, handling it
  bool pop(T& out) {
    std::unique_lock<std::mutex> lock(mtx);
    cv.wait(lock, [this](){
      return !q.empty();
    });
    out = std::move(q.front());
    q.pop();
    return true;
  }
};
```

## cv.wait

> cv.wait(lock, pred)`等价于：

```cpp
while(!pred()){
    cv.wait(lock); // 释放锁，阻塞休眠；被唤醒后重新抢锁
}
```

执行流程：

1. 拿到 mutex 锁；
2. **先判断谓词`!q.empty()`**
   - 如果队列**不为空 → pred=true，不进入休眠，直接往下执行代码**；
   - 如果队列为空 → pred=false，解锁 mutex，线程阻塞休眠；
3. 当别的线程调用`cv.notify_one()`，这个线程**被唤醒，重新抢占 mutex**；抢到锁之后**再次检查谓词**！

## compare_exchange_weak 和 strong 的区别？

weak 允许**虚假失败（spurious failure）**，即使值相等也可能返回 false；适合循环 CAS；strong 不会虚假失败，但开销略大。

## 无锁数据结构，不靠 OS 的 mutex/cv 做互斥阻塞；依靠 CPU 原子指令 + std::atomic + 内存序，实现多线程并发访问，保证线程安全。无锁 ≠ 无同步，只是不使用内核锁。

> std::atomic<T> 封装 CPU 原子指令（x86：`lock cmpxchg`，ARM：ldxr/stxr）：
> CAS 是绝大多数无锁结构的核心：**乐观修改，先读，尝试更新；如果期间被别的线程改了，就重试。**
> 无锁结构大多是**乐观并发**，不是悲观加锁。

### 内存序 std::memory_order

CPU 和编译器会做**指令重排**（单线程语义不变，但多线程下数据可见性错乱）。
`std::memory_order` 用来约束重排，建立线程间数据同步关系：

1. `relaxed`：仅保证原子性，不限制重排，最快；只适合独立计数器。
2. `release`：写操作；**本操作之前的读写，不能重排到本写之后**。发布数据。
3. `acquire`：读操作；**本操作之后的读写，不能重排到本读之前**。获取别人发布的数据。
4. `acq_rel`：同时 acquire+release。
5. `seq_cst`：默认，全局顺序，最强，开销最大。

> 经典配对：**写端 release，读端 acquire**，形成同步链，保证读线程能看到写线程 release 之前所有写入。

## 无锁 vs 加锁（面试对比）

- 加锁（mutex）：悲观锁，竞争时线程阻塞，进入内核态休眠；竞争激烈时上下文切换开销大。实现简单，内存回收自动管理。
- 无锁（atomic+CAS）：乐观，失败自旋重试；不进入内核；**低延迟、高吞吐场景优势明显**。但实现极其复杂，必须处理 ABA、内存回收、内存序，调试困难。

⚠️ 误区：**无锁不是一定更快！**
竞争很小的时候，mutex 开销极低；无锁 CAS 自旋会空耗 CPU。只有锁竞争激烈的场景，无锁才有收益

## ABA 问题

> ABA 问题：变量从 A→B→A，CAS 只比较值，认为没有变化，实际中间被修改过。
> 解决方案：

1. **增加版本号（时间戳）**：不仅比较内存值，同时比较版本号，每次修改版本号 + 1。AtomicStampedReference 就是这个思路。
2. **AtomicMarkableReference**：标记是否被修改过（布尔标记，不记录次数）。

> 线程 A 读到 `tail = A`；线程 B 把 A 节点删除、释放，再新建一个节点**地址刚好还是 A**，放回链表。
> 线程 A 继续 CAS，发现 tail == A，CAS 成功，然后访问已经被释放的旧节点 → 野指针崩溃。

解决手段：

1. **带标记指针（tagged pointer）**：指针 + 版本号，每次修改版本号 + 1，就算地址复用，版本号不一样，CAS 失败。x86_64 有空闲高位可以存版本。。
2. **Hazard Pointer（风险指针）**：线程访问一个节点前，标记这个节点是正在使用；回收节点时，检查是否有线程标记它；没人在用才 delete。
3. **EBR（Epoch Based Reclamation，纪元回收）**：按纪元分批延迟回收，等旧纪元所有线程离开，再释放内存。

  2. **无等待 wait-free**：所有线程有限步骤内一定完成，不会无限重试.

## 设计一个限流器：接入服务器要限制每个 key 每秒访问次数上限（如每秒 100 次），超过直接拒绝，怎么处理？

> 首先最简单是固定窗口计数器，每个 key 维护窗口起始时间和计数，按时间分片，每个窗口独立计数。但固定窗口存在窗口边界流量突刺问题：上窗口末尾 + 下窗口开头短时间叠加流量超限。
> 解决办法是滑动窗口，统计滚动最近 N 秒内请求数量；基础滑动窗口存储每条请求时间戳，内存开销大，工程上用分桶滑动窗口做折中，拆成多个小桶，只存桶计数。
> 判断请求：清理窗口内过期记录，统计剩余请求数，小于阈值放行。
> key 量大内存高：用 LRU 淘汰长时间不访问的冷 key；使用分桶滑动窗口减少单 key 存储；使用窄整型节省内存；哈希分片降低并发锁竞争。

## 对称加密 vs 非对称加密

> AES **加密解密速度快，计算开销小，适合大量业务数据加密；密钥长度短，算力消耗低**。
> RSA/ ECC 基于大数难题，**运算极慢，只适合加密小数据**

- 对称加密：同一个密钥加解密；密钥分发是难点。
- 非对称：公私钥，公钥加密私钥解密，解决密钥分发，但慢。

## 原子指令是怎么实现的，除了锁总线外还有别的方法吗？

### 原子指令底层（x86 cmpxchg）

早年多核 CPU 做原子操作：**锁总线（#LOCK 信号）**。
锁总线：CPU 发 LOCK 信号，独占系统总线，其他核心不能访问总线，保证这次内存操作原子；代价巨大，阻塞全部核的总线访问。

现代 CPU：**缓存一致性协议（MESI） + cache line 锁（缓存行锁定）**，优先不锁总线。

- 如果要操作的变量，缓存行只在当前 CPU 核心的独占状态（MESI 的 E 态）：**只锁定这个缓存行，不需要锁全局总线**；
- 只有跨 socket、缓存行在别的核手里，才会降级锁总线。
- 原子指令由 CPU 硬件提供。老方案是锁总线，开销大；现代多核 CPU 依靠 MESI 缓存一致性协议，优先锁定单个缓存行，减少全局总线抢占，提升性能。

**内存屏障是指令，限制编译器、CPU 的指令重排，保证内存访问顺序和可见性**。
C++ 里内存序（acquire/release/acq_rel/seq_cst）本质就是告诉编译器，在对应原子操作处插入合适的内存屏障。

分类：

1. **写屏障 (store barrier)**：屏障前所有写，必须先完成；屏障后的写不能提前。对应 release。
2. **读屏障 (load barrier)**：屏障之后的读写，不能跑到屏障前面；对应 acquire。
3. **全屏障 (full barrier)**：读写都不能穿越屏障，对应 seq_cst。

## 写乱序的概念，和指令重排相比分别是什么时候发生的

> 两个层面：**编译器重排（编译期），CPU 乱序执行（运行期，CPU 硬件层面，也就是写乱序 / 内存乱序）**

1. **编译器指令重排：编译阶段**
   编译器为优化单线程性能，在**不改变单线程程序语义**前提下，调换代码指令顺序。C++ 内存序可以阻止编译器重排。
2. **CPU 乱序执行（CPU out-of-order execution，运行期）**
   CPU 发射单元，不严格按照程序指令顺序执行；只要输入就绪，就先执行，充分利用流水线。

> 写乱序（store reorder，存储重排）：CPU**把写操作放到后面执行**。指令虽然按顺序提交，但写入缓存 / 内存的顺序被打乱。
> 例如：指令 A 写内存，指令 B 写内存；CPU 先完成 A 指令执行，但**A 的写回缓存，晚于 B 写回缓存**。多线程下另一个核看到 B 写完，A 还没写。

一句话区分：

- 指令重排：广义，包含**编译期编译器重排 + CPU 运行期乱序执行**。
- 写乱序：特指**CPU 硬件层面，存储（写）操作的内存可见性乱序，发生在程序运行时**。

## COW Copy-On-Write 写时复制（Linux 进程）

fork 的时候，**不复制进程的物理内存页，父子进程共享同一份物理页，页表标记为只读**。
当父或者子进程**尝试写这个内存页**，触发缺页异常，操作系统才单独复制一份页面给修改方，修改新页面。
优点：fork 瞬间极快，节省内存；
缺点：大量写操作会触发大量缺页中断，有开销。

### 零拷贝 Zero-Copy

目标：**减少数据在内核缓冲区、用户缓冲区之间来回拷贝，减少 CPU 参与内存复制**。
传统 read+write：磁盘 → kernel buffer → user buffer → socket buffer →网卡，两次 CPU 拷贝。
Linux 零拷贝方案：

1. `sendfile`：磁盘 -> kernel buffer -> socket buffer，**跳过用户态缓冲区**，一次拷贝；
2. `mmap`：文件映射到用户虚拟地址空间，共享内核 page cache；
3. io_uring：新一代异步 IO，也支持零拷贝。

> 一句话：零拷贝不是完全没有拷贝，是**减少 CPU 参与的内存拷贝次数，数据直接在内核内部流转，降低 CPU 开销**。

## 进程通信方式 IPC（口述背）

1. 管道 pipe / 命名管道 FIFO：字节流，半双工；
2. 信号 signal：简单通知，携带信息少；
3. 共享内存 shared memory：最快 IPC，直接共享物理内存；必须配合信号量 / 原子变量做同步；
4. 消息队列 msgqueue：内核维护消息链表；
5. 信号量 semaphore：主要做同步互斥；
6. Socket：本地 Unix domain socket / 网络 socket，跨主机。

## 进程处理 signal 的时机

> Linux：**进程从内核态返回用户态的一瞬间，检查待处理信号，调用信号处理函数**。
> 不是收到信号立刻处理！
> 场景：

- 系统调用返回时；
- 中断处理完成，准备回到用户态；

> 进程在内核态返回用户态时，内核检查进程 pending 信号位图，如果有待处理信号，就执行信号 handler。正在内核态执行系统调用的时候，不会立刻处理。

## C++移动语义有什么作用 ？

- 核心：**转移资源所有权，避免昂贵的深拷贝，提升性能**。
- 容器`emplace_back`就是利用移动语义，直接原地构造，减少临时对象拷贝。

> `std::move`仅仅做类型转换，**不会真正移动，真正移动靠移动构造 / 移动赋值函数**。

## 有没有什么数据库设计要违背三大范式的场景

三大范式核心目标：**减少数据冗余、避免更新异常、插入删除异常**。
但在**查询性能优先、读多写少**场景会主动反范式（冗余、允许数据重复）。

典型场景：

1. **统计 / 报表表、宽表**
   订单表，存用户 ID，正常范式要关联用户表拿用户名；如果报表频繁展示订单 + 用户名，可以**订单表冗余存储用户名**。避免大量 JOIN 多表关联，提升查询速度；代价：用户改名时，需要同步更新所有订单里冗余的名字，存在数据不一致风险。
2. **历史归档、快照数据**
   订单历史快照，不能依赖外键关联；如果用户删除，历史订单信息不能丢，直接冗余保存当时的用户信息。
3. **大表分库分表之后**
   分表后做 JOIN 代价极高，跨库不能做外键；会冗余部分字段，减少跨库 join。
4. **缓存化宽表，OLAP 分析库**
   数仓的宽表大量反范式，把维度全部打在事实表，牺牲写性能换查询速度。

> 总结：范式优先保证写；反范式为了**读性能，减少 join**，需要业务层做数据同步，承担数据不一致风险。

## redis 的 ZSET 里的 score 在内存里是怎么存储的，会不会越界

1. score 类型是**double（64 位双精度浮点数）**，redis 内部直接存 double。
2. 底层 zset 由两部分构成：
   - **dict 哈希表**：member -> score 映射，O (1) 查找 member 对应的 score；
   - **跳表 skiplist**：按 score 排序，做范围查询、范围遍历。
3. 会不会越界：
   double 有取值范围：最大约`1.7e308`，最小约`‑1.7e308`。

- 如果传入数值超过 double 可表示范围，会变成`inf/-inf`（正负无穷）；
- **不会内存越界崩溃**，但是会出现数值失真；

> 重点坑：double 是浮点数，**整数超过 2^53 之后不能精确保存整数**。如果你把大整数当做 score，超过 2^53 会丢失精度，数值错乱，不是内存越界，是精度丢失。

> 面试重点：不是内存越界，是浮点数精度丢失问题。

## 9. SSE 长连接，底层也是长连接吗？为什么

SSE：Server‑Sent‑Events，服务端推送，基于 HTTP 协议。
✅底层是 TCP 长连接。

原理：

1. 客户端发送普通 HTTP GET 请求；
2. 服务端返回响应头`Content‑Type: text/event‑stream`，**不关闭 TCP 连接**；持续向这个连接流式输出`data:`格式事件；
3. TCP 连接一直保持，服务端源源不断推送消息。

为什么是长连接：
HTTP1.1 默认`Connection:keep‑alive`，SSE 不会完成响应结束，服务端不调用 close，TCP 连接持续存活。

⚠️区分：

- SSE 是**单向**：只能服务器推送给客户端，客户端只能发初始 GET；
- WebSocket 是双向全双工；
- SSE 底层是 HTTP，建立在 TCP 长连接之上。

> 如果网络断开，浏览器会自动重试建立新的 SSE 连接。

# C++ 异常机制 try / throw / catch

> try：监控可能发生异常的代码；throw：抛出异常对象；catch：捕获并处理异常

## 1. 关键字作用

- **try**：包裹可能抛出异常的代码块。如果内部代码（或调用的函数）执行 `throw`，立刻终止当前代码执行，开始向上寻找匹配的 `catch`。
- **throw**：发现无法本地处理的错误时，抛出异常对象。抛出后当前函数终止，后续代码不再执行，触发**栈展开**。
- **catch**：捕获对应类型的异常，执行错误处理逻辑。

> 语法特性：throw 可以抛出任意类型对象（int、字符串、自定义类都可以），工程实践推荐使用 std::exception 及其派生类。

## 2. 栈展开（Stack Unwinding）

当 `throw` 抛出异常后：

1. 停止当前代码执行；
2. 沿函数调用栈向上回溯；
3. **自动销毁已经成功构造完成**的局部对象（调用析构函数）；
4. 直到找到类型匹配的 `catch`；
5. 如果全程没有匹配的 catch，程序调用 `std::terminate` 直接终止。

> ⚠️ 注意：栈展开时，**构造未完成的对象不会调用析构函数**。
> ⚠️ 禁止在析构函数抛出异常：栈展开过程中析构抛异常会直接触发 std::terminate。

## 3. 基础示例

```cpp
#include <iostream>
#include <stdexcept>

int divide(int a, int b)
{
    if (b == 0) {
        // 创建并抛出标准异常对象
        throw std::invalid_argument("除数不能为零");
    }
    return a / b;
}

int main()
{
    try {
        int result = divide(10, 0);
        std::cout << "结果：" << result << std::endl;
    } catch (const std::invalid_argument &e) {
        // const引用接收：避免拷贝开销、保留多态特性，防止对象切片
        std::cerr << "捕获到异常：" << e.what() << std::endl;
        return -1;
    }
    return 0;
}
```

## 多个 catch 分支

> ⚠️ 顺序原则：**先具体派生类型，后通用基类类型**
> 如果把基类 `std::exception` 放前面，后面派生类的 catch 分支永远不会被匹配。

```
try {
    // 可能抛出多种异常的代码
} catch (const std::out_of_range &e) {
    std::cerr << "越界错误：" << e.what() << std::endl;
} catch (const std::invalid_argument &e) {
    std::cerr << "参数错误：" << e.what() << std::endl;
} catch (const std::exception &e) {
    std::cerr << "其他标准异常：" << e.what() << std::endl;
} catch (...) {
    // 捕获任意C++类型异常，但无法拿到异常信息
    // ❗注意：catch(...) 不能捕获操作系统信号（SIGSEGV等段错误信号）
    std::cerr << "未知异常" << std::endl;
}
```

## 核心要点总结1. `try`：包裹可能出错的代码；

2. `throw`：检测错误，抛出异常对象；
3. `catch`：匹配异常类型，做错误恢复、打日志等处理；
4. 异常传播时触发栈展开，**仅已构造完成的局部对象会析构**；
5. catch 顺序：派生类在前，基类在后；
6. 优先使用 `const &` 捕获异常，防止对象切片，减少拷贝；
7. `catch(...)` 捕获所有 C++ 异常，但拿不到异常信息，不能捕获 OS 信号；
8. ❌ 不要在析构函数内抛出异常；
9. 没有匹配 catch → std::terminate，程序直接退出。

## Linux 中创建子进程的系统调用接口是？怎么判断是子进程还是父进程？

1. 创建子进程系统调用：`fork()`。

> 补充：vfork ()，子进程共享父进程地址空间，现在基本废弃。

2. fork 调用一次，返回两次：

- 在**子进程**中：返回值 = 0；
- 返回 -1：fork 失败，创建子进程出错。

示例代码：

```

if(pid < 0){
    //失败
}else if(pid == 0){
    //子进程逻辑
}else{
    //父进程逻辑，pid是子进程id
}
```

> fork 会复制父进程的文件描述符，写时复制 COW，父子初始页表指向同一块物理内存，只有修改内存才真正拷贝。

## HTTP 和 HTTPS 的区别

1. **安全层面**

- HTTP：明文传输，数据裸奔，中间人可以窃听、篡改、劫持。端口 **80**。
- HTTPS = HTTP + SSL/TLS；传输数据加密，防窃听、篡改、身份认证；端口 **443**。

2. **加密体系**
   HTTPS 握手：非对称加密协商会话密钥；后续业务报文使用**对称加密**加密传输；证书做服务器身份校验，防止伪装服务器。
3. **性能**
   HTTPS 多 SSL/TLS 握手过程，建立连接比 HTTP 耗时略高；现代会话复用可以降低开销。
4. **证书**：HTTPS 需要 CA 颁发数字证书；HTTP 不需要。

## MySQL 的 ACID

ACID 是事务四大特性：

1. **A 原子性 Atomicity**：一个事务的所有操作，要么全部成功，要么全部失败回滚，不会出现做一半。依靠**undo log 回滚日志**实现。
2. **C 一致性 Consistency**：事务执行前后，数据库约束、业务逻辑状态保持合法正确。**一致性是最终目标，由 AID 共同保障，不是日志直接实现**。
3. **I 隔离性 Isolation**：多个事务并发执行，事务之间互相不可见，避免并发问题（脏读、不可重复读、幻读）。依靠 MVCC + 锁机制实现；4 种隔离级别：读未提交、读已提交 RC、可重复读 RR（MySQL InnoDB 默认）、串行化。
4. **D 持久性 Durability**：事务一旦提交成功，修改永久生效，即使宕机重启数据不会丢失。依靠**redo log 重做日志**实现。

## MVCC 如何解决不可重复读和幻读问题？

> MVCC：多版本并发控制，InnoDB 实现，不加锁的读（快照读 `select`），读取数据历史版本；当前读（select ... for update、update、delete）走行锁。
> 版本链：每行记录隐藏字段 `DB_TRX_ID`(事务 ID)、`DB_ROLL_PTR`(指向 undo log 旧版本)，修改数据就把旧版本放到 undo log，通过 roll_ptr 串成版本链。`read view`读视图决定当前事务能看见哪些版本。

### 不可重复读

> 不可重复读：同一个事务内，两次读取同一行，中间别的事务提交修改，两次读到结果不一样。

- **RC 隔离级别**：每次 select 都会生成新 read view，不能解决不可重复读；
- **RR（可重复读）**：**事务第一次 select 的时候生成一次 read view，整个事务复用同一个 read view**，所以整个事务看到的都是第一次快照，同一行多次读取结果不变，**解决不可重复读**。

### 幻读

> 幻读：同一个事务，两次范围查询，其他事务 insert 新数据并提交，第二次查询多出来新行，像幻觉。

- MVCC 快照读层面：RR 下快照读看不到别的事务新插入的数据，快照读感受不到幻读；
- **MVCC 本身不能解决当前读的幻读问题**；InnoDB 在 RR 级别靠 **Next‑Key Lock 临键锁（行锁 + 间隙锁）** 锁住间隙，阻止其他事务插入，解决当前读幻读。

## MySQL 的三大日志，如何记录、如何崩溃恢复、如何解决不一致问题？

三大日志：`redo log`（重做日志）、`undo log`（回滚日志）、`binlog`（二进制日志，server 层）

### redo log（InnoDB 层，保证持久性 D）

1. **记录**：事务执行 DML，修改内存页，同时写 redo log（物理日志，记录页做了什么修改）；redo log 是循环写的文件，先写日志再刷磁盘数据页 (WAL 预写日志)。事务提交时 redo log 落盘，不需要立刻把脏页刷到磁盘数据文件。
2. **崩溃恢复**：宕机，内存脏页还没刷回磁盘文件；重启读取 redo log，把已经提交但没刷盘的数据重做；未提交的事务回滚。
3. 作用：保证持久性，减少随机 IO，提升性能。

### undo log（InnoDB 层，保证原子性 A，MVCC 版本来源）

1. **记录**：逻辑日志，记录数据修改前旧版本。update/delete 生成 undo log；更新一行，旧数据写入 undo log。
2. **崩溃恢复**：宕机后，**未提交的事务利用 undo log 回滚，撤销修改**。
3. 用途：事务回滚、MVCC 多版本数据来源。

### binlog 二进制日志（MySQL Server 层）

1. **记录**：逻辑日志，记录 DML/DDL 执行语句或者行变更；只记录已经提交成功的事务；用于主从复制、数据备份恢复。格式：statement、row、mixed。
2. 崩溃恢复**不依赖 binlog**。主从架构中，主库 binlog 传给从库，从库重放 binlog 实现数据同步。

### 如何解决崩溃后数据不一致（redo log 与 binlog 一致性）

事务提交阶段有**两阶段提交（2‑phase commit）**

1. prepare 阶段：写 redo log 并落盘；
2. 写 binlog，binlog 落盘；
3. commit 阶段：redo log 标记 commit 状态。

- 如果宕机发生在 prepare 完成，binlog 还没写完：重启回滚该事务；
- 如果宕机发生在 binlog 写完，redo 还没 commit 标记：重启，对比 redo 与 binlog，事务提交。
  保证 redo log 和 binlog 事务状态对齐，主从复制不会出现数据不一致。

## 分布式事务：2PC、3PC、Raft 协议

> 分布式事务：多个不同节点 / 数据库，要保证事务 ACID。

### 2PC（两阶段提交）

角色：协调者 Coordinator、多个参与者 Participant。

1. **准备阶段（Prepare）**：协调者向所有参与者发送 prepare；参与者执行事务写 redo/undo 日志，但**不提交**；返回 yes (可以提交) /no (拒绝)。
2. **提交阶段（Commit/Rollback）**

- 如果全部返回 yes：协调者发 commit，各个参与者本地提交事务，释放锁。
- 任意一个返回 no：协调者通知全部参与者 rollback 回滚。

**缺点**

1. 同步阻塞：参与者在 prepare 后持有锁，等待协调者指令，阻塞业务；
2. 协调者单点故障；
3. 协调者发送 commit 之后宕机，部分参与者收到 commit 提交，部分没收到，出现数据不一致。

### 3PC（三阶段提交）

把 2PC 准备阶段拆分成 CanCommit、PreCommit，再到 DoCommit；增加超时机制。

1. CanCommit：协调者询问参与者能不能执行事务，参与者简单返回 yes/no，不执行 SQL。
2. PreCommit：全部 yes，发送 preCommit，参与者执行事务，写日志，不提交。
3. DoCommit：正式提交或者回滚。

增加超时：参与者收不到协调者消息，超时后自动提交。
**问题**：网络异常下，自动提交策略依然会产生数据不一致；工程很少用。

### Raft 协议（一致性协议，解决多节点复制状态机一致性）

Raft 目标：多个副本节点，保证所有节点状态一致，选出 leader。
角色：**Leader 领导者、Follower 跟随者、Candidate 候选者**。
三大模块：**领导选举、日志复制、安全性**。

1. 领导选举：超时没收到 leader 心跳，follower 变成 candidate 发起投票；获得过半票数成为 Leader。Leader 持续发送心跳。
2. 日志复制：所有写请求走 Leader；Leader 生成日志条目，复制给全部 follower；follower 写入日志返回 ACK；**过半节点复制成功，日志才提交生效**。
3. 安全性：保证已经提交的日志不会被覆盖。

> 区别：2PC/3PC 是**分布式事务协议**，解决跨资源事务原子性；Raft 是**副本一致性协议**，解决多机器数据备份复制一致，例如 etcd。分布式数据库会结合 Raft 做副本，上层再做分布式事务。

> SDD：**Spec-Driven Development，规格驱动开发**，S 就是 Spec（规格），AI 编码工程化模式，区别于随手丢需求让 AI 写代码的 Vibe Coding。

## SDD 完整流程（人是架构师，AI 是代码施工员）

1. **先写 Spec（spec.md）**：只定义**做什么、输入输出、验收标准、边界 case、错误处理**，不写实现细节；人和 AI 先对齐需求。
2. **技术设计 design.md**：模块划分、接口定义、数据结构、依赖、目录结构，人工评审通过。
3. **任务拆解 tasks.md**：拆成小任务，每个任务独立可测试，避免一次性生成超大代码。
4. AI 按单任务生成代码；**每次只生成一个模块**。
5. 生成后人工评审代码 → 单元测试（gtest）验证 → 提交到 git，CI 自动跑回归。
6. 迭代：缺陷优先修改 spec，再重新生成 / 局部修改代码，而不是直接硬改代码。

> 简单一句话：**先契约、后编码；先测试用例、后实现代码**。

## 怎么确保 AI 输出符合项目要求？怎么做？怎么验证？

1. **全局约束文件（constitution.md/ AGENTS.md）**：项目全局规则：技术栈、目录结构、编码规范、禁止写法、禁用库。每次 AI 生成代码都带上这个上下文。
2. 每个任务的 spec 里**写死验收标准**，必须可自动化验证，不是主观描述。
3. 生成代码后三层校验：
   - 静态检查：clang-format /eslint/clang-tidy，代码规范、编译检查
   - 单元测试：gtest，跑预先写好的测试用例
   - 集成测试：模块联调、CI 流水线自动化执行
4. 人工 code review：重点看逻辑漏洞、边界、安全、依赖。

## 有没有注重代码规范？怎么规范 AI 开发架构？

**有，强制规范**

- 全局文档约束 AI：命名规范、注释风格、文件拆分原则、模块职责、错误处理范式。
- 架构规范：**高内聚低耦合，模块单向依赖，禁止跨层调用**；spec 预先定义模块接口，AI 不能私自新增跨模块依赖。
- 架构约束：禁止 AI 随意修改已有核心模块；AI 只能在指定目录 / 指定包内生成代码。
- 工具链：提交前自动格式化、静态扫描，不符合规范直接拦截提交。

## 除了上面这些还有吗？怎么做？

- 上下文管理：**不要把整个百万行代码一次性喂给模型**，用 RAG / 代码检索，只把相关文件片段作为上下文，减少幻觉。
- 版本控制：AI 生成代码全部走 git，每一次 AI 生成都是独立 commit，方便回滚、对比 diff。
- 提示词分层：全局项目规则（长期）+ 当前模块 spec（任务级）+ 单次生成指令（单次 prompt）。
- 缺陷闭环：AI 产出 bug，优先更新 spec 和测试用例，再让 AI 修复，沉淀到知识库，防止重复踩坑。

## 项目代码量哪个最大？量级？百万级项目怎么用 AI？

**百万级项目 AI 落地策略：**

1. 绝对不一次性让 AI 改整个工程；**按模块垂直切片**，每次只处理单个子模块。
2. 建立项目知识库：代码、接口文档、spec、历史 bug，用 RAG 检索相关上下文喂给模型。
3. 存量代码不交给 AI 大重构，AI 只做增量开发、bug 修复、补单元测试；核心底层逻辑由人主导设计。
4. CI 流水线强制回归：每次 AI 改动，自动跑全量单元测试、集成测试。
5. 分层模型：复杂架构评审用强模型；简单 CRUD、补注释、写单测可以用本地轻量模型，降低成本。

## 遇到问题怎么排查？

1. 先看日志、断言、单元测试失败信息，定位模块。
2. 区分：是**spec 写错（需求理解错误）**，还是 AI 实现代码逻辑错误。
3. 最小复现：提取最小可复现 case，单独喂给模型定位。
4. 用 git diff 看 AI 改动范围，隔离变更，缩小可疑代码。

## 用过 gtest 吗？

**用过，C++ 项目单元测试主力框架**。写 TEST/TEST_F 宏，mock 依赖，对模块写独立单元用例；CI 自动批量执行，用于回归测试。

## 定位到 bug，是重写还是局部修改？

- 小 bug、边界错误：**局部增量修改**，让 AI 只修改对应函数，不要重写整个文件，降低破坏其他逻辑风险。
- 接口设计错误、底层逻辑完全偏离 spec：**重写该模块**，重写前先冻结旧代码，保留旧的测试用例验证新实现。

## 怎么保证不改坏其他模块？

1. **最小变更原则**：限制 AI 修改范围，限定只能修改指定文件 / 函数。
2. 单元测试：每个模块独立 gtest 用例；改动后**跑全量回归测试**，只要旧用例失败就禁止合并。
3. 模块隔离：依赖抽象，用 gmock 做 mock，减少模块耦合。
4. Code review + CI 门禁，失败直接阻断合并。

## 有没有模块功能测试用例？

有，**TDD 风格，先写测试用例再让 AI 写实现**。每个模块的 spec 里附带正向用例、边界用例、异常用例，gtest 落地。

## 写过 Skill 吗？过程？为什么写？多个 Skill 如何配合？

> Skill：Agent 的能力包，给模型的结构化操作手册，定义触发条件、执行流程、可用工具。

### 为什么写 Skill

原生模型容易幻觉、不会按固定工程流程执行；Skill 把固定工作流固化，让 AI 在指定场景下按规范做事（比如 SDD 编码流程、代码静态检查、单元测试生成），减少 prompt 重复编写，稳定输出。

### 编写过程

1. 基线测试：先看裸模型做这件事会在哪失败，定位能力缺口。
2. 定义触发条件：什么时候启用这个 skill。
3. 编写最小 skill 主体：工作流、输入输出约束、示例。
4. 编写评测用例，验证是否触发正确、执行结果符合预期。
5. 迭代：真实场景测试，优化触发条件，精简描述，补充边界 case。

### 多个 Skill 配合

- 用**路由逻辑**：根据用户任务选择激活对应的 skill；同一时间一般只激活一个主 skill。
- 可在 skill 内部调用其他子 skill，形成能力组合；
- 职责拆分：每个 skill 只做一件事，避免大而全，防止互相干扰。

## 记忆怎么设计

分层记忆：

- 短期记忆：当前会话上下文，本轮任务 spec、代码片段；
- 长期工程记忆：项目 spec、架构文档、历史 commit、历史 bug，用向量库做 RAG 检索；
- 实体记忆：模块接口、全局常量、约束规则，结构化存储。

### 三次握手（建立连接）

TCP 是面向连接协议。

1. **第一次握手**：客户端发送`SYN`报文，客户端状态变为`SYN_SENT`，请求建立连接。
2. **第二次握手**：服务端收到 SYN，回复`SYN+ACK`报文；服务端进入`SYN_RCVD`。
3. **第三次握手**：客户端收到 SYN+ACK，回复`ACK`；客户端进入`ESTABLISHED`；服务端收到 ACK 后也进入`ESTABLISHED`，连接建立完成。

> 为什么三次，不是两次：防止过期失效的连接请求报文在服务端打开无效连接，浪费资源。

### 四次挥手（断开连接，全双工，双方独立关闭读写）

1. **第一次挥手**：主动关闭方调用 close，发送`FIN`，状态`FIN_WAIT_1`。
2. **第二次挥手**：被动方收到 FIN，回复`ACK`，进入`CLOSE_WAIT`；主动方收到 ACK 变为`FIN_WAIT_2`。此时主动方不再发数据，被动方还可以继续发送数据。
3. **第三次挥手**：被动方业务处理完毕调用 close，发送`FIN`，状态`LAST_ACK`。
4. **第四次挥手**：主动方收到 FIN 回复`ACK`，进入`TIME_WAIT`，等待**2MSL**时间后关闭；被动方收到 ACK 直接`CLOSED`。

> TIME‑WAIT 作用：保证对方收到最后 ACK；网络延迟报文不会干扰下一次新连接。

## C++ 怎么把代码转成二进制的？

C++ 源码到可执行二进制，4 个阶段：**预处理 → 编译 → 汇编 → 链接**

1. **预处理（preprocess）**：`g++ -E`
   处理`#include`头文件展开、`#define`宏替换、条件编译`#ifdef`、删除注释；输出`.i`预处理文本文件，仍然是 C++ 代码。
2. **编译（compile）**：`g++ -S`
   把预处理后的 C++ 代码做词法、语法、语义分析，生成**汇编代码 (.s)**。做优化（‑O2），检查语法错误。
3. **汇编（assemble）**：`g++ -c`
   汇编器 as，将汇编指令翻译成机器指令，生成**目标文件 .o（ELF 格式）**，二进制，但内部存在大量未解析符号（函数调用、全局变量地址未定）。
4. **链接（link）**
   链接器 ld，把多个`.o`目标文件 + 库文件（静态库`.a` / 动态库`.so`）合并。

- **静态链接**：把库代码拷贝进可执行文件；
- **动态链接**：运行时加载`.so`，不拷贝代码。
  符号解析、重定位，填充函数、变量真实地址，输出最终可执行二进制程序。

> 补充：运行的时候操作系统加载器把可执行文件加载进内存。

## 线程池了解吗，为什么要用线程池？

**线程池**：提前创建一批工作线程，任务提交到任务队列；工作线程不断从队列取出任务执行；线程不会执行完任务就销毁，循环复用。

### 使用线程池的原因

1. **避免频繁创建销毁线程开销**：创建 / 销毁线程涉及系统调用，消耗 CPU；高并发场景频繁 new thread 性能差。线程复用，降低开销。
2. **控制最大并发线程数量**：限制线程总数，防止无限制创建线程耗尽内存、CPU；避免操作系统线程调度压力过大。
3. **便于管理**：统一管控任务队列、超时、拒绝策略；可以统计任务数量。
4. **解耦任务提交和任务执行**：业务只把任务丢队列，不用关心哪个线程执行。

> 缺点：任务队列阻塞、任务堆积风险；任务不能执行耗时过长的阻塞 IO，会占满工作线程。

## 谈谈用过的数据类型

C++ 可以分：**内置基础类型、STL 容器、自定义类型**

1. **内置基础类型**
   整数：`char, short, int, long, long long`；无符号版本`uint32_t、uint64_t`（stdint.h）；浮点：`float double`；布尔`bool`；指针。注意不同平台字节差异，跨平台优先用固定宽度 uintxx_t。
2. **STL 容器**

- 序列容器：`vector`动态数组（随机访问，尾部插入高效）；`list`双向链表；`deque`双端队列。
- 关联容器：`set/multiset`红黑树有序集合；`map/multimap`有序键值；`unordered_set/unordered_map`哈希表，平均 O (1) 查找。
- 适配器：`stack、queue、priority_queue`。

3. **智能指针**：`unique_ptr shared_ptr weak_ptr` RAII 管理堆内存。
4. **自定义类型**：`struct class`结构体 / 类，封装业务数据。

## 写代码怎么验证功能的？

1. **单元测试**：针对函数 / 模块，写输入输出用例；C++ 常用 gtest。覆盖正常、边界、异常输入。
2. **手动构造测试用例**：边界值、空输入、超大输入、错误输入。
3. **调试运行**：本地编译运行，打印日志，看输出结果是否符合预期。
4. **集成测试**：多个模块组合跑通完整业务流程。
5. **回归测试**：修改代码后跑旧用例，保证不破坏原有逻辑。
6. 如果有条件，压力测试，模拟高并发，看稳定性。

请解释什么是操作系统的死锁？产生死锁的四个必要条件是什么？如何避免或解决死锁？
**死锁定义**：一组进程，每个进程都占有部分资源，同时又等待其他进程持有的资源，所有进程互相等待、都无法继续向前推进，永远阻塞，这就是死锁。

**四个必要条件（必须同时满足才会发生死锁）**

1. **互斥条件**：资源是互斥访问，同一时刻只能一个进程使用。
2. **请求与保持**：进程已经占有若干资源，又请求新的资源，原有资源不释放。
3. **不可剥夺**：已经分配给进程的资源，不能被其他进程强行夺走，只能持有者主动释放。
4. **环路等待**：存在进程资源环形等待链，P1等P2资源，P2等P3，…Pn等P1。

**处理死锁的手段**

1. **预防死锁**：破坏4个必要条件中任意一个。
   - 破坏请求保持：进程一次性申请全部需要资源；
   - 破坏不可剥夺：资源可被抢占；
   - 破坏环路等待：资源统一编号，进程按固定顺序申请资源。
2. **避免死锁**：不破坏条件，动态判断分配是否安全，银行家算法。每次分配资源前检查系统是否存在安全序列，只有安全才分配。
3. **检测+解除死锁**：允许死锁发生，定期检测死锁；发现死锁后，终止部分进程、剥夺资源，解除死锁。

## 线程池核心参数 & 任务提交判断逻辑

七大核心参数：

1. `corePoolSize`：核心线程数；
2. `maximumPoolSize`：最大线程数；
3. `keepAliveTime`：非核心线程空闲存活时间；
4. `unit`：时间单位；
5. `workQueue`：阻塞任务队列；
6. `threadFactory`：线程工厂，创建线程；
7. `handler`：拒绝策略。

**任务提交完整判断逻辑**

1. 新任务进来，如果当前运行线程数 < `corePoolSize` → 创建核心线程执行任务；
2. 核心线程满了，任务加入`workQueue`阻塞队列；
3. 队列满，当前线程数 < `maximumPoolSize` → 创建非核心线程执行任务；
4. 线程数已经达到`maximumPoolSize`，队列也满 → 执行拒绝策略。

## MySQL 线上优化整体思路

1. **业务 SQL 层面**
   - 慢查询日志定位慢 SQL；优化 SQL 写法，避免 select *、避免函数操作字段、避免隐式转换；
   - 合理设计索引，避免索引失效，避免回表；联合索引遵循最左前缀。
2. **表结构设计**
   - 字段尽量小，避免大字段；适当冗余，减少 join；避免 NULL；合理选择字段类型；
   - 大表分库分表，冷热数据分离；归档历史数据，减少表数据量。
3. **存储引擎与配置参数**
   - InnoDB 参数调优：`innodb_buffer_pool_size`（最重要，尽量占物理内存 50%‑70%）；调整 redo log 大小；undo log；
   - 调整连接数、sort_buffer、join_buffer 等；不要盲目调大。
4. **架构层面**
   - 读写分离，主写从读；
   - 引入缓存 Redis，减少 DB 查询压力；
   - 大查询异步化，离线统计走数仓，不要在线库跑。
5. **锁与事务**
   - 避免长事务，长事务占用 undo、锁；减少行锁升级表锁；控制事务粒度，尽快 commit。

## InnoDB 底层数据与索引用什么数据结构

**B + 树**。
聚簇索引：主键索引，叶子节点存完整行数据；
二级索引（普通索引）叶子节点存主键值，回表拿到完整行。

## B + 树特点

1. 所有数据都存放在叶子节点；非叶子节点只存索引键，用于路由；
2. 叶子节点用双向链表串联；范围查询、order by 非常友好；
3. 非叶子节点不存真实数据，可以存储更多索引 key，树高度很低；
4. 查询任何记录 IO 次数基本等于树高度；
5. 叶子节点有序，支持范围扫描；
6. 主键是聚簇索引，二级索引叶子存储主键。

对比 B 树：B 树每个节点都存行数据，非叶子节点存数据，节点存 key 变少，树更高。

## InnoDB 如何实现事务 ACID

- **A 原子性 Atomicity**：undo log 回滚日志；事务失败，根据 undo log 回滚所有变更。
- **C 一致性 Consistency**：是最终业务结果；原子性、隔离性、持久性 + 业务约束共同保证一致性，不是由某一个日志单独实现。
- **I 隔离性 Isolation**：MVCC 多版本并发控制 + 锁机制。读不加锁通过 undo log 构建快照；写使用行锁；不同隔离级别由锁 + MVCC 实现。
- **D 持久性 Durability**：redo log 重做日志。修改先写 redo log，再刷盘数据页；数据库宕机重启，从 redo log 恢复已提交事务。

> binlog 是归档日志，用于主从复制，不负责 ACID。

## Redis 分片集群（cluster）读写，底层是否哈希实现

Redis Cluster 分片集群，**是基于哈希槽实现，不是直接对 key 做哈希取模节点**。

1. 总共有 16384 个哈希槽`0‑16383`；
2. 每个节点分配一部分槽；
3. 对 key 做 CRC16 哈希，对 16384 取模，得到 key 对应的槽；定位到持有该槽的节点。

### 写入读取流程

1. 客户端计算 key 所属 slot；
2. 如果连接的正好是该 slot 对应的节点，直接读写；
3. 如果 key 不在当前节点，节点返回 MOVED 重定向，客户端去访问正确节点；高级客户端会缓存槽与节点映射，减少重定向。
4. 迁移槽的时候会出现 ASK 重定向。

> 不是哈希取模直接映射机器，而是哈希映射槽位，槽分配给节点。底层哈希算法 CRC16 (key)%16384。

## std::future

`std::future` 用于获取异步任务返回结果，配合`std::async`、`std::promise`、`std::packaged_task`。

- `std::future<T>`：异步结果对象，只能 move，不可拷贝；`get()`阻塞等待任务完成，拿到返回值；只能调用一次 get。
- `std::promise`：线程内写入结果，给 future 读取。
- `std::packaged_task`：包装可调用对象，绑定 future。
- `std::async`：启动异步任务，直接返回 future。

> 考点：
>
> 1. `future.get()`阻塞；只能调用一次；
> 2. `std::shared_future`可拷贝，多线程等待同一个结果；
> 3. async 策略：`std::launch::async`新建线程；`std::launch::deferred`延迟执行，调用 get 时才在当前线程跑。

**SIMD（Single Instruction Multiple Data，单指令多数据）**
CPU 向量指令集，一条指令同时对多组数据并行计算（SSE、AVX、AVX2、AVX512）。
适用场景：批量数值计算，图像、音频、矩阵运算，向量加速。

特点：

1. 一次指令并行处理多个连续数据；
2. 数据要内存对齐；
3. C++ 可手写 intrinsic 内置函数，或者编译器自动向量化（`-O3`）；
4. 属于 CPU 指令级并行，和多线程不同：SIMD 是**同一个线程内部**并行计算。

例子：数组全部元素 + 1，普通循环逐个算；SIMD 一次加载 8 个 float，一次性加 1。

> 面试一句话：SIMD 是 CPU 向量指令，单指令操作多份数据，适合批量数值计算，提升计算密集场景性能。

## 假设有一个包含百万级数据的表，你该如何通过 SQL 查询快速找到某个字段的最大值？

> 给该字段建立单列 B + 树索引，`MAX(col)`直接利用 B + 树叶子节点有序的特性，定位索引最右端叶子拿到最大值，不用扫描百万数据；无索引则只能全表扫描。联合索引需要注意最左前缀，只有查询条件对应的范围内目标字段有序，才能快速获取最值。

## 表字段 a,b,c，联合索引 `idx(a,b,c)`，`where a=? and b=? order by c` 能否命中索引？

✅ **可以命中索引，并且不需要额外文件排序（不会 Using filesort）**
联合索引遵循最左前缀：

- where 条件固定 a、b，索引中**a 相同、b 相同的记录，c 本身就是有序**。
- 查询过滤后的数据天然按 c 排好序，`order by c` 直接复用索引顺序，不需要额外排序。

> 对比坑：`where a=? order by c` 就不行，跳过 b，c 不再全局有序，会触发 filesort。
> explain Extra 看到 `Using index`（覆盖索引，如果 select 只查 a/b/c）最佳。

## 索引底层原理

InnoDB 索引是**B + 树**，数据存在页（16KB）。

1. 聚簇索引（主键索引）：B + 树叶子节点存**完整行数据**；
2. 二级索引（普通 / 联合索引）：叶子节点存**主键值**，拿到主键后回表查聚簇索引拿完整行；
3. B + 树非叶子节点只存索引键 + 页号，用来路由；叶子节点双向链表串联，有序，范围查询、order by 友好。

> 索引本质：把查询条件字段构建有序 B + 树，减少磁盘 IO，避免全表扫描。s

## 旁路缓存（Cache Aside）会存在脏数据吗

✅ **会存在短暂脏数据**
旁路缓存流程：

- 读：先查缓存，命中返回；未命中查 DB，回写缓存。
- 写：**先更新数据库，再删除缓存**。

脏数据场景：
线程 A 读，缓存失效，准备读 DB；线程 B 修改 DB 并且删除缓存；A 拿到旧数据写回缓存 → **缓存脏数据**。

> 解决方案：给缓存加 TTL 过期，脏数据最多存活 TTL 时间；或者延迟双删（更新 DB → 删除缓存 → 休眠一小段时间 → 再删一次缓存）降低概率；强一致性不适合旁路缓存。

## protobuf：修改 proto 结构体**字段名字**，会不会影响旧序列化数据反序列化？

✅ **不会影响**
Protobuf 识别字段依靠**field_number（字段编号），不是字段名**。

- 序列化时只存 field 编号 + 值，**不存字段名称**；
- 只要**field 编号不变**，仅仅修改字段名称，老数据可以正常反序列化。

> 一句话背诵：protobuf 靠字段编号识别字段，只改字段名、field_number 不变，不影响已序列化数据。

## Golang map 底层是什么

Go map 底层是**哈希表，数组 + 链表（Go1.18 之后改用数组 + 哈希桶，桶内链表，溢出桶）**
核心结构 `hmap`：

1. `hmap` 是 map 顶层结构体，包含桶数量、计数器、扩容标记等；
2. `bmap` 桶：一个桶最多存 8 个 key-value；
   - key 经过 hash，取低位选桶；高位用来在桶内快速查找；
   - 桶内 8 个 slot，按 hash 高位对比；
   - 超过 8 个，使用**溢出桶 overflow bucket**；
3. 哈希冲突：**拉链法**，同一个桶内链式存储；
4. 扩容：
   - **等量扩容**：大量删除元素，碎片多，整理内存，桶数量不变；
   - **翻倍扩容**元素数量达到负载因子（6.5），桶数量 ×2；
   - 渐进式扩容：不会一次性迁移所有数据，每次读写 map 的时候迁移少量桶，分摊开销
     补充考点：

- map**无序**，遍历顺序每次不一样；
- map 并发读写不安全，并发读可以，读写并发会 panic；并发场景用 sync.Map。

> Go map 底层 hmap，由多个 bmap 桶组成，hash 取低位定位桶，桶内最多存 8 个 kv，冲突用溢出桶；负载因子 6.5 触发渐进扩容。

## 是否了解 KCP 协议

KCP：**可靠 UDP，基于 UDP 实现的可靠传输协议**。TCP 是为带宽优化，KCP 是为**低延迟**优化。

- 底层传输：UDP（无连接，不可靠），KCP 在应用层实现确认、重传、滑动窗口；
- TCP 特点：拥塞控制保守，丢包会大幅降低发送速率，延迟高；
- KCP 特点：
  1. 选择性重传，**只重传丢的包，不重传后面所有**（TCPGBN 回退 N，会连带重传）；
  2. 快速重传机制，不靠超时等待；
  3. 可配置：调整窗口、ack 延迟；
  4. 牺牲一部分带宽换取更低延迟；
- 使用场景：游戏、直播、实时音视频；
- 缺点：**没有 TCP 内置拥塞控制，带宽抢占激进，容易丢包，增加带宽开销**。

一句话背诵：KCP 跑在 UDP 之上，用户态实现可靠传输；相比 TCP，使用选择重传，减少丢包带来的延迟，牺牲带宽降低延时，适合游戏这类实时场景。

## Go map 负载因子为什么是 6.5？

> 兼顾空间和查找效率，桶里 8 个 slot，平均每个桶 6.5 个元素时触发扩容。

## KCP 和 TCP 滑动窗口区别，KCP 为什么延迟更低

### 1. TCP 滑动窗口

TCP 是**面向连接、可靠、有序**。

- 滑动窗口核心：**接收方通告窗口 rwnd + 拥塞窗口 cwnd**，用来控制发送速率；
- 重传策略：**RTO（重传超时）**，丢包之后要等超时计时器到期才重传；
- 特点：强保序，严格 ACK 确认；**超时等待是 TCP 高延迟根源**。即使只是瞬时丢包，也要等 RTO 才补发。

### 2. KCP 滑动窗口

KCP 是基于 UDP 实现的**可靠传输协议**，也有滑动窗口，但设计思路完全不同：

1. **快速重传（核心降延迟）**
   收到 3 个冗余 ACK（选择性确认），不等 RTO 超时，立刻重传丢包；
2. **选择性重传 SACK**：只重传丢失的那一段，不是重传整个窗口；
3. **允许乱序交付**：收到后续数据包可以先交给上层，不用阻塞等待前面丢包；TCP 必须保序，前面丢了，后面包即使收到也缓存不交付；
4. **窗口控制**：同样有接收窗口 + 拥塞窗口，但拥塞控制更激进，适合弱网；
5. 代价：**带宽利用率会比 TCP 差，额外 CPU 开销**。

> 一句话总结 KCP 延迟低的根本原因：**不等超时计时器，快速重传 + 支持乱序交付，不会因为单个丢包卡住整个队列**。

## 什么时候哈希表优于 256 数组

> 数组方案：用数值直接当下标，`arr[val]`，O (1) 访问。但前提：**key 的数值范围小且连续**。

✅ **哈希表优于数组：key 数值范围极大，但实际元素数量很少（稀疏）**
例子：key 是 uint64，取值范围 0~2^64，但只存几十 / 几千个元素。

- 数组：需要预分配 2^64 个位置，内存完全不可能；
- 哈希表：只给存在的元素分配内存。

## inner join 和 left join 区别

- `inner join`内连接：**只返回左右两张表能够匹配上的行**，不匹配的直接过滤丢弃。
- `left join`左连接：**以左表全部行保留**；右表匹配不上的字段全部填充 NULL。

> 注意：left join 如果 where 条件写右表字段！=xxx，会退化成 inner join；要把条件放 on 后面。

## 非聚簇索引存的什么数据

叶子节点存储：**索引列的值 + 主键值（聚簇索引 key）**，**不存完整行**。

> 通过二级索引查询，如果要拿不在索引中的字段，拿到主键再回表查聚簇索引；如果查询字段全部在索引里就是覆盖索引，不需要回表。

## MVCC 是什么，有什么作用

MVCC：Multi‑Version Concurrency Control，**多版本并发控制，InnoDB 实现隔离级别的核心机制**。

- 原理：行记录保存多个数据版本，依赖**隐藏字段 DB_TRX_ID、DB_ROLL_PTR、undo log 版本链、ReadView 读视图**；读操作读取快照版本，不加锁。
- 作用：

1. **读写不阻塞，读不阻塞写，写不阻塞读，大幅提升并发性能**；
2. 实现**可重复读隔离级别（MySQL InnoDB 默认）**；
3. 解决快照读下的幻读问题；

> 注意：MVCC 只针对快照读（普通 select）；当前读（select ... for update、update delete）还是要加行锁。

## sync.Map 的底层实现

Go 的 `sync.Map` 是为**读多写少、并发读远大于写**场景设计，不依赖互斥锁全部锁住，内部有两个主要结构：

1. **read（只读 map）**：是 `atomic.Value` 类型，保存只读数据，读取不加锁。修改不会直接修改 read，优先操作 dirty。
2. **dirty（脏 map）**：普通 map，会存放新增、修改、删除的数据，操作 dirty 需要加互斥锁 `mu`。

- 查找逻辑：优先查 read，命中直接返回；read 没命中，加锁查 dirty。
- miss 计数：每次 read 未命中，miss 计数器 + 1；当 miss 达到 dirty 长度，就把**dirty 全量升级覆盖 read，dirty 置 nil**，减少后续锁竞争。
- 删除：不会立刻从 read 删掉，只是给 read 里面 value 标记为 `nil（已删除标记）`；真正清理发生在 dirty 升级的时候。

> 缺点：不适合大量写场景，大量写性能不如 `map + sync.RWMutex`。

## 操作系统内存管理

操作系统把物理内存做抽象，引入**虚拟内存**，每个进程拥有独立虚拟地址空间。
核心模块：

1. 内存分配：给进程分配物理页；
2. 地址翻译：MMU + 页表，虚拟地址→物理地址；
3. 换入换出：物理内存不足时，把不常用页置换到磁盘 swap 分区；
4. 空闲内存管理：维护空闲物理页，记录哪些内存块可用。

进程看到的都是虚拟地址，进程之间内存隔离；多个进程可以通过共享页，实现内存共享。缺页的时候触发**缺页中断**，操作系统加载磁盘数据到物理内存。

## EXPLAIN 看过吗？查询有没有走索引

`EXPLAIN` 分析 SQL 执行计划，看 MySQL 如何执行这条 SQL。
重点看字段：

- `type`：访问类型，`ref/range` 代表走索引；`ALL` 代表全表扫描，没走索引。
- `key`：实际使用的索引，NULL 表示没用到索引。
- `Extra`：`Using filesort` 文件排序、`Using temporary` 使用临时表，代表索引优化不足。

如果 `EXPLAIN` key 为 NULL，说明没有用到索引：可能索引失效（隐式类型转换、or 条件、like% 前缀通配符等）、查询条件不满足索引最左前缀、优化器判断全表扫描比索引更快。

## MySQL 有哪些索引

InnoDB：

1. **B + 树索引**：聚簇索引（主键索引），二级索引（普通索引、唯一索引）；
2. **Hash 索引**：只有 Memory 引擎原生支持；InnoDB 有自适应哈希索引 AHI，是内存中自动构建，不能手动创建 hash 索引；
3. **全文索引 FULLTEXT**，针对文本内容分词检索；
4. **空间索引 SPATIAL**，地理坐标数据。

## 索引是不是越多越好？索引太多有什么问题

**索引不是越多越好**。
问题：

1. **写操作代价上升**：insert/update/delete，不仅修改数据，还要维护每一个索引；索引越多写越慢。
2. **占用磁盘空间**，二级索引占用存储空间。
3. MySQL 优化器选择执行计划开销变大，索引多，优化器评估索引的耗时增加，有可能选错索引。

## 设计索引的原则

1. 遵循**最左前缀匹配原则**；
2. 优先给 where 条件、join 条件、order by/group by 字段建索引；
3. 尽量索引覆盖，避免回表，建立联合索引；
4. 避免建立低区分度字段索引（性别这类区分度很低，索引几乎无效）；
5. 联合索引把区分度高字段放前面；
6. 不要建立大量很少使用的索引；定期删除无用索引。

## Hash 索引和 B + 树索引区别

表格

| 对比项     | B + 树索引                        | Hash 索引                        |
| ---------- | --------------------------------- | -------------------------------- |
| 底层结构   | 多路平衡查找树                    | 哈希表                           |
| 查询       | 支持范围查询、排序、like 前缀匹配 | 只支持等值查询，不支持范围、排序 |
| 时间复杂度 | O(log n)                          | O (1) 等值查找，存在哈希冲突开销 |
| 顺序存储   | 叶子节点有序，范围查询高效        | 无序，范围查询失效               |
| 冲突       | 无哈希冲突                        | 存在哈希冲突                     |

> InnoDB 不支持手动创建 Hash 索引，自适应哈希索引是内部缓存。

## make 和 new 有什么区别？make 可以初始化哪些类型

1. `new(T)`：分配**内存**，把内存置零，返回`*T`指针。只分配内存，**不会初始化内部数据结构**。支持所有类型。
2. `make(T, args)`：**分配内存 + 初始化内部结构**，返回类型 T 本身，不是指针。

- make 仅支持三种内置引用类型：**slice、map、chan**。

> 举例：`new(map[int]int)`得到 nil map，不能直接存 kv；`make(map[int]int)`初始化哈希表，可以直接读写。

## Go 数组和切片区别

1. **数组`[N]T`**：长度 N 属于类型一部分，长度固定；值类型，赋值会完整拷贝全部元素。
2. **切片`[]T`**：长度不写，长度可变；引用类型，拷贝切片头，底层数组共享。

## Slice 底层结构

```Go
type slice struct {
    array unsafe.Pointer // 指向底层数组起始
    len int              // 当前元素个数
    cap int              // 底层数组总容量
}
```

- `len`：切片当前有效元素数量，访问不能超过 len。
- `cap`：底层数组总容量，代表最多可以存多少元素，不用重新分配内存。

## append 容量不足发生什么 & Slice 扩容机制

当`append`后新长度`>cap`，触发**切片扩容，分配新底层数组，拷贝旧数组全部元素到新数组**。
Go1.18 后扩容规则：

1. 旧切片`cap < 256`：新容量直接 `cap *=2`（翻倍）
2. 旧切片`cap >=256`：新容量按 `cap *=1.25`增长，直到满足需要的容量。

> 注意：扩容会发生内存拷贝，**原底层数组不变，返回新 slice 对象，必须接收返回值**。

## 什么是 Goroutine？为什么比 OS 线程轻量

Goroutine：Go 语言用户态协程，由 Go 运行时管理，不是操作系统内核线程。
轻量原因：

1. 栈初始很小（2KB），栈动态扩容收缩；OS 线程栈通常 MB 级别。
2. Goroutine 切换**在用户态完成，不陷入内核**，不需要内核上下文切换开销。
3. 调度由 Go 运行时 GMP 完成，少量 OS 线程可以调度成千上万 goroutine。

## GMP 调度模型

- **G(Goroutine)**：待执行协程，保存任务、栈、上下文。
- **M(Machine)**：操作系统内核线程，真正执行代码。
- **P(Processor)**：逻辑处理器，持有运行所需上下文，有本地 G 队列。P 的数量默认等于 CPU 核心数 GOMAXPROCS。

流程：M 必须绑定 P 才能运行 G；P 有本地运行队列；全局 G 队列；M 空闲会去偷其他 P 队列的 G（work‑stealing 工作窃取）；发生系统调用时 M 和 P 解绑，M 阻塞，P 绑定新 M 继续跑其他 G

## G 的调度有哪些方式？比如 Sleep 或网络 IO 时会发生什么？

G 的调度触发时机：

1. **主动让出**：`runtime.Gosched()`；`time.Sleep()`；channel 读写阻塞；
2. **被动抢占**：Go1.14 后，基于信号的异步抢占，长时间运行 G 会被抢占；
3. **系统调用阻塞**（网络 IO、文件 IO）。

**Sleep 场景：**
G 标记为 Gwaiting，放到定时器堆；M 和 P 解绑，M 去拿新 G 继续跑；时间到，G 重新放入 P 队列等待调度。

**网络 IO 阻塞场景：**
Go 使用 netpoller（epoll/kqueue），G 进入 Gwaiting 状态，M 和 P 解绑，P 绑定新 M 继续跑其他 G；IO 就绪后唤醒 G，放回 P 队列。

> 关键点：**G 阻塞不会阻塞 P，不会浪费 CPU，这是 GMP 轻量的核心**。

## 除了 WaitGroup，Go 中还有哪些并发控制手段？

- `sync.Mutex` / `sync.RWMutex`：互斥、读写锁
- `sync.Once`：只执行一次（单例）
- `sync.Cond`：条件变量，等待 / 广播唤醒
- `channel`：Go 推荐，CSP 模型，协程通信
- `context.Context`：超时、取消、传递请求域信息

## Context 的超时传播和取消机制是什么？

Context 是接口，核心：`Done()`返回 chan，取消时 chan 关闭；

- `WithCancel`：手动调用 cancel () 关闭 Done 通道；
- `WithTimeout/WithDeadline`：内置定时器，超时自动 cancel；
  **传播：Context 是树形结构，父 Context 取消，所有子 Context 都会被级联取消。**

> 注意：context 只传递请求元数据、取消信号，不要传业务变量；cancel 必须调用，防止资源泄露。

### 什么是协程泄露？如何定位内存泄露？

**协程泄露：Goroutine 永久阻塞，无法退出，一直占用栈资源，无法被 GC 回收。**
常见原因：

1. channel 读写一方永久阻塞（无接收的 send、无 send 的 recv）；
2. context 忘记 cancel；
3. 无限循环内没有退出条件；
4. 锁永久持有。

**定位手段：**

1. `pprof goroutine`：看协程数量、栈，看阻塞在哪一行；
2. `pprof heap`：内存分配；
3. trace 工具，查看协程调度；
4. 埋点监控 goroutine 数量，持续上涨大概率泄露。

## Goroutine 和 OS 线程上下文切换区别

1. OS 线程切换：陷入内核态，保存全套 CPU 寄存器、页表等，开销大。
2. Goroutine 切换：**用户态完成**，只保存 goroutine 栈和少量寄存器，不切换页表，开销很小。

## 进程、线程、协程区别联系

1. **进程**：操作系统资源分配最小单位；有独立虚拟地址空间；进程间隔离；切换开销最大。
2. **线程**：CPU 调度最小单位；共享所属进程内存、文件句柄；每个线程有自己栈；内核管理；切换需要内核态。
3. **协程 (Goroutine)**：用户态轻量级执行单元；跑在线程之上；共享线程资源；由运行时库调度；切换用户态完成。

> 层级关系：一个进程可以有多个线程；一个线程上可以跑多个协程（分时复用）。

## 线程之间同步、通信方式

1. 共享内存：互斥锁 Mutex、读写锁 RWMutex、条件变量 Cond；
2. 消息通信：管道 pipe；Go 推荐 Channel；
3. 信号量 Semaphore。

## OS 如何管理物理内存？为什么要虚拟内存

物理内存管理：操作系统维护空闲物理页；给进程分配物理页帧；管理页表；内存不足时 swap 换入换出。

虚拟内存好处：

1. **进程隔离**：每个进程独立虚拟地址空间，互不干扰。
2. 内存抽象，进程看到连续地址，物理内存可以碎片化。
3. **内存超限**：进程总虚拟内存可以大于物理内存，不常用页放到磁盘 swap。
4. 内存共享：多个进程虚拟地址映射到同一个物理页，实现共享内存。

## 虚拟地址通过页表转物理地址

1. CPU 的 MMU 内存管理单元接收虚拟地址。
2. 虚拟地址拆分为：**页号 + 页内偏移**。
3. MMU 查页表，虚拟页号→物理页框号；TLB 缓存加速页表查找。
4. 物理地址 = 物理页框号拼接页内偏移。
5. 如果页表标记该页不在内存，触发**缺页中断**，操作系统从磁盘加载页面。

> 页：虚拟内存的块；页框：物理内存同等大小内存块。

## 生产者‑消费者模型；多线程共享数据如何保证并发安全

生产者生成数据放到缓冲区，消费者从缓冲区取出消费，解耦生产消费速率。
并发安全方案：

1. 互斥锁保护缓冲区，同一时间只允许一个线程读写；
2. 条件变量：缓冲区满生产者等待，缓冲区空消费者等待；
   Go 中直接用 channel 实现。

## HTTP 和 HTTPS 区别

1. HTTP 明文传输，端口 80；HTTPS=HTTP+TLS 加密，端口 443。
2. HTTP 数据容易窃听篡改；HTTPS 加密传输。
3. HTTPS 需要数字证书做身份认证，HTTP 不需要。

## Redis 事务 MULTI/EXEC 工作机制；是否支持回滚，对比数据库事务

1. MULTI 开启事务；后续命令入队；EXEC 一次性批量执行队列内所有命令。DISCARD 放弃。
2. **不支持回滚**：
   - 如果入队时报语法错误，EXEC 直接全部不执行；
   - 如果执行阶段运行时错误（比如对 string 做 hset），错误命令失败，**前面已经执行成功命令不会回滚**。
3. 和传统数据库区别：数据库事务失败整体回滚；Redis 事务没有回滚能力，需要业务自己处理错误。

### Redis 分布式锁；SET NX EX 实现；释放锁为什么用 Lua 脚本

`SET lock_key value NX EX expire_time`

- NX：key 不存在才设置；EX 设置过期时间；**原子完成加锁 + 过期时间设置**，防止加锁后进程宕机锁永久不死。

释放锁为什么 Lua：
不能简单`DEL key`，会误删别人的锁。流程要：**判断锁属于当前持有者，再删除**。`GET + DEL`两条命令中间会被其他线程抢占，非原子。Lua 脚本保证判断 + 删除是服务端原子执行。

Lua 示例逻辑：

```lua
if redis.call('get',KEYS[1]) == ARGV[1] then
    return redis.call('del',KEYS[1])
else
    return 0
end
```

### Go 中数据竞争（Data Race）如何排查？

数据竞争：多个 goroutine 并发读写同一个变量，**至少一个写操作，没有同步保护**。

- 编译 / 运行加检测：`go run -race` / `go test -race`，自动检测并打印竞争栈（开发环境）；
- pprof + trace；
- 规范：共享变量必须锁、channel、atomic 保护。

> 注意：`-race`会大幅降低性能，生产环境不能开。

### Go Map 并发读写为什么是危险的？它有什么内部机制？

Go 原生 map**不是并发安全**。并发写（写 + 读，写 + 写）会触发 panic。
底层：哈希表，由多个 bucket 组成，每个 bucket 放 8 个 kv；溢出 bucket；oldbucket 用于扩容。
**并发写时，多个 G 同时修改 bucket，会破坏内部链表结构，直接 panic。**

> 读多写少：sync.Map；读写均衡：map + sync.RWMutex。

### Go Map 的扩容机制是怎样的？

两种扩容：

1. **增量扩容（正常扩容）**：负载因子 > 6.5；新建更大 bucket 数组，oldbucket 保留；**不是一次性迁移，访问时渐进迁移 kv**；
2. **等量扩容（same size）**：溢出 bucket 过多，bucket 满，但是元素数量不多；不扩大容量，只是清理溢出桶，整理内存。

### 解释一下 Go 的三色标记 GC 算法

三色标记：

- **白色**：初始状态，不确定是否存活；
- **灰色**：存活，子对象还没扫描；
- **黑色**：存活，子对象全部扫描完毕。

流程：

1. **初始标记（STW）**：扫描根对象（栈、全局变量），根对象标记灰色；
2. **并发标记**：和业务代码并行运行，遍历灰色对象，把引用对象标记灰色，自身变黑；
3. **重新标记（STW）**：短暂暂停，处理并发标记期间新增 / 修改引用；
4. **并发清扫**：并发回收白色对象，放回内存。

**混合写屏障**：解决并发标记时黑色对象引用白色对象导致漏标，减少 STW 时间。

### 整个 GC 过程会触发几次 STW？

**2 次 STW：初始标记、重新标记。清扫阶段并发，无 STW。**
Go1.9 之后引入混合写屏障，消除了栈扫描的 STW，两次 STW 都非常短（微秒～毫秒级）。

### 你做过哪些性能优化？遇到了什么问题，怎么解决的？

> 面试必问，准备 1 个 Go 后端优化案例，示例参考：
> 例子：接口 QPS 上不去，pprof 定位到大量锁竞争。

## redis 创建成功，mysql 写入失败怎么办

> 场景：先写 Redis 成功，写 MySQL 数据库失败，出现**缓存与数据库数据不一致**

1. **不能直接丢弃**：Redis 已经写入，MySQL 失败，直接放行会出现缓存脏数据。
2. 方案 1：**删除 Redis 缓存**。MySQL 写入失败，立刻删除刚写入 Redis 的数据，后续请求回源读 MySQL，保证缓存和数据库一致。
3. 方案 2：消息队列重试。把本次 DB 写入任务投递 MQ，不断重试 MySQL 写入；注意设置重试次数上限，超过则告警人工介入。

## 压测怎么做的

1. **明确压测目标**：确定接口 QPS、响应时间 p95/p99、CPU、内存、连接数指标；确定压测场景（正常、秒杀、并发）。
2. **选压测工具**：Go 后端常用 `wrk`、`vegeta`；

## 缓存击穿是什么，怎么解决的

- **缓存击穿**：**热点 key 过期的一瞬间，大量并发请求同时打到数据库**。缓存中热点 key 失效，大量请求绕过缓存直接访问 MySQL。

> 和缓存雪崩（大量 key 同时过期）、缓存穿透（查不存在的数据）区分。

解决：

1. **互斥锁（分布式锁）**：缓存失效时，只有一个请求去更新缓存，其他请求等待。Go 可用 redisson 分布式锁。缺点：带来等待，吞吐量下降。
2. **热点 key 永不过期（逻辑过期）**：Redis 不设置 TTL；把过期时间放在 value 内部。后台异步线程刷新数据；请求直接返回缓存，不等待更新。适合热点数据。
3. 预热：提前把热点数据加载进缓存。

## 并发场景怎么处理（加锁，channel）

1. **sync 包锁机制**

- sync.Mutex 互斥锁：同一时间只有一个 goroutine 访问临界区。
- sync.RWMutex 读写锁：读多写少场景，多个读可以并行，写互斥。适合缓存。

2. **Channel 通信：不要通过共享内存通信；通过通信共享内存**
   使用 channel 传递数据，goroutine 之间不共享变量；单向 channel 控制读写。
3. 其他：sync.WaitGroup 等待协程、sync.Once 只执行一次、context 控制协程退出。

## go 中的 channel 的区别

1. **无缓冲 channel**：`ch := make(chan int)`
   发送 goroutine 和接收 goroutine 必须同时就绪，否则阻塞；同步通信。
2. **有缓冲 channel**：`ch := make(chan int, 10)`
   内部有缓冲区；缓冲区未满，发送不会阻塞；缓冲区空接收才阻塞；异步。
3. **单向 channel**`chSend chan<- int` 只写 channel`chRecv <-chan int` 只读 channel，用于函数参数约束。
4. 关闭 channel：关闭后还可读，写会 panic；range 遍历 channel 直到关闭。

## Golang 对比 C++，并发编程的区别和优势

1. **协程模型不同**

- C++：C++20 引入了**无栈协程语法（coroutine）**，但**标准库只定义语法，没有内置调度器**。
  - 老版本 C++ 没有原生协程，只能使用 OS 线程（栈 MB 级，很重）或第三方库（libco 等）。
  - C++20 协程是**无栈协程**：没有独立栈，状态保存在堆上协程帧；必须自己实现事件循环 / 调度器（asio/stdexec）。**如果协程内部执行阻塞系统调用，会直接卡住整个 OS 线程，不会自动迁移任务**。
- Go：原生 goroutine，**有栈轻量级协程**，由 Go 运行时 GMP 做 M:N 调度，goroutine 不永久绑定 OS 线程；可以轻松创建数十万 goroutine。当 goroutine 触发阻塞 syscall 时，runtime 自动把 G 和 M 解绑，P 换新 M 继续跑其他任务，线程不会被卡死。

2. **通信方式**

- C++：不管是普通线程还是 C++20 协程，**没有原生 channel**。并发主要依靠共享内存 + mutex / 条件变量；协程之间通信逻辑需要自己封装，容易出现竞态、死锁。
- Go：理念**不要通过共享内存来通信，要通过通信来共享内存**，原生提供 channel；同时也提供 sync 包锁，两种方案按需选择。

3. **内存栈管理**

- C++
  - OS 线程：栈固定大小，栈溢出直接 crash；
  - C++20 协程：无栈模型，不存在栈扩容，但**协程帧生命周期、内存释放全由开发者管控**，容易出现悬空引用、内存泄漏。
- Goroutine：**独立栈，动态扩缩容**，初始 2KB，运行时自动增长、收缩，栈管理完全由 runtime 自动处理，不用开发者手动维护。

4. **工具与语法层面**

- Go：runtime 全权接管调度；`go func(){}`一键拉起 goroutine；`sync.WaitGroup`、`context`原生提供协程生命周期、超时取消能力。
- C++：
  - C++ 线程：创建销毁开销大，海量并发成本高；
  - C++20 协程：语法复杂，需要手写 promise、awaiter、coroutine_handle，学习成本很高；调度、超时、取消都需要自己实现或依赖第三方库。

> 总结一句话（面试收尾）
> C++20 虽然提供协程语法，但它只是**无栈协程，缺少内置调度器，阻塞 IO 会卡住线程**；而 Go 的 goroutine 是 runtime 完整托管的 M:N 有栈协程，调度、栈管理、并发原语全部原生内置，开发海量并发服务更简单。

## Goroutine 轻量级，除初始栈 2KB 外还有哪些体现

1. **调度在 Go 用户态 Runtime 完成，减少内核态切换**：goroutine 切换不需要陷入操作系统内核；OS 线程切换要保存大量寄存器，开销巨大。
2. **栈动态伸缩**：初始 2KB 栈，按需扩容、缩容，不会直接分配大内存；成千上万 goroutine 内存整体可控。
3. **goroutine 创建销毁开销极小**，远小于 OS 线程；OS 线程创建要内核分配内核栈、PCB 等资源。
4. GMP 复用 OS M（系统线程），大量 goroutine 复用上少量操作系统线程，不需要一个协程绑定一个线程。

## Go 如何管理大量 goroutine — GMP 模型

GMP 三个核心对象：

- **G(goroutine)**：代表一个 goroutine，保存任务函数、栈、程序计数器，是待执行任务。
- **M(machine)**：操作系统内核线程，真正执行代码的载体。
- **P (processor) 逻辑处理器**：调度器上下文，持有本地运行队列`runq`，P 的数量默认等于 CPU 核心数 GOMAXPROCS；M 必须绑定 P 才能执行 G。

调度流程：

1. 用户`go func()`创建 G，放入 P 的本地运行队列 runq。
2. M 绑定 P，P 从本地队列取出 G，M 执行 G。
3. P 本地队列满了，G 会放到**全局运行队列 GRQ**。
4. P 本地队列没有任务时，触发 work‑stealing 工作窃取，从其他 P 偷 G，或者去全局队列拿 G。
5. M、P 可以分离；M 可以被复用，不需要每个 goroutine 独占 OS 线程。

> 简单总结：G 是任务，M 是内核线程，P 是调度器，M 必须拿到 P 才能运行 G；通过复用 M 实现大量 goroutine。

## Work‑Stealing 工作窃取解决什么问题

**解决各个 P 之间任务负载不均衡的问题**。

场景：多个 P，有的 P 本地 runq 队列任务很多，CPU 很忙；有的 P 本地队列已经空了，CPU 空闲。

- 空闲的 P 会随机找别的 P，从对方本地队列偷一半 G 到自己队列执行。
- 充分利用多核 CPU，避免部分 CPU 核心空闲、部分过载。

> 注意：全局队列任务不会被窃取，P 空闲优先尝试窃取其他 P 本地队列，再去全局队列拿任务。

## Goroutine 发生系统调用时，调度过程变化

> 例如：socket 读写、文件 IO 阻塞系统调用。

1. G 正在 M 上执行，发生阻塞 syscall 系统调用；M 进入内核阻塞。
2. **M 和 P 解绑分离**：P 不能跟着阻塞，P 需要找别的 M 继续跑其他 G。
3. runtime 寻找空闲 M；没有空闲 M 就新建 M；新 M 绑定 P，P 继续执行队列里其他 G。
4. 原来阻塞的 M 带着阻塞的 G 继续在内核等待系统调用返回。
5. 当 syscall 调用完成返回：原来的 M 尝试获取 P；
   - 如果有空闲 P：M 绑定 P 继续运行这个 G；
   - 如果没有空闲 P：G 放到全局队列，M 归还放入线程池等待复用。G 等待被其他 P 调度执行。

效果：某个 goroutine 阻塞系统调用，**不会阻塞整个 P，不会卡住其他 goroutine 执行**。

## map 的特点和注意事项

**特点**

1. key 必须是可比较类型（不能是 slice、map、function）；value 无限制。
2. 底层哈希表，无序；遍历 range 顺序每次不一样。
3. 零值 map 是`nil`，nil map 可以读，但是**写入会 panic**。
4. 自动扩容，负载因子达到阈值触发扩容。

**注意事项**

1. nil map 不能写，声明后要么 make 初始化，要么字面量初始化。
2. **并发读写不安全，不加锁读写直接 panic**。
3. range 遍历 map 的时候删除 key 是允许的；新增 key 不一定能遍历到。
4. map 的 value 如果是结构体，不能直接修改结构体内部字段；需要整体赋值取出修改再写回。
5. map 不是引用类型，是 hmap 结构体指针；函数传参拷贝的是指针，函数内部修改会影响外部原 map。

## map 为什么并发读写不安全

Go 原生 map 内部没有任何同步保护。
底层 hmap 有读写的标志位；当一个 goroutine 在写（插入、删除），另一个 goroutine 同时读 / 写，会破坏哈希表内部数据结构（桶、溢出桶），导致数据错乱。

runtime 会检测并发读写，直接抛出 panic，防止发生更严重内存损坏。

> 不是数据竞争导致脏数据，runtime 主动检测直接 panic。

## sync.Map 底层如何实现并发安全

sync.Map 不是用普通互斥锁保护整个 map；采用**读写分离设计**，两个主要结构：

1. **readOnly（read map）**：只读，无锁访问；保存 key 的 entry。entry 有标记：未删除、已删除。读优先走 read，不加锁，性能高。
2. **dirty（dirty map）**：读写都需要加互斥锁`mu`；新增、修改、删除的 key 先落到 dirty。

执行逻辑：

1. **读**：优先访问无锁 readOnly；如果 read 找不到或者标记被删除，再加锁去 dirty 中查找。
2. **写 / 新增**：加锁，优先操作 dirty；如果 key 在 read 中标记删除，更新 read 的 entry 指针。
3. **提升 (promote)**：当 read miss 次数累计超过 dirty 长度；把 dirty 整体升级变成新的 readOnly，dirty 置 nil。
4. **删除**：不会立刻从 read 删除；只是把 read entry 标记为已删除；dirty 中真正删除。

> 核心：读尽量无锁；写需要加锁；定期把 dirty 提升到 read，减少锁竞争

## 无缓冲 channel 和 有缓冲 channel 区别

1. **无缓冲`make(chan T)`，缓冲区长度 0**
   发送 goroutine 和接收 goroutine 必须同时就绪。发送操作阻塞直到有 goroutine 接收；接收阻塞直到有 goroutine 发送。**同步通信，发送接收双方握手**。
2. **有缓冲`make(chan T, N)`，缓冲区大小 N**
   内部有环形缓冲区。缓冲区未满，发送不会阻塞；缓冲区不为空接收不阻塞。缓冲区满发送阻塞；缓冲区空接收阻塞。异步解耦。

### 无缓冲 channel（同步握手）

适合两个 goroutine 之间做**同步通知、事件握手**，保证两件事情时序。

> 例子：任务完成通知。A goroutine 做完逻辑，往无缓冲 ch 发送；B goroutine 接收。保证 A 发送那一刻 B 一定已经准备好，严格同步。

```
ch := make(chan struct{})
go func(){
    // 做任务
    ch <- struct{}{} // 等待外面goroutine接收才会解除阻塞
}()
<-ch // 等待协程任务执行完成
```

### 有缓冲 channel（异步，队列、限流）

1. **任务队列**，缓冲区 N 当作任务队列；生产者不断投递任务，消费者消费，解耦生产者消费者，生产者不用等待消费者立刻处理。

```
taskCh := make(chan Task, 100)
```

2. **限流控制并发**：缓冲区大小等于最大并发数量，做信号量。

```
limitCh := make(chan struct{}, 5) //最多5个并发
```

> 例子：爬虫，控制最多同时发起 5 个 http 请求。

> 小结：无缓冲强调同步等待；带缓冲做队列、削峰、限流。

### Redis 持久化、过期策略、内存淘汰策略

- 持久化：RDB（快照，全量）、AOF（追加写命令，增量），可以混合使用。
- 过期策略：惰性删除（访问的时候才删过期 key）+ 定期删除（定时抽样扫描过期 key）。
- 内存淘汰策略：volatile‑lru、allkeys‑lru、volatile‑lfu、allkeys‑lfu、volatile‑ttl、no‑eviction。

> 区分核心：**volatile 系列只会在【设置了过期时间】的 key 里面淘汰；allkeys 系列在【全部 key，不管有没有过期】里面淘汰**s

1. volatile 系列的共性：**如果没有带过期的 key 可供淘汰，就会触发 no-eviction 行为，写报错**。
2. 选型一句话总结：
   - 纯缓存：`allkeys-lru`（最通用）
   - 热点区分明显：`allkeys-lfu`
   - 部分数据永久保存，只清缓存：`volatile-lru`
   - 优先清快要到期的缓存：`volatile-ttl`
   - 数据不能丢，内存必须提前规划：`no-eviction`

## MySQL 覆盖索引

> 覆盖索引：**索引包含 SQL 查询所需要的全部字段，不需要回表读取主键行数据**，`explain Extra显示Using index`。

1. InnoDB 二级索引叶子节点存的是主键；普通二级索引查到主键后，需要回表去聚簇索引拿行数据。
2. 如果 select 的所有列，全部存在于二级索引的列上，就不用回表，直接从索引拿结果，就是覆盖索引。

示例表`user(id,name,age)`

- 索引：`idx_name_age(name,age)`
- SQL：`select name,age from user where name='xxx'` → 覆盖索引，Using index。
- SQL：`select name,age,id from user where name='xxx'`，id 本身就在二级索引叶子，同样触发覆盖索引。
- SQL：`select name,age,phone from user where name='xxx'`，phone 不在索引，需要回表。

**优点**：避免回表 IO，查询性能大幅提升；
**限制**：select 列全部要包含在索引字段，不要 select *。

## MySQL 深分页怎么解决

> 问题：`limit offset,size`，offset 很大时，mysql 扫描 offset+size 行，丢弃 offset 行，返回 size 行，性能极差。

### 主键索引分页（最常用）

**记住上一页最大 id，where id > last_id limit size**

```sql
-- 不推荐深分页
select * from table order by id limit 100000,20;

-- 优化，id有序自增主键
select * from table where id > 100000 order by id limit 20;
```

优点：走主键索引，性能稳定；
缺点：不能跳页，只适合滚动下拉，不适合 “跳转到第 1000 页”。

### 子查询延迟关联

```sql
select t.* from table t inner join (select id from table order by id limit 100000,20) temp on t.id = temp.id;
```

先通过索引拿到 id，再 join 拿完整行，减少回表开销。

## go 语言里面有哪些数据类型？

分为**基础类型**、**复合类型**、**引用类型**、**接口类型**、**指针类型**

1. 基础类型：`bool`、`string`、int/int8/int16/int32/int64、uint、float32/float64、complex64/complex128、rune、byte
2. 复合类型：数组`array`、结构体`struct`
3. 引用类型：`slice`切片、`map`、`channel`
4. 指针类型：`*T`
5. 接口类型：`interface`

> 一句话记忆：基础、结构体数组、引用 (slice/map/chan)、指针、interface

## slice 是并发安全的吗？

**slice 本身不是并发安全**。
底层是数组指针 + len+cap，多个 goroutine 同时读写同一个底层数组会产生竞态。

- 只读：没问题
- 一写多读 / 多写：会数据竞争，需要加锁`sync.Mutex`。

## make 一个 map 与 new 一个 map 有什么区别？

- `new(map[int]int)`：只分配**map 结构体内存**，返回指针，**不会初始化底层哈希表**，得到 nil map，直接写入 key 会 panic
- `make(map[int]int)`：**初始化底层哈希表**，返回已经初始化好的 map 引用

## make 和 new 创建的 map 哪一个是可以直接拿来用的？

**make 创建的 map 可以直接读写；new 出来的是 nil map，不能直接写。**

## goroutine 之间怎样传递数据？

两种主流方式：

1. **channel（推荐，CSP 模型）**：协程之间通过 channel 传递数据，不共享内存
2. **共享内存 + sync 锁**：多个 goroutine 共享变量，配合`sync.Mutex/RWMutex`保护（容易出竞态）

> 面试金句：**不要通过共享内存通信，通过通信共享内存**

## sync.WaitGroup () 的 ADD () 方法是干什么的？

`wg.Add(delta)`：**修改等待计数器的值**。delta 正数一般在协程启动前调用，代表新增等待任务。

- 计数器 > 0：Wait () 阻塞
- 计数器 = 0：Wait () 解除阻塞
  注意：Add**不要放到 goroutine 内部**，会有竞态风险。
  `Done()`等价`Add(-1)`

## 可重复度隔离级别解决了幻读问题吗？

**MySQL InnoDB RR 级别通过 MVCC + 间隙锁，解决了**【当前读】场景下的幻读；**快照读依然存在幻读现象**。

> 面试一句话：RR 不能完全杜绝幻读，快照读下还会出现幻读；加锁的当前读通过间隙锁防止幻读。

## 什么是幻读？

同一个事务内，**前后两次相同的范围查询，第二次查到了第一次不存在的新插入记录**。

> 区分：脏读（读到未提交）、不可重复读（同一条记录被别人修改）、幻读（别人新增 / 删除，范围查询行数变化）

## 什么是快照读？

利用 MVCC，读取**事务快照版本**的数据，不加锁，读到的是历史快照，不会阻塞其他事务。
普通`select * from t`默认就是快照读。
与之对应：**当前读**：`select ... for update / lock in share mode`、update、delete、insert，读取最新数据，会加锁。

## mysql 的索引有了解过吗，把你了解的简单说下

InnoDB 是聚簇索引，底层 B + 树：

1. **聚簇索引**：主键索引，叶子节点存完整行数据；一张表只能一个聚簇索引
2. **二级索引（非聚簇）**：普通索引，叶子节点存主键值，查到主键后回表查询完整数据
3. 联合索引：多个字段，最左前缀原则
4. 覆盖索引：查询字段全部在索引内，**不需要回表**，性能高
5. 索引失效场景：like % xxx、隐式类型转换、or、函数操作索引列、not in != 等
6. 索引优点：减少 IO 加快查询；缺点：占用磁盘，写操作（增删改）维护索引成本高

## 如果一个索引列是 string 类型的，但在查询的时候把它当成了 int 类型（隐式类型转换），这种情况索引会失效吗？

**会索引失效**
`where str_col = 123`，数据库会**对索引列 str_col 做函数转换，转为数字**，索引列做运算，不走索引，触发全表扫描。

> 记住规则：**索引列不要做函数 / 转换**，常量转换没问题，列转换失效。

## GORM 的软删除机制说一下

GORM 软删除不是真正 delete，**更新 delete_at 字段（时间戳）**。

1. 模型内嵌 `gorm.DeletedAt` 字段，自动开启软删除
2. `Delete(&user)` 不会执行 DELETE 语句，执行 UPDATE，设置 delete_at 为当前时间
3. 查询时，GORM 自动加上`WHERE delete_at IS NULL`，过滤掉已软删除记录

## GORM 这个库里有没有一些你觉得很高级的操作

1. 事务：`Begin/Commit/Rollback`，支持嵌套事务、SavePoint
2. 钩子 Hook：BeforeCreate、AfterUpdate 等生命周期回调
3. 预加载 Preload：解决 N+1 查询问题，关联表一次性加载
4. 链式查询、子查询、SQL 表达式
5. 自定义 Logger，打印 SQL 慢日志

## JWT 是有状态的还是无状态的？

**JWT 本身无状态**，token 自带全部信息，服务端不需要在 redis/db 保存 token 信息，只校验签名。
缺点：签发后，在过期前**无法主动失效**。

## 如果有个用户已经登录了，我现在想把这个用户踢掉，怎样把已经给这个用户签发的令牌变为失效状态？

JWT 原生无法作废，几种方案：

1. **Redis 黑名单**：token 的 jti（JWT 唯一编号）存入 redis，设置过期时间和 JWT 过期一致；每次鉴权中间件先查黑名单，存在则拒绝访问（最常用）
2. 短有效期 JWT + RefreshToken：access_token 有效期很短（5~15min），就算被盗很快过期；refreshToken 单独存库 /redis，拉黑 refreshToken 即可踢下线
3. 版本号机制：用户表维护 token 版本号，JWT 携带版本号；版本号不一致直接拒绝（修改用户版本号实现踢人）

## 为什么不直接通过数据库通信而需要用消息队列呢？

直接数据库通信指：服务之间互相直接读写对方业务库。引入 MQ 主要解决下面问题：

1. **解耦服务**
   服务 A 不需要直接依赖服务 B 的数据库，A 只发消息到 MQ；B 消费消息。B 内部表结构变更不会直接影响 A。如果直连数据库，下游表字段、索引改动上游全部受影响，耦合极强。
2. **削峰填谷，抗流量突刺**
   上游瞬时大流量，数据库扛不住；MQ 缓冲消息，下游消费者按自己处理能力消费，保护数据库不会被突发流量打垮。直连数据库，峰值 QPS 全部压到 DB，极易慢查询、锁、雪崩。
3. **异步处理，提升响应时间**
   很多业务不需要同步完成（短信、日志、通知、后置业务计算）。主流程发完 MQ 直接返回，不需要等待下游处理完成，缩短接口 RT；直连数据库同步写会拉长接口耗时。
4. **流量广播，一对多分发**
   一个事件要通知多个下游，比如订单完成，需要通知积分、物流、推送。直连 DB 需要多个服务轮询或者多次写库；MQ 一次投递，多个消费组各自消费。
5. **可靠事件、最终一致性**
   可实现事件驱动，配合本地消息表 / 事务消息，完成分布式场景下事件通知；

## SSE vs Websocket

1. **SSE**：基于 HTTP 长连接，服务端单向推送，适合大模型输出、日志实时推送，协议简单；

2. **WebSocket**：双向通信，适合聊天类双向交互场景。

> SSE 适合只读流式输出，开发简单；WebSocket 适合双向收发。

## JWT vs Session

**网关统一鉴权**：一般不在每个业务服务写鉴权逻辑，在 API 网关层完成身份认证，解析后把用户 id 放到请求头透传给下游微服务；下游业务服务直接读取请求头。
**权限和认证区分**：认证（你是谁），授权（你能干什么）。认证拿到身份之后再做 RBAC 权限判断。

> 面试话术：项目采用网关层鉴权，使用 JWT 做身份凭证，登出通过 Redis 黑名单实现，网关拦截器统一校验 token，解析用户身份向下游透传。

# skill 的作用是什么

> 背景：在大模型 Agent / LangGraph 体系里的 Skill（技能）
> **Skill = Agent 可调用的能力单元**，封装了一段独立可执行逻辑。

1. 对大模型：提供**能力描述（function description）**，大模型判断什么时候调用这个 skill，填写入参；
2. 封装具体执行代码：比如查询数据库、调用 http 接口、文件读写、计算器；
3. 标准化输入输出：统一入参、出参格式，便于框架自动解析；
4. 解耦：模型只负责思考决策，真实动作交给 skill 执行；新增能力只需要新增 skill，不用改模型 prompt 主干。

一句话面试口述：Skill 是给 Agent 使用的工具，封装外部能力，让大模型可以按需调用，模型负责判断调用时机，skill 负责实际执行。

## equired 和 optional（仅 proto2，proto3 删掉了 required 关键字）

1. **required**：消息**必须携带这个字段**，缺少该字段，解析直接失败抛异常。
   - 坑：一旦定义 required，后续永远不能删掉这个字段、不能改成 optional。老版本程序收到不带这个字段的消息直接拒绝，线上滚动升级会灾难。Google 官方强烈不推荐使用 required。
2. **optional**：字段可选，消息里可以有也可以没有。
   - 带该字段：解析填充值；
   - 不带：返回类型默认值；proto2 还可以判断`has_xxx()`看有没有显式设置；

> proto3：默认隐式 optional，标量类型无法区分 “没设置” 和 “显式等于默认值”；proto3 也支持显式写`optional`，此时会生成 has 标记，可以判断是否显式赋值。

# 锁底层：多个线程抢锁，怎么知道锁已经被占用？

锁（mutex / 自旋锁）内部维护一个**共享原子状态变量**（比如一个 int / 原子指针），用来记录锁状态：空闲 / 已被持有，部分还会记录持有者线程 ID、等待队列。
关键点：**读 state、判断、修改 state 这三步必须原子**, 这个原子操作底层就是**CAS**。

## Nginx 反向代理有什么特点，是怎么分给后端服务器的？

### 反向代理特点

1. **隐藏后端真实服务**，客户端只和 Nginx 交互，后端节点对客户端不可见。
2. **负载均衡**，把请求分发多台后端，实现扩容。
3. **高并发高性能**：基于 epoll 多路复用，异步非阻塞模型，单机支持大量连接。
4. **附加能力**：可以做静态资源缓存、SSL 解密、限流、黑白名单、请求改写。
5. **解耦**：客户端不需要知道后端多实例，只访问 Nginx 地址。

### 请求分发（负载均衡）

Nginx 通过`upstream`定义后端服务集群，内置多种调度策略：

1. **轮询（默认）**：请求依次分配每台后端服务器。
2. **weight 权重轮询**：权重越大分到请求越多，用于机器性能不均场景。
3. **ip_hash**：按客户端 ip 哈希，同一个 ip 始终打到同一台后端，用于会话保持。
4. **least_conn**：选择当前连接数最少的后端节点。
5. url_hash、fair 第三方模块策略。

工作流程：客户端请求 Nginx → nginx 解析 upstream 配置，按负载均衡算法选出一台后端服务器 → 转发 http 请求给后端，拿到响应再返回给客户端。

### 什么是可重入分布式锁

同一个线程，已经拿到锁之后，可以再次获取同一把锁，不会自己把自己阻塞死。Redisson 实现的就是可重入分布式锁。
底层：redis hash 结构，key = 锁名，field = 线程唯一标识，value = 重入计数。每次加锁计数 + 1；释放锁计数‑1，计数归 0 真正删除锁。

## MQ 如何保证消息不丢失

> 消息丢失发生在 3 个阶段：生产者发送、MQ 服务存储、消费者消费。**每个阶段都做确认机制**。

1. **生产者端：保证消息可靠投递**
   - 开启生产者确认（ACK）：RabbitMQ 的 publisher-confirm；RocketMQ/Kafka 的发送回调。
   - 失败重试：发送失败做重试，注意**幂等**；
   - 消息落盘前不要认为发送成功；不要丢在内存直接返回。
   - 兜底：消息发送前先落本地消息表，定时任务扫描重试（事务消息 / 可靠消息最终一致性方案）。
2. **MQ 服务端：保证消息存储不丢**
   - 刷盘机制：开启**持久化**，消息写入磁盘，不是只放内存；
   - 集群多副本：Kafka 多副本、RocketMQ 主从，主节点宕机，副本保留数据；
   - 避免异步刷盘丢数据：根据业务选择同步刷盘（性能低，可靠性高）。
3. **消费者端：保证消费成功才确认 ACK**
   - **先执行业务，再 ACK**，顺序不能反。如果先 ACK，业务执行失败，消息丢失。
   - 关闭自动 ACK，手动 ACK；业务异常时不 ACK，消息重新投递。

> 额外注意：消息会重复投递，**保证不丢失 ≠ 不重复**，业务层必须做幂等。

## 分布式 ID 生成方案

### 方案对比（面试重点）

1. **数据库自增主键**
   简单，单点瓶颈；分库分表可用分段号段模式（预取一批 ID 到内存）。
2. **UUID / GUID**
   无序、长字符串，数据库索引性能差，不推荐做主键。
3. **雪花算法 Snowflake（最常用）**
   64bit long：时间戳 + 机器 id + 数据中心 id + 序列号。
   ✅ 趋势有序、高性能，内存生成，不依赖 DB。
   ❗ 问题：依赖系统时钟，**时钟回拨会产生重复 ID**。
   解决：记录上一次时间戳，检测到时钟回拨，暂停等待或者使用机器内备用序列号。
4. **Redis INCR**
   `INCR key`，原子自增；适合短 ID；缺点：Redis 单点风险，需要集群 + 持久化。

## RDB 的过程

RDB 就是**把某一瞬间内存全部数据 dump 到磁盘二进制 rdb 文件**，触发分**手动触发**和**自动触发**。

### 1. 触发方式

- **手动**：`SAVE` / `BGSAVE`
  - `SAVE`：主线程阻塞，直接 dump，大数据量会卡死 redis，生产不用。
  - `BGSAVE`：**fork 子进程**，不会阻塞主线程（生产默认）。
- **自动触发**：配置文件 `save 秒数 变更次数`，如 `save 900 1` 900s 至少 1 个 key 修改就执行 BGSAVE；另外主从全量复制、执行 shutdown 也会触发 RDB。

### BGSAVE 完整流程（重点，面试必背）

1. Redis 主线程收到 BGSAVE 指令，调用`fork()`创建**子进程**；

> fork 会复制进程页表，采用**写时复制 COW**，不会立刻拷贝全部内存，降低开销。

2. fork 完成后，**子进程负责遍历内存，把当前时刻数据写入临时 RDB 文件**；主线程继续正常处理客户端请求。
3. 在子进程写文件期间：如果主线程修改 key，会触发 COW，把该页内存复制一份，子进程看到的还是 fork 瞬间的旧数据，保证快照一致性。
4. 子进程写完临时 rdb 文件后，**原子 rename 替换旧的 rdb 文件**，完成快照。
5. 子进程退出。

## Redis集群

Redis 集群有**3 套主流方案**：主从复制 + 哨兵 Sentinel + Redis Cluster（官方分片集群）

### 1. 主从复制（基础）

一主多从，主节点写，从节点只读；从节点复制主节点数据，实现读写分离。
问题：**没有自动故障转移**，主挂了需要人工切换。

### 2. Sentinel（哨兵集群，高可用，不分片）

哨兵是独立进程集群，监控主从节点；

- 自动检测节点下线；
- 主节点故障，哨兵自动选举新主，自动故障转移；
- 对外提供统一主节点地址。

> 局限：**不能分片，所有数据全量存在主节点，单节点内存上限，无法水平扩容存储**。

### 3. Redis Cluster（官方分片集群，Redis3.0+，最常问）

> 核心：**分片 + 高可用，数据分散到多个主节点**，可以扩容存储。

1. **哈希槽 slot**：一共 `16384` 个 slot，key 通过 `CRC16(key) % 16384` 计算 slot，每个主节点负责一部分槽位。
2. 架构：至少 **3 主 3 从**，每个主节点挂载从节点，主挂了从自动升主。
3. 客户端：需要集群客户端，请求 key，客户端算出 slot，直接路由到对应节点；
   若访问节点不对，返回 MOVED 重定向。
4. 扩容缩容：迁移 slot，在线迁移，不停机。

**缺点**：

- 不支持多 key 批量操作（跨 slot 的 mget/mset 事务受限）；
- 集群内部有一定开销；
- 只支持数据库 0，不能 select 切换 db。

1. **语言层面原生支持并发**：`go func()` 直接启动协程，不需要复杂线程库；
2. **M:N 调度**：多个 goroutine 映射到少量操作系统线程，由 Go runtime 调度，不是完全交给操作系统；
3. **CSP 思想**：提倡使用 channel 通信共享内存，而不是用共享内存加锁；
4. 开销极低，可以轻松起几万、几十万 goroutine；
5. runtime 帮我们处理栈扩容缩容，栈自动增长收缩，C++ 线程栈大小固定。

> 优势总结：开发简单、协程开销小、调度在 runtime 做，高并发场景开发效率高。

## Goroutine 轻量级，除初始栈 2KB，还有哪些体现

1. **栈是动态伸缩**：初始 2KB，不够自动扩容，空闲自动缩栈；OS 线程栈是固定大小。
2. **调度发生在用户态**：goroutine 切换大部分不需要陷入操作系统内核，上下文切换代价远小于 OS 线程。
3. **创建销毁代价小**：runtime 管理，不需要向操作系统申请释放线程资源，可以轻松创建十万级别 goroutine。
4. **上下文小**：goroutine 只保存少量寄存器、栈指针等信息；OS 线程要保存完整 CPU 寄存器组。

## Go 如何管理大量 goroutine？GMP 模型

GMP 三个核心概念：

- **G(goroutine)**：协程，保存任务、栈、状态，我们写的 go 函数就是 G。
- **M(machine)**：操作系统内核线程，真正执行代码。
- **P(processor)**：逻辑处理器，调度器上下文，持有本地运行队列，保存调度需要资源；P 的数量默认等于 CPU 核心数。

**整体流程**：

1. 我们启动 goroutine，G 被创建，优先放到当前 P 的**本地队列**；本地队列满放入全局队列。
2. P 绑定 M，M 执行 P 上的 G；G 运行完，M/P 继续取下一个 G 执行。
3. P 负责调度，M 负责干活；一个 M 必须绑定 P 才能执行 G。
4. 当 P 本地队列没有任务，会通过**工作窃取**从其他 P 偷 G，或者取全局队列 G。

## Work‑Stealing 工作窃取解决什么问题

**问题**：各个 P 的本地 goroutine 任务数量不均衡。有的 P 任务很多忙不过来，有的 P 本地队列为空空闲，CPU 资源浪费。

**工作窃取机制**：空闲的 P，从其他繁忙 P 的本地队列偷一半的 goroutine 放到自己队列来执行。

> 注意：偷是偷别人本地队列；全局队列所有 P 公平拿。
> 目的：**均衡各个 P 的任务负载，充分利用多核 CPU，避免部分 CPU 核心闲置**。

## Goroutine 发生系统调用，调度过程变化

G 执行系统调用（如读文件、sleep）会阻塞 M：

1. G 正在 M 上运行，发起**阻塞的系统调用**；此时 M 陷入内核阻塞。
2. **P 会和当前 M 解绑**。
3. 调度器找一个空闲的 M（新建 M 如果没有空闲），接管这个 P；P 继续运行队列里其他 G，CPU 不会卡住。
4. 原来阻塞的 M 带着 G 继续在系统调用里等待。
5. 系统调用返回之后，这个 G 要重新找 P；如果拿到 P 就继续执行；拿不到 P，G 放到全局队列，M 归还。

> 关键点：阻塞 syscall 不会卡住整个 P，不会浪费 CPU，这是 goroutine 高并发的关键。

## MySQL InnoDB 引擎的索引是怎么实现的

InnoDB 索引底层采用 **B + 树**，并且是**聚簇索引**。

1. **聚簇索引（主键索引）**：把整行数据存放在 B + 树叶子节点；叶子节点存放完整的一行记录，非叶子节点只存索引键值 + 页号，用于导航查找。表的数据本身就放在主键 B + 树叶子，**数据和主键索引是同一棵树**。
2. **二级索引（普通索引、唯一索引）**：叶子节点**不存完整行数据，存主键值**。查到叶子得到主键后，需要回表，拿着主键去聚簇索引再查一次，拿到完整行记录。
3. B + 树特点：所有数据全部在叶子节点；叶子节点通过双向链表串联，方便范围查询；非叶子只做索引导航。
4. 数据存储单位是页，默认一页 16KB。

> 如果表没有主键，InnoDB 自动生成隐藏 rowid 作为聚簇索引。

## InnoDB 哪些字段适合做索引

1. **where 经常用来过滤、查询条件的字段**；
2. `join`关联条件字段；
3. `order by`、`group by`经常排序分组的字段；
4. 区分度高（基数大），比如手机号、id；
5. 短字段，占用存储空间小，索引页可以存放更多索引项，减少 IO；
6. 唯一度高的字段，优先考虑唯一索引。

## 秒杀面临的问题和难点是什么？

1. **流量洪峰**：短时间海量请求涌入，远超系统正常承载，数据库直接打满。
2. **超卖问题**：并发下库存扣减没有原子性，多个请求读到同一份库存，卖出数量大于实际库存。
3. **资源浪费**：大量用户下单后不支付，占用库存，其他人无法购买。
4. **一致性问题**：订单创建、库存扣减、消息通知需要保证最终一致。
5. **雪崩风险**：热点商品导致单库 / 单实例压力巨大，连锁拖垮整个系统。
6. **恶意请求**：刷接口、爬虫、黄牛请求。

> 常用方案：前端限流、按钮置灰；网关限流；Redis 预减库存；消息队列削峰；异步下单；超时订单自动释放库存。

## 为什么要用延迟队列渐进式实现超时订单自动取消？和直接设置 15 分钟再判断是否付款的差别是什么？

> 需求：下单成功，15 分钟未支付，自动取消订单，归还库存。

### 方案 A：延迟队列（推荐）

下单成功，投递一条 15 分钟延迟消息；消息到期被消费，查询订单状态：

- 未支付：取消订单 + 回滚库存
- 已支付：直接丢弃消息

### 方案 B：定时任务轮询（直接查 15 分钟前订单）

定时任务每隔一段时间（比如 1min）扫描数据库，查出 15 分钟前、未支付订单，批量取消。

## 假设秒杀场景没有分布式锁，怎么去实现秒杀活动？

分布式锁作用：控制并发扣库存，防止超卖。**不用分布式锁，核心思路：把库存扣减操作放到 Redis 单命令或者数据库原子 SQL，利用单线程 / 数据库事务原子性保证，而不是锁。**

1. **Redis Lua 脚本（最常用）**
   Lua 脚本在 Redis 中是原子执行。脚本里：判断库存 > 0 → 库存 - 1；返回扣减结果。

> Redis 单线程执行 Lua，天然不会并发竞争，不需要分布式锁。

2. **数据库原子更新 SQL**

```
update seckill_goods set stock = stock -1 where id=#{goodsId} and stock>0;
```

利用数据库行锁，并发更新同一行时串行执行，返回受影响行数判断是否扣减成功。

## 怎么理解虚表

1. **虚表 vtable**：每一个含有虚函数的**类**，会生成一张虚函数表，存放该类所有虚函数的函数地址。
2. **虚指针 vptr**：每一个对象，开头隐藏一个虚指针，指向本类的虚表。
3. 子类继承基类：
   - 继承基类虚表；如果子类重写虚函数，就**覆盖虚表中对应位置的函数地址**，替换成自己实现；没有重写就保留基类函数地址。
4. 注意：虚表存放在**只读数据段**，不是堆、不是栈。
5. 调用流程：`对象->vptr -> vtable[索引] -> 函数地址`。

> 一个类多张虚表？不会；**一个类一张虚表；每个对象一个 vptr**

## 构造和析构有虚函数吗？

### 构造函数 **不能是 virtual**

1. 虚表是在构造函数执行过程中才初始化；构造对象的时候，还没有虚指针。
2. virtual 的目的是通过基类指针调用子类；构造的时候子类对象还没构建完成，没有意义。

> 编译器直接报错：`virtual 构造函数`非法。

### 析构函数**可以是 virtual，强烈建议基类析构写成 virtual**

### ① 防超卖

核心逻辑：**先判断库存 > 0，再扣减库存，全部逻辑放在 Lua 脚本保证原子性**，不能分开`get+decr`（中间会被其他请求插入，引发超卖）。

```lua
-- KEYS[1]：库存key，ARGV[1]：要扣减的数量
local stock = tonumber(redis.call('get', KEYS[1]))
if stock >= tonumber(ARGV[1]) then
    return redis.call('decrby',KEYS[1],ARGV[1]) -- 返回扣减后库存
else
    return -1 -- 库存不足
end
```

### ② 一人一单（限制每个用户只能下单一次）

需要两套判断：1）库存充足；2）该用户没有已经下单（Redis set 存储已经下单的用户 id）。

```lua
-- KEYS[1]库存key，KEYS[2]已下单用户集合；ARGV[1]扣减数量，ARGV[2]用户ID
local stock = tonumber(redis.call('get',KEYS[1]))
local userExist = redis.call('sismember',KEYS[2],ARGV[2])
if stock >= tonumber(ARGV[1]) and userExist == 0 then
    redis.call('decrby',KEYS[1],ARGV[1])
    redis.call('sadd',KEYS[2],ARGV[2])
    return 1 -- 成功
else
    return 0 -- 失败：库存不足 或者 用户已经下单
end
```

> 注意：Lua 脚本只是预扣，真实扣减以数据库为准；Redis 和 DB 最终需要一致性方案（MQ、定时校验回补库存）。

## 大量相同 query 请求怎么解决：缓存 /singleflight

**singleflight（https://golang.org/x/sync/singleflight）**
核心：**相同 key 并发请求，只放行一次回源调用，其他请求等待复用这一次调用结果**。
当大量并发相同查询，只有第一个请求去查 DB/Redis；其余 goroutine 阻塞等待，复用同一个返回结果。
