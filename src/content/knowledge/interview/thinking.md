## Agent 落地

> 阶段 1

```

建立可靠的单 Agent 闭环
仓库规则、标准化 Issue、独立分支、自动测试、PR 模板、人工合并、执行报告。
目标：Agent 能够可靠地完成一个小 Issue。
```

> 阶段 2

```
建立可调度的任务流水线
依赖图、自动领取 Ready Issue、任务状态跟踪、失败重试、独立 Reviewer、并行开发。
目标：减少你手动协调 Agent 的时间。
```

> 阶段 3

```
构建自己的 Agent Orchestrator
统一任务队列、并发限制、工作区隔离、预算控制、审计日志、失败恢复和模型路由。
目标：把个人开发流程升级为可以复用的 Agent 工程系统。
```

## Agent 驱动开发

阶段 1：项目规划
AI 编写需求文档、架构设计、技术选型与开发路线图

阶段 2：GitHub 项目管理
创建仓库、制定开发规范、拆分 Epic 和 Issues、定义验收条件

阶段 3：Agent 自主开发
领取 Issue → 创建分支 → 编码 → 测试 → 提交 PR

阶段 4：自动化质量检查
CI、单元测试、静态检查、PR Review、集成测试

阶段 5：你负责验收和复盘
理解实现原理、检查设计缺陷、记录技术笔记、准备面试讲解

#### 优化流程

L1 · 项目目标层

你负责定义用户需求、项目边界、成功标准与优先级。

L2 · 规划与任务编排层

Planner Agent 分析需求，拆分 Epic、Issue、依赖关系和验收标准。

L3 · 开发执行层

Coding Agent 在隔离分支或工作区内领取任务、编码、测试、提交 PR。

L4 · 质量门禁层

CI、测试、静态分析、独立 Reviewer Agent 检查改动是否满足验收标准。

L5 · 集成与发布层

审核通过后由你批准合并，验证集成结果，维护版本与发布记录。

L6 · 反馈与恢复层

跟踪失败、阻塞、返工率和测试结果；失败时重试、回退或重新规划。

> 第一版完全可以由一个主 Agent 加脚本和 CI 实现。先把流程做可靠，再考虑多 Agent 协作。
> 从“Prompt 驱动”升级到“仓库规则驱动”
> 你不能指望 Agent 每次都记住一大段总控 Prompt。真正稳定的规则应该写进仓库，作为所有 Agent 共同遵守的项目契约。

```go
AGENTS.md  #Agent 通用开发规则
docs/
│   ├── PRD.md                # 产品需求
│   ├── ARCHITECTURE.md       # 架构设计
│   ├── API.md                # API 契约
│   ├── ROADMAP.md            # 开发路线图
│   ├── DECISIONS.md          # 架构决策记录
│   └── TESTING.md            # 测试规范

```

> 其中，AGENTS.md 可以规定：

- 开始任务前必须阅读哪些文档。
- 哪些目录允许修改，哪些接口不能随意变更。
- Go 代码格式、错误处理、测试和日志规范。
- PR 的要求，以及什么情况下必须暂停并向人类报告。
- 完成任务后必须更新哪些文档。
- 这样，你更换模型、重新开启会话，甚至让不同的 Agent 接手同一个 Issue，都不会完全依赖对话历史。

##### 从“拆分 Issue”升级到“依赖图 + 任务状态机”

应该先建立任务之间的依赖关系。
有了依赖图，Agent 才知道哪些任务可以并行、哪些必须等待。
每个 Issue 可以有以下状态：

```text
Ready -> In Progress -> In Review

Accepted 验收完成后进入此状态

Blocked 遇到依赖、设计冲突或测试失败时进入此状态
```

##### 从“一个 Agent 包办”升级到“角色分离”

建议先采用轻量的角色分工，而不是立刻搞一群 Agent 互相聊天。

| 角色        | 职责                             | 能否直接改代码   |
| ----------- | -------------------------------- | ---------------- |
| Planner     | 分析需求、设计架构、拆分任务     | 默认不改业务代码 |
| Implementer | 负责指定 Issue 的实现            | 可以             |
| Reviewer    | 独立检查代码、设计和测试         | 默认只审查       |
| Tester      | 检查验收条件、测试覆盖和异常场景 | 默认不改业务代码 |
| 你          | 决定架构方向、处理争议、批准合并 | 可以             |

> 最重要的是让 Reviewer 与 Implementer 尽量分离。

这里有个关键规则：PR 创建成功，不等于 Issue 完成；CI 通过，也不自动等于功能验收完成。

##### 从“测试通过就交付”升级到“分层质量门禁”

建议至少设定四道门：
第一道：提交前检查
格式化、单元测试、静态检查，检查任务范围是否超出 Issue。

第二道：PR 自动检查
CI、竞态检测、构建、依赖检查、必要的安全扫描。

第三道：独立审查
核对需求、错误处理、并发安全、接口兼容性和测试有效性。

第四道：集成验收
验证真实请求链路、异常行为、文档和整体构建，再由你批准合并。

### 三阶段推动

阶段 Agent 权限 你的职责
第一阶段：搭建骨架 规划、生成代码、创建 Issue、提交 PR 审核架构和目录设计
第二阶段：功能开发 自主领取明确的 Issue，开发并提交 PR 审核核心逻辑和测试
第三阶段：自动化迭代 自动处理符合条件的 Issue、CI 失败和部分 Review 意见 设定权限、处理高风险决策

> 建议使用这样的工作约束：

- 一个 Issue 对应一个明确的交付目标，尽量让一个 PR 只解决一件事。
- Issue 必须包含背景、任务范围、接口约定、验收标准和测试要求。
- Agent 不得擅自修改无关模块、删除测试或为了通过 CI 而降低检查标准。
- PR 必须通过测试、go vet 等检查，关键模块需要人工审查。
- 数据库迁移、生产环境部署、密钥和付费资源操作，需要额外审批。

##### “失败恢复机制”

通宵运行时，这个机制尤其重要。
给 Agent 设置明确的停止条件：

- 同一测试连续失败两次：暂停，分析根因，不要盲目重复修改。
- 修改公共接口或架构文档：检查是否影响其他未完成任务。
- 发现任务依赖不存在或需求有歧义：标记 Blocked。
- CI 失败：先读取真实日志，再修复，不得跳过测试。
- 达到重试次数或运行预算：保存工作状态，输出交接报告。
- 发现主分支变化：同步并重新验证，不要强行覆盖。
  每轮结束时，输出一份结构化的执行报告：
  本轮完成：
- Issue #12
- PR #18

验证结果：

- go test ./...：通过
- go vet ./...：通过
- 竞态检测：通过

未解决的问题：

- 某 Provider 的流式响应尚未实现

阻塞任务：

- Issue #15 依赖 Issue #12 合并

下一步：

- 等待人工审核 PR #18
- 通过后执行 Issue #15

这样，Agent 即使中途崩溃、会话结束或者达到运行限制，也能够恢复工作，而不是每次重新猜测项目进度。

## 现在的思路

> AI 做项目规划 → 创建 Git 仓库 → 拆分 Issues → 使用 gh 发布 Issues → Agent 逐个完成 Issue 并提交 PR → 持续推进项目。

- 不要把“让 AI 持续提交 PR”当成最终目标，而要让 AI 在明确的工程约束下持续交付可验证的功能。

1. 先冻结项目设计，再批量创建 Issue
   要求 AI 先生成 PRD.md、ARCHITECTURE.md、ROADMAP.md 和 DECISIONS.md。
   重点检查服务边界、API 协议、错误处理、数据模型、测试策略。设计不稳定时不要一次创建几十个 Issue，否则后面可能要集体返工。

2. Issue 必须足够小，而且有依赖关系
   每个 Issue 都要包含：

- 要解决的问题和明确的范围
- 前置依赖，例如 blocked by #12
- 验收条件和测试用例
- 允许修改的模块及不允许修改的范围
  使用 GitHub CLI 创建 Issue、设置阻塞关系是可行的。

3. 每个 Issue 对应独立分支和 PR
   建议使用这样的分支命名：
   feat/issue-12-provider-interface
   PR 描述中写明 Closes #12，并说明改动、测试结果、设计取舍。GitHub 会在 PR 合并后自动关闭关联 Issue。

4. 设置不可绕过的质量门槛.每个 PR 至少运行：

```bash
gofmt -w .
go test ./...
go vet ./...
```

另外可以使用 GitHub Actions、竞态检测 go test -race ./...、覆盖率检查和集成测试。

> 注意，Agent 不能仅仅声称“测试通过”。要检查实际执行结果，并让 GitHub 分支保护规则阻止未通过检查的 PR 合并。

5. 限制 Agent 的权限
   允许它创建分支、提交代码、创建 PR 和运行测试，但不要默认允许它直接向 main 推送、自动合并所有 PR、修改仓库保护规则或访问生产凭据。
   如果 Agent 能够执行 Shell 命令，还要限制命令执行环境、网络访问和密钥权限。自动化越强，权限边界就越重要

## 风险

| 风险         | 典型表现                                | 解决办法                           |
| ------------ | --------------------------------------- | ---------------------------------- |
| 架构漂移     | 不同 Issue 各自设计一套接口             | 固定接口契约，修改设计需要更新文档 |
| 任务依赖错误 | Provider 接口还没完成，就开始实现适配器 | 明确 Issue 阻塞关系                |
| 假测试       | 只测试 Mock，真实模型 API 无法调用      | Mock 测试与真实服务集成测试分开    |
| 无效循环     | CI 失败，Agent 不断修改又引入新问题     | 限制自动修复次数，超限就停下来报告 |

## issue

> 每个 Issue 最好都包含：

- 任务目标与明确的非目标。
- 允许修改的模块和依赖。
- 验收标准。
- 必须通过的测试。
- 完成后应提供的结果，例如 PR、测试日志和设计说明。

> PR 合并前至少检查：

- go test ./... 是否通过。
- go vet ./... 是否通过。
- 是否存在明显的竞态、资源泄漏、密钥泄露问题。
- 是否添加了与任务相符的测试。
- 是否破坏之前的 API 和模块约定。

## 心法：不要从"我要做 X 功能"开始，从"怎么算做完了"倒推

> 大多数人拆不动任务，是因为起点是一个名词（"实现 HTTP 缓存"），名词是无法拆的。把它换成一个可执行的验证动作，拆解自动就出来了：

```
❌ "实现静态文件缓存"
✅ "同一个文件连续请求 1000 次，只有第 1 次走 ifstream，用 strace -c 或计数器验证；wrk -t4 -c100 QPS 从 19.1k 提升到 ≥35k"

```

粒度检验：4 个问题，有一个答不上就说明太大

| 校验问题                                                  | 含义                                         | 判定结果                                                      |
| --------------------------------------------------------- | -------------------------------------------- | ------------------------------------------------------------- |
| 检查答不上来的含义                                        | 需求/方案本身模糊，没有清晰定义              | 答不上来：范围不清，需要先澄清                                |
| 能用一条命令验证吗？（如 `ctest -R buffer / curl / wrk`） | 是否具备自动化验证手段，可一键复现、验证结果 | 不能：缺少可验证标准，不合并                                  |
| 还没想清楚，或者没拆够                                    | 任务拆解不足，逻辑/边界未思考完整            | 没拆够：需要继续拆分任务                                      |
| 能在 0.5~2 天内做完吗？                                   | 评估任务体量                                 | 太大：任务范围过大，继续拆分                                  |
| 要同时改 3 个以上模块吗？                                 | 评估改动的影响面                             | 太大，或该先做「接口 PR」：改动模块过多，优先单独提交接口层PR |
| 能一句话说清不做什么吗？                                  | 控制边界，防止需求蔓延                       | 不能：本次PR容易出现范围跑偏                                  |

> 核心原则：issue 是范围合同。例如写 Buffer 单测时顺手去改 HTTP 缓存，属于违反合同。单人开发时 issue 的读者主要是自己，作用就是拦住这类范围跑偏。
