均匀消费的 3 个核心配置

关闭**自动消息确认**

自动确认会导致：消息一发送给消费者，RabbitMQ 就标记删除，

**不管消费者是否处理完成**，会丢消息且无法控制分发。
必须手动确认，让 RabbitMQ 知道消息已处理完成，再发送下一条。

设置**预取数（basicQos）= 1 同一个消费者，在未确认当前消息前，不要推送新消息给它 处理快的消费者会快速确认，立刻拿到新消息；处理慢的消费者阻塞，少拿消息 → 真正的能者多劳**

消费者处理完业务逻辑后，手动发送确认信号，RabbitMQ 才会删除消息并继续分发。

开启 **Confirm 模式 + Return 模式**，让生产者**精准感知消息状态**

**Confirm 模式**：消息**是否成功到达交换机（Exchange）**

**Return 模式**：消息**到达交换机，但无法路由到队列**时的回调

| 模式                 | 作用                                     | 触发条件               |
| -------------------- | ---------------------------------------- | ---------------------- |
| **Confirm 确认模式** | 监听消息**是否到达 Broker 交换机**       | 成功 / 失败都会触发    |
| **Return 退回模式**  | 监听消息**到达交换机，但无法路由到队列** | 只有**路由失败**才触发 |

RabbitMQ 是内存数据库，如果**不做持久化持久化**：就是把数据存到**磁盘**上
交换机持久化 + 队列持久化 + 消息持久化

**交换机持久化（Exchange Durable）**

- **参数**：`durable=true ：交换机存盘，MQ 重启不消失`
-

**. 队列持久化（Queue Durable）**

- **参数**：`durable=true`
- **作用**：队列结构存盘，MQ 重启不消失

**消息持久化（Message Persistent）**

- **参数**：`deliveryMode=2`（1 = 非持久化，2 = 持久化）
- **作用**：消息内容存盘，MQ 重启不消失

**为什么三者都持久化了，还会丢消息？**

1. **时间差问题**
   - 生产者把**持久化消息**发送给 Broker
   - Broker 收到消息，**写入磁盘缓存**
   - **还没来得及同步到物理磁盘**
   - 此时 Broker **断电 / 宕机**
   - 缓存数据丢失 → 消息没了！
2. **异步刷盘机制**
   - RabbitMQ 为了性能，**不是每发一条消息就立刻刷盘**
   - 它是**批量、异步**刷盘的
   - 刷盘前宕机 → 缓存中的持久化消息丢失！

MQ 把消息**发送给消费者**后，**立刻认为消息消费成功**，并删除消息。

**手动告诉 MQ：我处理完了，你可以删消息了**。

- 消息**绝对不丢**
- 消费者挂了 → 消息自动重回队列
- 可重试、可死信、可控制分发
- **能实现均匀消费（basicQos=1）**

## . 消费失败的 3 种错误处理方式（对比）

1. **重回队列（requeue=true）**
   - 会无限循环 → 雪崩
   - **禁止使用！**
2. **直接丢弃**
   - 消息丢失
   - 业务违法
3. **死信队列（Dead Letter Queue）**
   - 失败消息进入专门队列

## 什么是死信队列？

消息变成死信的条件：

1. 消费者 **NACK/Reject 且不重回队列**
2. 消息**过期**
3. 队列**满了**

死信会被转发到死信交换机（DLX），最终进入死信队列。

生产者 → 业务交换机 → 业务队列（绑定死信）
↓（死信触发）
死信交换机 → 死信队列 → 死信消费者

- 订单超时未支付 → 自动取消
- 预约成功后 10 分钟提醒
- 未评论订单 7 天后自动好评

## . 死信队列 + TTL（原生实现，无需插件，通用）

- 利用**消息过期** → 变成死信 → 转发到死信队列
- 优点：无需安装插件，兼容所有版本
- 缺点：**同一队列只能有一个 TTL**，多延迟时间会不准

## 2. 延迟插件（官方推荐，灵活精准）

- 安装 `rabbitmq_delayed_message_exchange` 插件
- 交换机类型变为：`x-delayed-message`
- 优点：**每条消息可设置不同延迟时间，精准**
- 缺点：需要安装插件

## 什么是幂等性？

**一次请求 和 多次请求 结果一样**，就是幂等。

- 消费者处理完，**网络闪断**，没来得及 ACK
- MQ 认为消息没处理，**重新投递**给其他消费者
- 结果：**同一条消息被消费多次**

给每条消息一个唯一 ID（messageId），记录已经处理过的消息 ID，处理前判断是否处理过。

- 每条消息带 **唯一 messageId**（如订单号、UUID）
- 消费时，把 messageId 插入业务表 / 去重表
- 利用 **数据库唯一索引** 阻止重复插入
- 插入成功 → 处理业务；插入失败 → 说明重复，直接跳过
- 消息唯一 ID 作为 Redis Key
- **消费前先拿锁**，拿到锁才允许消费
- 消费完成 → 释放锁 / 设置过期
- 没拿到锁 → 说明正在处理 / 已处理，直接跳过

如何保证 RabbitMQ 消息不丢失？

答：生产者确认 + 消息持久化 + 消费者手动 ACK + 死信队列兜底

消息重复消费怎么办？

答：通过消息唯一 ID + 数据库唯一约束 / Redis 记录消费状态实现幂等

# 如何用死信队列实现延迟消息？（核心原理）

## 一句话总结

**给消息 / 队列设置 TTL 过期时间 → 过期后自动转发到死信队列 → 消费死信队列 = 延迟消费**

```yaml
1. 生产者发送带 TTL 的消息
2. 消息进入【延迟队列】（没有消费者）
3. 等待 TTL 时间（10s/15min）
4. 消息过期 → 变成死信
5. 自动转发到【死信交换机】
6. 进入【死信队列】
7. 消费者监听死信队列 → 实现延迟执行
```

args["x-dead-letter-exchange"] = "死信交换机"
args["x-dead-letter-routing-key"] = "死信路由key"
args["x-message-ttl"] = 10000 // 延迟10秒

## 如何用死信实现延迟消息？

答：

1. 给队列 / 消息设置 **TTL 过期时间**
2. 队列绑定 **死信交换机**
3. 消息过期后自动转发到 **死信队列**
4. 消费死信队列，实现延迟执行效果

## prefetch 预取值优化

**1. 参数含义**

`basicQos(prefetchCount, 0, false)`

- `prefetchCount`：单个消费者**未手动 ACK 的最大消息数**

：限制 MQ 一次性推送给消费者的消息总量，避免消费者积压爆内存

- **prefetch=1**
  - 逐条推送，处理完一条才发下一条
  - 优点：消费均匀、流量平稳、故障影响小
  - 适用：**耗时不均任务、需要负载均衡**的工作队列
- **prefetch=5~20**
  - 批量预拉取，提升吞吐，减少网络交互
  - 适用：**消费速度稳定、短耗时**业务
- **prefetch=0**
  - 不限制，MQ 一次性全推，极易堆压，**生产禁用**

必须开启**手动 ACK**，autoAck=true 时 prefetch 失效

ch.Qos(10, 0, false) // 单个消费者最多积压10条未确认消息

## 队列分片（消息拆分优化）

**1. 问题根源**

单队列是**单进程单锁**，并发写入 / 消费存在瓶颈，上万 QPS 极易阻塞。

**2. 分片原理**

将同一业务消息**按规则路由分发到多个同质队列**，多队列并行消费提升整体吞吐。

- 路由规则：订单 ID 哈希、用户 ID 取模、业务类型拆分
- 多队列绑定相同消费者组，并行拉取

**3. 实现方式**

1. **Topic 交换机 + 路由键分片**
   例：路由键 `order.0` `order.1` … 绑定不同分片队列
2. **生产者哈希取模分发**

**集群两种模式区别**

普通集群仅同步元数据，节点宕机队列不可用；镜像集群全量同步数据，主从切换实现高可用，生产核心业务必用镜像队列。

| MQ           | 优点                                               | 缺点                         | 适用场景                                 |
| ------------ | -------------------------------------------------- | ---------------------------- | ---------------------------------------- |
| **RabbitMQ** | 功能全、可靠性强、死信 / 延迟 / 重试完善、路由灵活 | 高吞吐略弱                   | 电商订单、支付、业务异步、可靠性优先     |
| **Kafka**    | 超高吞吐、百万级 QPS、分区并行、日志流式           | 实时弱、延迟略高、事务弱     | 日志采集、大数据流、海量埋点、高吞吐削峰 |
| **RocketMQ** | 吞吐高、事务消息好、阿里生态、重试队列完善         | 社区生态偏弱                 | 互联网电商、金融业务、事务消息场景       |
| **Redis**    | 轻量简单、延迟极低、部署零成本                     | **无完整 MQ 机制、可靠性差** | 简易临时队列、低并发短流程               |

**原生 Redis 没有完善的消息确认机制**

- RabbitMQ：**手动 ACK / NACK / 重回队列 / 死信**全套机制

  - `LPUSH + BRPOP` 消费后直接弹出
  - **消费失败无法回滚重投**，一旦消费异常消息直接丢失
  - 没有消费状态标记，无法实现可靠重试

1. **没有交换机、路由分发**
   - 无法实现广播、主题订阅、精准路由
2. **没有死信队列、延迟队列、重试队列**
   - 订单超时、消费失败归档、定时任务全都做不了

4. **没有预取限流 prefetch、流量削峰精细化管控**

**4. 并发消费存在竞态与重复消费难控制**

- 多客户端同时`BRPOP`极易出现争抢混乱
- 没有消费锁、没有消息投递隔离，重复消费只能业务层硬写
- 高并发下队列阻塞、消费倾斜问题无解
- Redis 内存有限，海量消息堆积直接 OOM 宕机
- RabbitMQ/Kafka 支持磁盘海量堆积，削峰能力碾压 Red

**高并发下为什么不用 Redis 实现消息队列？**

1. Redis 缺少**消费者 ACK 确认机制**，消费失败无法重新投递，极易丢消息；
2. 持久化机制薄弱，宕机、主从切换场景消息丢失概率远大于专业 MQ；
3. 不具备交换机路由、死信队列、延迟队列、重试队列等业务必备高级特性；
4. 无法做消费限流、负载均衡、消息堆积治理，高并发易过载宕机；
5. 缺少分布式消费可靠机制，重复消费、顺序消费难以管控；
6. Redis 定位是**内存缓存**，并非消息中间件，架构设计不满足异步解耦与流量削峰的生产级需求。

OOM 内存溢出 / 内存耗尽 **申请的内存太多，系统剩余内存不够用了**，操作系统直接把进程**强行杀死**。

## RTT一次网络请求的往返

| 特性       | 自动 ACK         | 手动 ACK（推荐）                 |
| ---------- | ---------------- | -------------------------------- |
| 确认时机   | 接收瞬间         | 处理完成后手动确认               |
| 消息安全性 | 低，易丢失       | 高，不丢失                       |
| 适用场景   | 测试、不重要日志 | 生产环境、订单 / 支付 / 核心业务 |

- **自动 ACK + 消费者宕机**
  消息刚发过去，还没处理完，服务挂了 → MQ 已经删了消息 → **消息永久丢失**
- **MQ 宕机但队列 / 消息没持久化**
  重启后消息全部消失
- **生产者没开启确认机制**
  消息发到一半网络断了 → 生产者不知道发送失败
- **手动 ACK 代码写错**
  抛异常时没 NACK，也没 ACK → 消息堆积但不会丢

## QoS 预取数（prefetchCount）作用 + 使用前提

**1. 作用：限流 + 负载均衡**

```
prefetchCount = 1
```

表示：

**每个消费者同一时间最多只拿 1 条消息**

处理完确认后，才能拿下一条。

**2. 解决什么问题？**

- 防止一个消费者把队列消息**全部抢走**，导致其他消费者空闲
- 保护消费者不被瞬间大量消息压垮
- 让消息**均匀分配**给多个消费者

**3. 使用前提（必须满足）**

1. **必须使用 手动 ACK**
   自动 ACK 下 QoS 无效！
2. 必须设置 `channel.basicQos(prefetchCount)`

**4. 实战建议**

- 核心业务：`prefetchCount=1`（最安全、均匀）

## RPC 模式：CorrelationId + ReplyTo 设计原理

**1. 什么是 MQ RPC？**

普通 MQ 是异步单向的
RPC =

**请求 + 响应**

，像调用接口一样等待返回结果

**2. 核心两个参数**

1. **ReplyTo**
   存放：**回调队列名**
   作用：消费者处理完后，把结果发回这个队列
2. **CorrelationId**
   存放：**唯一请求 ID**
   作用：区分 “哪次请求对应哪次响应”

**3. 执行流程**

1. 生产者创建**临时回调队列**
2. 发送消息：`replyTo=回调队列` + `correlationId=UUID`
3. 消费者处理业务
4. 消费者发结果：带上相同 `correlationId`
5. 生产者根据 ID 匹配结果 → 得到返回值

**4. 适用场景**

- 需要**同步等待结果**的场景
- 跨服务同步调用
- 订单校验、支付查询等

**异步非阻塞，Broker 收到消息后主动回调通知生产者**

分两种：

1. **普通 Confirm**：单条消息发完等确认
2. **批量 Confirm**：批量发送，批量确认（性能更高）
3. **异步 Confirm**：**真正生产主流**，不阻塞业务，回调通知结果

**核心逻辑**：

- 消息发送 → 交换机收到 → 返回 `ack`（成功）
- 消息失败 → 返回 `nack`（失败），可重试

手动 ACK：**业务处理成功 → 手动确认；失败 → 拒绝 / 重回队列**

**核心：RabbitMQ 原生没有延迟队列**

**底层实现 = TTL 过期消息 + 死信队列**

**2. 实现原理**

1. 给消息 / 队列设置 **TTL（过期时间）**
2. 消息过期 → 变成死信
3. 死信路由到死信队列
4. **消费者监听死信队列 → 实现延迟消费**

**3. 经典业务场景**

- 订单超时未支付 → 自动取消
- 发货后未确认收货 → 自动确认
- 定时通知、定时任务

**4. 配置示例（订单延迟 30 分钟关闭）**

**. 标准重试流程**

1. 消费异常 → **自动重试**（配置次数）
2. 超过最大重试次数 → **不再重试**
3. 消息转入 **死信队列 / 失败归档队列**

AMQP = 高级消息队列协议

**定义了客户端和消息队列服务器如何通信、数据如何传输、消息如何路由**。
连接模型：Connection / Channel（通信基础）

**Connection（TCP 连接）**

- 本质：**一条 TCP 长连接**
- 作用：客户端和 RabbitMQ 服务器之间的**物理连接**

**Channel（信道，轻量级连接）**

- 本质：**Connection 里的虚拟连接**
- 作用：真正用来发送 / 接收消息的通道
- 特点：
  - 极轻量，创建 / 销毁极快
  - 一个 Connection 可以创建**成百上千个 Channel**

AMQP 协议传输数据不是整段发，而是拆成**帧（Frame）**

**Method Frame（方法帧）**

- 作用：**传输指令 / 命令**
- 例子：
  - 声明队列 `queue.declare`
  - 发布消息 `basic.publish`
  - 消费消息 `basic.consume`
- 理解：相当于 “告诉 RabbitMQ 要做什么操作”

**2. Header Frame（头帧）**

- 作用：**传输消息元数据**
- 内容：消息属性（过期时间、优先级、持久化、自定义参数等）
- 理解：相当于快递单，写清包裹信息，不装货物

**3. Body Frame（体帧）**

- 作用：**传输真正的消息内容**
- 内容：你业务里的 JSON、字符串、字节数据
- 理解：真正的快递货物

发送一条消息 =

```
Method Frame（发消息指令）
```

-

```
Header Frame（消息属性）
```

-

```
N个Body Frame（消息内容分片）
```

**虚拟主机 vhost（Virtual Host）**

- 作用：**RabbitMQ 里的「隔离容器」**
- 类比：一台 MySQL 里可以创建多个数据库，互相隔离
- 特点：
  - 一个 RabbitMQ 服务器可以创建多个 vhost
  - 每个 vhost 有独立的：交换机、队列、绑定、用户权限

**交换机 Exchange（路由器）**

- 作用：**消息的入口 + 路由分发器**
- 关键点：
  - **生产者永远只把消息发给交换机，不直接发队列！**
  - 交换机不存消息，只负责根据规则转发到队列
- 4 种类型（必须记住）：
  1. **direct**：精准匹配路由键（一对一）
  2. **topic**：通配符匹配（一对多，最常用）
  3. **fanout**：广播（发给所有绑定队列，无视路由键）
  4. **headers**：用消息头属性匹配（极少用）

**3. 队列 Queue（仓库）**

- 作用：**存储消息的容器**
- 消费者只从队列取消息
- 关键属性：
  - 持久化：重启不丢失
  - 排他：只允许一个连接使用
  - 自动删除：无消费者自动删除

**4. 绑定 Binding（路由规则）**

- 作用：**交换机 和 队列 之间的 “连线”**
- 绑定需要带：**路由键 Routing Key**
- 交换机根据绑定规则 + 路由键，决定把消息发给哪个队列

**生产者（Producer）**

**定义**：**发送消息的一方**

- 负责创建消息，然后发送给 RabbitMQ 服务器
- 不关心消息给谁，也不关心谁接收
- 只做一件事：**发消息**

**Broker（RabbitMQ 服务器）**

**定义**：**消息队列的服务端 / 中转站**

- 接收、存储、转发消息
- 是生产者和消费者之间的**中间桥梁**
- 包含：交换机（Exchange）、队列（Queue）、绑定（Binding）

**简单理解**：快递中转站，负责暂存包裹，按规则分拣，再派送给收件人。

**3. 消费者（Consumer）**

**定义**：**接收并处理消息的一方**

- 监听 Broker 里的队列
- 消息到达后自动接收、处理
- 只做一件事：**收消息 + 处理消息**

**简单理解**：你就是消费者，在家等快递，收到后拆包使用。

## Mnesia 数据库（RabbitMQ 元数据存储）

RabbitMQ

**2. 存储什么内容？（RabbitMQ 核心元数据）**

- 队列、交换机、绑定关系
- 用户、权限、vhost

- 镜像队列策略

**3. Mnesia 关键特性（适配 RabbitMQ）**

1. **分布式**：多节点自动同步数据，集群中所有节点元数据一致
2. **混合存储**：热数据放内存，冷数据刷磁盘
3. **事务支持**：元数据修改原子性，不会错乱
4. **与 Erlang 无缝融合**：直接存 Erlang 数据结构，无序列化开销

**4. 与 RabbitMQ 集群的关系**

- Mnesia 是 **RabbitMQ 集群的大脑**
- 集群元数据同步 = Mnesia 分布式同步
- 新增节点 = Mnesia 数据自动复制到新节点

**Actor = 独立的计算实体**

Erlang 里一切都是 Actor，对应概念就是

**Erlang 进程**

（不是操作系统进程，是极轻量的虚拟机进程）。

**2. Actor 模型三大铁律（RabbitMQ 运行的基础）**

1. **每个 Actor 都是独立的**：有自己的状态、自己的邮箱、不共享数据
2. **只通过消息通信**：不直接调用函数、不共享内存
3. **完全异步**：发消息不等待回复，并发拉满

| Erlang Actor | RabbitMQ 实体                  |
| ------------ | ------------------------------ |
| 轻量进程     | 队列、交换机、连接、信道       |
| 进程邮箱     | 消息缓冲队列                   |
| 消息发送     | 生产者投递消息、消费者获取消息 |
|              |                                |

1. **异步**：发送完立刻继续执行，不等待对方处理
2. **可靠**：消息不会丢失（本地 / 分布式都一样）
3. **有序**：同一个发送者发的消息，接收方按顺序收到
4. **位置透明**：本地进程 / 分布式远程进程，写法完全一样

**3. 对应 RabbitMQ 的实际流程**

1. 生产者发送消息 → 发给 **信道进程**
2. 信道进程转发 → 发给 **交换机进程**
3. 交换机路由 → 发给 **队列进程**
4. 队列进程缓存 → 发给 **消费者进程**

**Erlang/OTP 最伟大的设计**，也是 RabbitMQ 高可用、容错的核心。

**1. 核心理念：任其崩溃（Let It Crash）**

- 不写大量防御性代码
- 进程出错直接崩溃
- **监督者自动重启崩溃的进程**

顶级监督者（RabbitMQ 主进程）
├─ 网络监督者 → 管理连接、信道进程
├─ 队列监督者 → 管理所有队列进程
├─ 存储监督者 → 管理消息持久化进程
└─ 集群监督者 → 管理节点通信进程

**监督策略（RabbitMQ 都在用）**

1. **one_for_one**（最常用）：哪个进程崩了，只重启哪个
   - 队列崩了 → 只重启该队列，不影响其他队列
2. **one_for_all**：一个崩，全部重启
3. **rest_for_one**：一个崩，重启它和后面的进程

**4. 为什么这对 RabbitMQ 至关重要？**

- 消息堆积、异常消息导致队列崩溃 → **自动重启**
- 客户端异常断开连接 → **连接进程自动清理**
- 节点网络闪断 → **自动重连、自动恢复**
- 这就是 RabbitMQ 号称 99.99% 可用性的底层支撑

RabbitMQ 客户端与服务端**全部基于 TCP 长连接**通信

`Connection` = **一条完整 TCP 套接字连接**

`Channel` = 同一条 TCP 连接内**多路虚拟逻辑通道**，复用 TCP 流

- **面向连接、可靠传输**
  消息不会丢包乱序，RabbitMQ 依赖 TCP 可靠性实现消息投递保障
- **粘包 / 拆包问题**
  AMQP 协议自定义**帧格式**做边界拆分，解决 TCP 流无边界问题
  帧头固定长度标识帧类型 + 数据长度，服务端按长度解析 Method/Header/Body 帧
- 连接模型
  - 服务端：`listen`监听 5672 端口，接受客户端 TCP 连接
  - 高并发下**不能单进程单连接**，靠 IO 多路复用承接万级连接

NIO 多路复用：少线程管万连接，RabbitMQ、Nginx、Redis 通用架构

- `fsync()` / `fdatasync()`：**强制刷盘**，把页缓存数据真正写入物理磁盘
  RabbitMQ 持久化消息必须调用刷盘，否则重启丢失

**3. 刷盘级别**

- 异步刷盘：写完缓存就返回，后台定时刷盘，性能高、有丢数风险
- 同步刷盘：调用 fsync 阻塞直到落盘，安全、性能低

## 内存页 Page（操作系统内存核心）

**1. 基础概念**

- 操作系统把物理内存划分为固定大小块：**内存页（通常 4KB）**
- 程序读写内存，本质都是操作内存页

**2. 页缓存 PageCache**

OS 内核维护的**磁盘文件内存缓存区**

1. 读文件：先查页缓存，有则直接读内存，无则从磁盘加载进页缓存
2. 写文件：先写入页缓存，延迟刷入磁盘

**3. 和 RabbitMQ 强关联**

1. **消息优先存内存**
   空闲队列消息全部放在内存页缓存，收发速度极快
2. **内存阈值限流**
   RabbitMQ 配置最大使用内存，超出后：
   - 停止接收生产者消息
   - 内存消息批量转存磁盘
3. 内存页换入换出
   内存不足时，OS 会把冷队列消息页交换到 swap 分区，严重降性能

**4. 核心结论**

**RabbitMQ 快 = 大量消息命中内存页缓存**

**消息不丢 = 关键数据从页缓存 fsync 强制落盘**

## 五、RabbitMQ 完整持久化机制（融合上面所有知识点）

**1. 两大持久化维度**

**（1）消息持久化**

生产者发送消息标记`delivery_mode=2`，消息写入后落地磁盘

**（2）队列持久化**

声明队列时设置 durable=true，队列元数据（绑定、路由规则）重启不丢失

**2. 底层持久化存储结构**

1. **队列索引文件 (.idx)**
   记录消息位置、偏移量、状态，存在页缓存加速查询
2. **消息数据存储文件 (.log)**
   顺序追加写入（顺序 IO 远快于随机 IO），利用磁盘顺序写高性能

**3. 持久化完整流程（串全知识点）**

1. 生产者通过**TCP 连接 + Channel**发送 AMQP 帧消息
2. IO 多路复用监听 TCP fd，读取消息送入内核**内存页缓存**
3. MQ 先写入内存队列，高速响应生产者
4. 满足条件（定时 / 数量阈值）：
   调用**文件 IO write**写入磁盘日志文件（先写 PageCache）
5. 执行**fsync 强制刷盘**，页缓存数据写入物理磁盘
6. 消费者消费时，优先读内存页缓存消息，内存不足从磁盘文件加载回页缓存
7. 消息删除后，后台合并压缩日志文件，清理无效数据

**4. 持久化三种策略**

1. **不持久化**：全内存，断电全丢，极致性能
2. **半持久化**：队列持久、消息不持久，重启队列还在，消息清空
3. **全持久化**：队列 + 消息都持久，重启数据完好，兼顾安全与性能
