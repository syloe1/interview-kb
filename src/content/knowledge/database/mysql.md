## MySQL 事务（InnoDB 为主，面试高频）

**1. 事务四大特性 ACID**

- **原子性 (A)**：事务要么全部执行成功，要么全部回滚，不可拆分。
- **一致性 (C)**：事务执行前后，数据整体合法（约束、业务规则不变）。
- **隔离性 (I)**：多个事务并发时，互不干扰。
- **持久性 (D)**：事务提交后，数据永久落地，宕机也不丢失。

**2. 事务隔离级别（MySQL 默认：可重复读 RR）**

由低到高 4 级，解决不同并发问题：

1. **读未提交**：能读到其他事务未提交数据 → 脏读、不可重复读、幻读都存在
2. **读已提交 RC**：只能读已提交数据 → **解决脏读**，仍有不可重复读、幻读
3. **可重复读 RR（InnoDB 默认）**：同一事务内多次查询结果一致 → **解决脏读、不可重复读**，**存在幻读**
4. **串行化**：最高级别，完全串行执行 → 所有问题都解决，性能最差

**三个并发问题解释**

- 脏读：读到别的事务**未提交**的脏数据
- 不可重复读：同一事务内，**两次相同查询结果不同**（其他事务更新并提交）
- 幻读：同一事务内，范围查询**前后行数不一致**（其他事务新增 / 删除并提交）

**3. InnoDB 如何实现隔离 & 特性**

- **原子性、持久性**：依赖 **redo log、undo log**
  - redo log：崩溃恢复，保证已提交数据不丢失
  - undo log：事务回滚、实现 MVCC
- **隔离性**：依赖 **MVCC（多版本并发控制）** + 锁机制
- **MVCC（RR/RC 核心）**：
  每行数据存**隐藏列**：事务 ID、回滚指针，读数据时读**历史快照**，不加锁，提升并发。

**4. 事务锁（简单面试考点）**

- 行锁：锁单行，并发高（InnoDB 索引生效才会触发行锁）
- 表锁：锁全表，并发低（无索引、索引失效会升级为表锁）
- 意向锁：InnoDB 自动加，协调行锁与表锁，不用手动控制

## 二、MySQL 索引优化（面试重中之重）

**1. 索引基础**

- 索引本质：**B+ 树**（InnoDB），有序、多路平衡树，磁盘 IO 少，范围查询友好
- 分类：
  1. 主键索引（聚簇索引）：叶子存**整行数据**，一张表只有一个
  2. 普通索引 / 二级索引（非聚簇）：叶子存**主键值**，回表查询
  3. 唯一索引：值唯一，允许一个 null
  4. 联合索引：多个字段组成，遵循**最左匹配原则**

**2. 索引失效场景（必背）**

1. 不满足**最左前缀**（联合索引跳过最左列）
2. 索引列做**运算、函数、类型转换**
3. `like %xxx` 左模糊（`like xxx%` 可走索引）
4. `or` 连接无索引字段，两边字段必须都有索引
5. 字段**隐式类型转换**（字符串和数字对比）
6. `not in、not exists、!=、<>` 大多不走索引
7. 数据量**超过表 20%~30%**，优化器认为全表更快，放弃索引

**3. 联合索引设计原则**

- **最左优先**：高频查询字段放左侧
- 区分度高的字段靠前
- 经常 `where、order by、group by` 字段优先建索引
- 避免冗余索引

**慢查询 & 索引优化实战方案**

1. **先用 explain 分析执行计划**
   重点看：`type`（最优 range > ref > eq_ref）、`key`（是否用到索引）、`rows`（扫描行数）、`Extra`（Using filesort/Using temporary 需优化）
2. 优化方向
   - 避免 select *，只查必要字段（减少回表）
   - 建立**覆盖索引**：查询字段全部包含在索引中，无需回表
   - 大分页优化：`limit 100000,10` → 用主键定位 `where id>100000 limit 10`
   - 排序分组优化：`order by/group by` 字段加入联合索引，避免文件排序

- 回表：二级索引查到主键，再去聚簇索引查整行数据
- 覆盖索引：索引包含所有查询字段，**无需回表**，性能极高

**为什么 InnoDB 用 B+ 树不用 B 树 / 哈希？**

B + 树非叶子节点只存键，数据都在叶子，树矮、IO 少；叶子链表有序，范围查询强。哈希不支持范围、排序。

- **聚簇索引和非聚簇索引区别？**
  聚簇叶子存整行数据，非聚簇存主键；查询非聚簇大概率会回表。
- **RR 隔离级别怎么解决幻读？**
  靠 **MVCC 快照读** + **间隙锁 + 临键锁**（当前读）共同解决。
- **一条 SQL 慢，排查步骤？**
  开启慢查询日志 → explain 看执行计划 → 检查索引是否失效 / 缺失 → 优化 SQL / 索引。

## 缓存使用流程（标准回答）

1. **先查缓存**，命中直接返回
2. **缓存未命中**，查数据库
3. **把数据库结果写入缓存**，方便下次查询
4. **数据更新时**，更新数据库 + 淘汰 / 更新缓存

## 2. 缓存三大问题（必背）

**① 缓存穿透**

- **现象**：查**不存在的数据**，缓存不命中，每次都查库
- **危害**：压垮数据库
- **解决**：
  1. 缓存空值（null），设置短过期时间
  2. 布隆过滤器过滤不存在的 key

**② 缓存击穿**

- **现象**：**热点 key 过期**，大量请求同时打数据库
- **解决**：
  1. 热点 key 永不过期
  2. 加互斥锁（分布式锁），只让一个线程查库更新

**缓存雪崩**

- **现象**：**大量 key 同时过期 / Redis 宕机**，请求全部打库
- **解决**：
  1. 过期时间加随机值，避免同时失效
  2. 搭建 Redis 集群（主从 + 哨兵）
  3. 服务降级、限流
  4. 多级缓存（本地缓存 + Redis）

## 3. 缓存与数据库一致性（最常问）

**标准方案：先更新数据库，再删除缓存**

- 为什么不更新缓存？避免频繁更新造成浪费，懒加载更优
- 极端并发问题：用**延迟双删**（删缓存→更新库→延迟几百 ms 再删）
- 强一致性：用**Canal 订阅 binlog**异步更新缓存

## Redis 淘汰策略

1. **volatile-lru（最常用）**：只删设置了过期时间的 key，删除最少使用的
2. allkeys-lru：所有 key 都删，删最少使用
3. volatile-ttl：删即将过期的
4. noeviction：不删除，直接报错（默认）

## 5. 缓存预热

- 项目启动时，把**热点数据提前加载到 Redis**，避免第一次请求卡顿

## 6. 缓存更新策略

- 写穿透：直接写库，不写缓存
- 写回：写缓存，异步刷库（不常用）
- **写删除（推荐）**：更新库，删缓存

# 二、Redis 分布式锁（面试必考）

## 1. 核心命令

plaintext

`SET lock_key unique_value NX PX 30000`

- **NX**：只有不存在才设置（互斥）
- **PX 30000**：30 秒过期（避免死锁）
- **unique_value**：唯一值（防止误删别人的锁）

## 2. 分布式锁执行流程

1. 线程 A 加锁，设置**唯一 ID + 超时时间**
2. 执行业务逻辑
3. **判断唯一 ID，再释放锁**（Lua 脚本保证原子性）
4. 若线程 A 挂了，锁自动过期，不会死锁

## 分布式锁三大问题 & 解决方案

**① 锁过期，业务没执行完（锁失效）**

- 解决：**看门狗（WatchDog）**
  定时任务，**自动续期锁**（Redisson 自带）

**② 误删别人的锁**

- 解决：加锁时存**唯一值**，删除前先判断是不是自己的锁
- 必须用 **Lua 脚本** 保证判断 + 删除原子性

**③ Redis 主从切换导致锁丢失（集群问题）**

- 主节点加锁，同步到从节点前主节点宕机 → 从节点变主，无锁
- 解决：**RedLock 红锁**（不推荐）/ 使用 **Redisson + 集群优化**

## 为什么用 Lua 脚本？

因为 **判断锁 + 删除锁** 必须是**原子操作**，否则并发会删错锁。

看门狗 = 给分布式锁自动 “续期” 的后台线程。业务执行太慢，30 秒到了，锁自动释放了，但业务还没跑完！

## 看门狗怎么工作？（流程）

1. 你加锁：`lock.lock()`
2. 看门狗**后台启动**
3. 每隔 **10 秒**（锁时间的 1/3）检查一次：
   - 线程还在执行业务吗？
   - 在 → **自动把锁重置为 30 秒**
4. 直到：
   - 业务执行完，释放锁
   - 或服务挂了，锁自然过期

只要业务没跑完，看门狗就一直给锁续命，保证锁不会提前释放。

# RabbitMQ 如何保证消息可靠性？（面试超级高频）

从 **生产 → 存储 → 消费** 三个环节全方位保证。

## 1. 生产者可靠性（消息不丢）

- **Confirm 确认机制**：消息到达交换机，MQ 返回 ACK
- **Return 退回机制**：消息没到队列，返回失败
- 开启**事务机制**（不推荐，性能差）

## 2. 队列存储可靠性（MQ 不丢）

- **队列持久化**：`durable=true`
- **消息持久化**：`deliveryMode=2`
- 交换机持久化
- （集群）镜像队列，主挂了从顶上

## 3. 消费者可靠性（不重复消费、不丢消息）

- **手动 ACK**：处理完业务再确认，否则消息重回队列
- **幂等性**：保证消息**不重复消费**（用唯一 ID 去重）
- 限流：防止消费者被压垮

：**客户端→网关用 QUIC（UDP+HTTP/3），网关→后端仍用 TCP（HTTP/1.1/2）**，在接入层把 TCP+TLS+HTTP/2 的痛点一次性解决，**弱网更快、切换不断、握手更短、安全更强**

**QUIC = 基于 UDP 的传输层协议，内置 TLS 1.3、多路复用、连接迁移、0-RTT**，是 TCP+TLS+HTTP/2 的替代，对应应用层 HTTP/3

## 网关层为什么用 QUIC（核心优势）

**1. 握手延迟大降（关键）**

- TCP：3 次握手 + TLS 1.2 握手 → **2-RTT**
- QUIC：**0-RTT（会话复用）/1-RTT（首次）**

**无队头阻塞（HTTP/2 痛点）**

- TCP：单流丢包 → 所有请求阻塞
- QUIC：**多流独立**，一个流丢包不影响其他
- TCP：IP / 端口变 → 连接断，重连耗时
- QUIC：**Connection ID 不变**，4G/Wi-Fi 切换**不断链**

：4 层 LB 直接转发 QUIC 包到后端 → 低延迟、但后端需支持 HTTP/3

- 0-RTT：会话复用，**无握手延迟**，适合重复请求（如登录、API 调用）
- 1-RTT：首次连接，1 次往返完成握手

**客户端→协调节点→路由到主分片→写 Buffer+Translog→Refresh（1s）生成 Segment→Flush 刷盘→同步副本→返回**。

# 先搞懂：WebSocket 是什么？

## 一句话

**基于 TCP 的全双工长连接协议，一次握手，永久连接，服务器能主动推消息给前端。**

## 解决什么问题？

- HTTP：只能**前端请求 → 服务器响应**（被动）
- WebSocket：**服务器主动推消息**（主动）
- 场景：**聊天、通知、直播弹幕、实时数据大屏**

## 核心特点

- 长连接，不断开
- 全双工（两边都能发）
- 轻量，开销小
- ws:// 、 wss://（加密）

# WebSocket 消息**持久化**怎么做？（面试重点）

WebSocket **本身不存消息**，要持久化必须**自己存数据库**。

## 标准方案：

**1. 消息流向**

前端 ←→ WebSocket 服务 ←→ **数据库（MySQL/Redis/Mongo）**

**2. 持久化流程**

1. 前端发消息 → WebSocket 收到
2. **先存库**（必须）
3. 再转发给目标用户

**离线消息怎么存？**

用户不在线 → 消息

**存入 DB/Redis**

用户上线 → WebSocket 连接成功 →

**主动拉取历史消息**

**WebSocket 断开了消息会丢吗？**

不会。

**只要先存库再转发，断开就存为离线消息，重连后拉取即可。**

**大量连接怎么支撑？**

- 分布式 WebSocket 集群
- 网关层（如 Spring Cloud Gateway）

- 多节点广播

**Kafka 事件 = 系统里发生的一件 “事”，用消息记录下来，发给 Kafka。**

## 通俗解释

- 用户下单 → 产生一个**下单事件**
- 支付成功 → 产生一个**支付事件**
- 商品出库 → 产生一个**出库事件**

这些 “事” 就是**事件**。

## Kafka 事件用来干嘛？（背这 4 点）

1. **系统解耦**
   订单系统不直接调用支付、物流，只发事件。
2. **异步处理**
   不阻塞主线程，提高响应速度。
3. **流量削峰**
   高并发事件先存在 Kafka，下游慢慢消费。
4. **数据管道 / 数据同步**
   把数据从 MySQL → Kafka → 数仓 / ES / 缓存。

Kafka 数据同步怎么做？

**通过 CDC 工具（如 Canal / Debezium / Flink CDC）监听数据库 binlog，转换成消息发送到 Kafka，实现准实时数据同步。**

## 完整流程（超级清晰）

1. **业务数据写入 MySQL**
2. **Canal/Debezium 监听 binlog**
3. **把增删改数据封装成 Kafka 消息**
4. **发送到 Kafka Topic**
5. **下游消费**：同步到 ES、Redis、数仓、其他业务库

MySQL → Kafka → **ES**（实现实时搜索）

## 什么是幂等？

**无论执行多少次，结果都一样，不会重复消费、不会重复插入。**

## Kafka 为什么需要幂等？

- 重试机制会导致**消息重复**
- 网络波动会导致**重复投递**
- 消费者重启 → **重复消费**

## 实现幂等 3 种方案（面试必背）

**方案 1：生产者幂等（Kafka 自带）**

生产者设置：

plaintext

`enable.idempotence = true`

- Kafka 自动去重
- 保证**生产者不重复发送**
- 只能保证单分区、单会话内有效

**方案 2：数据库唯一键（最常用、最简单）**

消费消息时：

# ACK 是什么？

**ACK = 消息确认（Acknowledgment）**

作用：

**告诉 RabbitMQ：这条消息我消费成功了，你可以删掉了！**

# 二、为什么必须用 ACK？

**防止消息丢失！**

如果没有 ACK：

- 消费者一拿到消息，MQ 就删除
- 结果消费者**刚拿到就挂了**，业务没处理
- **消息永久丢失**

有了 ACK：

- 消费者处理完业务 → 手动发 ACK
- MQ 收到 ACK → 才删消息
- 消费者挂了 → **消息自动重回队列**，给别人消费

```go
// GenerateToken 生成JWT
func GenerateToken(userID int, username string) (string, error) {
	// 过期时间：2小时
	expireTime := time.Now().Add(2 * time.Hour)

	// 构造claims
	claims := CustomClaims{
		UserID:   userID,
		Username: username,
		RegisteredClaims: jwt.RegisteredClaims{
			ExpiresAt: jwt.NewNumericDate(expireTime),
			IssuedAt:  jwt.NewNumericDate(time.Now()),
			NotBefore: jwt.NewNumericDate(time.Now()),
		},
	}

	// 生成token（HS256加密）
	token := jwt.NewWithClaims(jwt.SigningMethodHS256, claims)

	// 签名
	return token.SignedString(jwtSecret)
}
```

## 验证

```go
// ParseToken 解析Token
func ParseToken(tokenStr string) (*CustomClaims, error) {
	// 解析token
	token, err := jwt.ParseWithClaims(tokenStr, &CustomClaims{}, func(token *jwt.Token) (interface{}, error) {
		return jwtSecret, nil
	})

	if err != nil {
		return nil, err
	}

	// 校验并返回claims
	if claims, ok := token.Claims.(*CustomClaims); ok && token.Valid {
		return claims, nil
	}

	return nil, jwt.ErrSignatureInvalid
}
```

# 为什么是**删缓存**，不是**更新缓存**？

因为：

1. **高并发下更新缓存会产生脏数据**
2. 线程 A 更新 DB → 线程 B 更新 DB → 线程 B 更新缓存 → 线程 A 更新缓存
   → **缓存旧数据覆盖新数据！**

**结论：缓存只做删除，不做更新！**

Redis Pub/Sub 适合做「轻量、实时、允许丢消息」的广播 / 通知限流；专业 MQ（Kafka/RabbitMQ）适合做「可靠、可堆积、可重试」的分布式队列限流。

## Redis Pub/Sub 做分布式队列限流（本质：广播 + 内存推模式）

**原理**

- 生产者 → PUBLISH channel → Redis → 推给所有在线订阅者（SUB）
- **无存储、无队列、无 ACK、无持久化**，发后即忘
- 限流靠：**client-output-buffer-limit pubsub**（默认 32MB/8MB60s），超了直接踢客户端、丢消息
- 分布式限流：多个服务订阅同一 channel，抢消息？**不能抢，是广播**，每条消息所有订阅者都收到

| 维度            | Redis Pub/Sub           | 专业 MQ（RabbitMQ/Kafka）      |
| --------------- | ----------------------- | ------------------------------ |
| **模型**        | 广播推送，无队列        | 队列拉取，持久化               |
| **限流方式**    | 生产端 QPS + 信号量     | 生产 + Broker + 消费端三级限流 |
| **堆积 / 削峰** | ❌ 无缓冲，直接丢       | ✅ 队列缓冲，削峰填谷          |
| **可靠性**      | ❌ 无 ACK、不持久、易丢 | ✅ 持久化 + ACK + 死信，不丢   |
| **背压**        | ❌ 无，消费者慢不反压   | ✅ 有，消费者慢→生产者降速     |
| **吞吐量**      | 低（<1000 QPS）         | 高（万～百万 QPS）             |
| **复杂度**      | 低（Redis 原生）        | 中（需部署集群、运维）         |

**. 为什么电商订单限流不用 Redis Pub/Sub 而用 MQ？**

答：

- Pub/Sub**无队列缓冲**，秒杀高峰会直接丢消息，导致订单丢失。
- 订单需要**可靠不丢 + 重试 + 死信**，Pub/Sub 无 ACK、不持久，无法保证。
- MQ 支持**削峰填谷 + 背压**，消费者慢可缓冲，保护下游数据库。

# Goroutine 能支撑高并发的 4 大核心特点（除了内存小）

## 1. **完全用户态调度，不进内核，无系统调用开销（最重要！）**

- 线程切换：必须进 OS 内核 → 保存上下文、切换页表、刷新 TLB → **极慢**
- Goroutine 切换：**完全在用户态**，由 Go 自己的 GMP 调度器完成
  → **不触发系统调用、不切换页表、不刷新 TLB**

## 2. **GMP 模型：M 个内核线程 调度 上百万 Goroutine（复用线程）**

Go 调度模型：

- **G：Goroutine（任务）**
- **M：内核线程**
- **P：逻辑处理器（核心）**

机制：

- **一个 M 可以绑定 N 个 G**
- **G 不绑定内核线程**
- **G 阻塞时，M 立刻切换 run 另一个 G**
- **线程永远不空闲**

## **同步代码变异步，无阻塞、无等待（IO 密集型神器）**

网络 / IO 操作时：

- 线程：**阻塞 → 挂起 → 内核切换**
- Goroutine：**Go 调度器挂起 G，切换到另一个 G 运行**
  → **内核线程 M 根本不阻塞！**

栈动态伸缩，极低资源占用

**线程的栈是：固定大小！**

- 线程启动，系统直接给你分配 **1MB ~ 8MB 内存**
- 不管你用不用，**先占坑！**
- 用完也不会缩小
- 1000 个线程 = **1GB 内存直接没了**

问题：

**绝大多数线程根本用不完 1MB，99% 内存浪费！**

这就是线程不能大量创建的原因。

## 二、Goroutine 栈：动态伸缩（核心！）

**Goroutine 刚启动时：**

**栈大小 = 2KB！**

（只有线程的

**不够用了怎么办？**

**自动扩容（翻倍增长）**

2KB → 4KB → 8KB → 16KB → 32KB...

**用完了、空闲了怎么办？**

**不会一直占内存，会自动缩容！**

释放不用的空间，还给 Go 运行时。

**Go GMP 调度（Go 自己负责）**

- Go 管理：**Goroutine（G）**
- 调度：**Go 运行时（runtime）自己写的代码实现**
- **不依赖任何 OS 特性**
- **不需要 OS 参与、不需要系统调用、不需要内核帮忙**

GMP 就是 Go 在用户态自己写的一个 “迷你操作系统调度器”

- **新建 goroutine 优先放入 当前 P 的本地队列**
- **P 本地队列有容量上限：** **256 个**
- **一旦满了，就会触发：全局队列 + 其他 P 偷任务（work stealing）**
- **1 万个 goroutine 会被均匀分散到所有 P 的本地队列 + 全局队列**

## P 的本地队列到底多大？

固定大小：

**256 个 G slots**

## 满了怎么办？（核心逻辑）

**规则：**

**本地队列满 → 把本地队列一半的 G 移到 全局队列**

## 其他 P 会来 “偷” 任务（Work Stealing）

如果别的 P 空闲了，它会：

1. 先看自己本地队列
2. 空了 → 去**全局队列**拿
3. 还空 → **去别的 P 那里偷一半的 G 过来**

**优先级：本地队列 > 全局队列 > 偷其他 P 队列**

**本地队列永远优先执行；全局队列是兜底、低优先级；每 61 次调度才轮一次全局，防止饿死**

---

## 二、完整执行顺序（M 找 G 的流程）

M（线程）绑定 P 后，循环找 G 执行，顺序严格如下：

**1）先看：P 本地队列（最高优先级）**

- 本地队列容量 **256**，无锁、最快
- 每次取一个 G 执行（FIFO）
- 本地不空 → **永远只执行本地，不看全局**

**2）本地空了 → 去全局队列拿（低优先级）**

- 全局队列是**加锁**的，竞争大、慢
- 拿多少？**全局 G 数 / P 数 +1**（一批拿，减少锁竞争）
- 关键规则：**每 61 次调度，才强制去全局拿一次**
  → 防止全局 G 永远不被执行（饥饿）

**3）全局也空 → 偷其他 P 本地队列（work stealing）**

- 随机找一个 P，**偷一半 G**放到自己本地
- 负载均衡，不浪费 CPU

**4）都空 → 自旋 / 休眠，等新 G**

## 入队规则（新 G 放哪里）

- 新建 G：**优先入当前 P 本地队列**
- 本地满（256）：**本地一半 G + 新 G → 全局队列**
- 阻塞后唤醒的 G：优先回原 P 本地；原 P 满→全局

每个 P 有个计数器 `schedtick`，**每调度 61 次**，**强制先去全局队列拿 1 个 G 执行**，再回来跑本地。

- 前 60 次调度：**全跑本地**，全局完全被跳过。
- 第 **61 次调度**：
  1. 暂停本地队列
  2. **加锁去全局队列拿 1 个 G**
  3. 执行这个全局 G
  4. 解锁，**继续回本地队列执行**
- 全局队列里的 G：**每 61 次调度才有一次机会被执行**，延迟非常大，但**绝对不会永久饿死**。

Goroutine 执行 IO（网络 / 文件）时，不会阻塞内核线程 M！
G 会被挂起（Gwaiting），M 立即去 P 队列拿其他 G 执行。
等 IO 完成后，G 被唤醒，重新入队等待运行。

## IO 完成（网络数据到达）

- 网络事件触发（epoll 通知）
- G 被**唤醒**
- G 重新进入 P 的队列，等待 M 执行
- 从 Read 调用处**继续执行**

## 线程做 IO：

- 线程进入阻塞
- OS 将线程挂起
- **CPU 切换到其他线程**
- 开销巨大（TLB 刷新、页表切换）

_写屏障是 GC 并发标记时，堆上指针赋值（slot = ptr）前执行的一段代码，拦截并标记新旧指针对象为灰色，防止并发修改导致漏标、误回收_。

**内存阈值触发（最常见）**

- 公式：**堆内存 ≥ 上轮存活堆 × GOGC%**（默认 GOGC=100）百分比
- 例子：上轮 GC 后存活 100MB → 堆涨到 **200MB** 触发 GC
- 目的：控制堆增长，避免内存溢出

**手动强制触发**

- 调用 `runtime.GC()` → 立即启动一轮 GC（STW + 并发标记）

**定时触发（兜底）**

- 若**2 分钟**没触发过 GC → 强制触发一次，防止长期不回收

**4. 堆内存耗尽（OOM 前）**

- 堆内存达到系统限制，**即将 OOM** → 强制 GC 回收内存

**GOGC 是 “相对阈值”**：堆涨多少比例触发 GC
