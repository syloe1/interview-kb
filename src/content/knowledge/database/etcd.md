对外是一个有序的 KV 数据库，对内是一个 Raft 复制状态机。

```
客户端 gRPC/HTTP
      ↓
KV / Watch / Lease / Auth / 事务 API
      ↓
MVCC 存储层（按 revision 多版本）
      ↓
Raft 层（日志复制、选主、成员变更）
      ↓
WAL + Snapshot + BoltDB 后端存储
```

etcd 对外提供 KV 接口，内部用 Raft 把写操作复制成一致日志，再用 MVCC 管理多版本，BoltDB 做单机持久化，Watch 做变更通知。

### 微服务原理

微服务 = 把一个大单体应用，按业务领域拆成多个独立、自治、可独立部署、独立扩容的小服务；每个服务聚焦一块业务，服务之间通过网络互相调用协作，共同完成整体业务。
按领域拆分：用户服务、订单服务、支付服务、商品服务，**各自独立进程，可以部署在不同机器 / 容器**

- 调用：**跨进程网络调用**（HTTP / gRPC）
- 发布：只发改动的那一个服务，其他不动
- 扩容：哪个模块压力大，单独扩哪个（比如订单秒杀，只加订单服务实例）

### 服务注册 & 服务发现（最核心）

问题：订单服务要调用商品服务，**商品服务部署在哪台机器、有几个实例、IP 端口是多少？**

- 服务启动时：**服务端注册**，把自己的服务名、ip、端口上报到注册中心（etcd /nacos/consul /eureka），并且持续续约心跳
- 调用方：**客户端发现**，客户端监听注册中心，拿到这个服务所有可用节点列表

> go-zero 默认用 etcd 做注册发现

> 一句话：注册中心就是微服务的通讯录。

### ② 负载均衡

拿到一堆节点之后，选哪一个实例去调用？
常见策略：轮询、随机、加权、**P2C（go-zero 默认，带 EWMA 延迟感知，优先选延迟低的节点）**

> go-zero 是**客户端负载均衡**：客户端自己选节点，不需要额外 LB 组件（和 Nginx 这种服务端 LB 不一样）

### ③ 服务通信

两种主流方式：

1. **同步调用（RPC）**：gRPC（go-zero 内部 RPC），适合服务之间内部调用；协议 protobuf，二进制、速度快、强类型
2. **异步调用（消息队列 MQ：Kafka/RabbitMQ）**：发布订阅，解耦，削峰；适合不需要立刻返回结果的场景

> 同步：A 等 B 返回；异步：A 发消息，B 慢慢消费，A 不等待

### ④ 服务治理（微服务最头疼的部分，也是 go-zero 内置的重点）

网络是不可靠的！会超时、抖动、服务挂掉。

- **熔断**：某个服务大量报错，直接熔断，不再继续调用，快速失败，防止雪崩（故障扩散）
- **限流**：保护服务，防止请求打垮服务
- **降级**：熔断之后返回兜底数据，不直接报错
- **超时控制**：每个调用设置超时，避免 goroutine 堆积
- **重试**：瞬时失败可以重试（注意幂等！）
- **链路追踪（trace）**：一个请求跨多个服务，串起整条链路，看慢在哪、错在哪
- **监控告警**：QPS、延迟、错误率

> 这一块就是你前面看到的：go-zero 天生把这些能力内置，不用自己手写。

### ⑤ 配置中心

配置（数据库地址、开关、阈值）统一放在配置中心，不用改代码、不用重启服务就能动态更新配置。go-zero 支持 nacos/apollo/etcd 配置。

### ⑥ API 网关（Gateway）

所有前端请求统一入口：路由转发、鉴权、限流、日志、跨域。
前端不直接访问后端微服务，只访问网关。go-zero 的 Rest 服务经常当做网关。

## 3. 数据怎么处理？数据库原则（重要）

> 微服务经典原则：**一个服务拥有自己的数据库，服务之间不共享 DB**

- 用户服务 → user 库
- 订单服务 → order 库
- 商品服务 → goods 库
  好处：服务之间数据隔离，互不影响；
  代价：**分布式事务问题**（下单同时扣库存、扣余额，多个库，怎么保证同时成功 / 同时失败？）
  方案：TCC、SAGA、本地消息表、事务消息（MQ），尽量避免强一致。

## 单体

所有模块都在**同一个进程**里：用户、订单、支付、商品都在一个服务，共用一个数据库。

- 调用：函数调用（本地，内存直接调用，快、无网络开销）
- 发布：改一行代码，整个项目打包重启
- 扩容：只能整体扩容，不能单独给订单模块多加机器

### 网关

> 路由转发， 负载均衡， 安全（鉴权， 防爬虫，CORS， 黑名单）， 限流，熔断， ssl卸载

**网关是所有客户端流量的统一入口，接收请求，先执行一系列前置治理逻辑，再按路由规则转发到后端微服务；拿到后端响应后，可选再做后置处理，返回给客户端。**

> 它本质就是一个**反向代理 + 统一治理层**，用你之前学的【责任链模式】理解最贴切：请求进来走一条过滤器链。

## 一次请求完整流转（核心流程）

1. **接收请求 + SSL 解密**
   客户端 HTTPS 请求到网关，网关完成 SSL 证书解密（SSL 卸载），后端服务只用跑 HTTP，不用反复处理证书。
2. **全局过滤器链（责任链！）**
   请求依次经过：**跨域 → 黑名单 / 白名单 → 鉴权（token 校验） → 限流 → 日志采集 → 链路追踪埋点**
   ✅ 任意一步校验失败，网关直接返回错误，**不转发到后端**，保护下游服务。
3. **路由匹配（最核心一步）**
   根据规则匹配：请求路径、请求方法、header、参数、域名等
   例：
   - `/api/user/*` → 转发给用户服务
   - `/api/order/*` → 转发给订单服务
4. **负载均衡**
   路由匹配到服务名之后，拿到该服务的多个后端实例，选一个节点转发（轮询、加权、P2C 等）

> 这里有两种：
>
> - Nginx：upstream 静态配置节点
> - APISIX/Kong/go-zero 网关：对接注册中心（etcd/nacos），**动态感知服务上下线**

5. **转发请求到后端微服务**
   修改请求（重写路径、追加 header、传递 traceId），发起调用。
6. **接收后端响应，后置过滤器**
   拿到返回结果：统一包装响应、统一异常处理、记录访问日志、上报监控指标。
7. **把响应返回给前端**

> 失败场景：后端超时、报错、熔断触发 → 网关直接返回兜底响应，防止雪崩。

### 配置中心

> 解决**配置动态下发**
> 存业务配置 KV，客户端 watch 配置变更，热加载配置

### 注册中心

> 解决**服务发现**
> **服务上报自己的节点信息 + 租约保活 + 客户端 watch 监听变更，实现服务注册、健康检查、服务发现**。
