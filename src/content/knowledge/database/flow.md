### Webrtc rtp vs RTSP rtp

- RTSP-RTP：**RTSP（554，TCP 控制通道） + RTP/RTCP（UDP 媒体）**，安防摄像头经典模型
- WebRTC-RTP：**ICE + 信令 + DTLS + SRTP（加密 RTP）**，RFC8834 规定的 RTP 用法，浏览器原生 P2P/SFU 模型IETF Datat...

> WebRTC 只是**对 RTP 做了强制约束 + 配套扩展 + 加密封装**
>
> 1. RTSP interleaved：UDP 不通时，RTP 包塞进 RTSP 的 TCP 流里，这是安防设备非常常见的兼容手段；WebRTC 不走这个逻辑，ICE 发现 UDP 不通会切 TURN TCP 中继
> 2. RTSP 是**拉流（pull）**；WebRTC 是双向对等，既可以推也可以收
>    网关转换链路：`IPC(RTSP-RTP) → 媒体网关 → 拆RTSP、RTP → 重新打包成SRTP+SDP → WebRTC推给浏览器`，这是监控网页预览标准链路；**RTP 包不能直接透传**，要加 DTLS、改写 SDP、补 WebRTC 需要的 RTCP 反馈与扩展头

## 什么时候选哪个

- 设备端、摄像头接入、局域网取流、需要快进 / 暂停回放控制：**RTSP-RTP**
- 公网、浏览器播放、双向互动、弱网自动降码、NAT 穿透：**WebRTC（SRTP）**

### STUN TURN ICE

- STUN：只帮你拿到自己的公网映射地址，**不转发流量，只是问路**
- TURN：是中继服务器，P2P 打不通的时候，媒体包全部经过 TURN 转发（relay），**兜底保障一定能连通**
- ICE：调度器，决定什么时候收集候选、怎么配对、按什么顺序探测、选哪条通路

### STUN vs TURN

**STUN 用来「查自己公网地址、尝试 UDP 打洞」，不转发媒体；TURN 是「兜底中继，流量全部经过服务器转发」**，二者都被 ICE 调用，不是二选一。

### STUN 打洞过程

1. 内网 A 发 UDP 包给 STUN 服务器
2. 路由器 NAT 新建映射：`内网A:portA <-> 公网A:portA'`
3. STUN 把 `公网A:portA'` 返回给 A
4. A、B 互相向对方的 srflx 地址发包
5. 两边路由器都新建 NAT 映射 → **直连通道打通，媒体包不再经过 STUN**

> 弱点：对称 NAT，**访问不同目标，NAT 会换不同公网端口**，对方用拿到的 srflx 发包过来，路由器直接丢弃，洞打不通。

### TURN 中继过程

1. A 向 TURN 申请 Allocate，拿到 TURN 上的中继地址 `TURN_IP:RELAY_PORT`
2. A 告诉对端 B：你往这个 relay 地址发媒体
3. B 的包发到 TURN 服务器，服务器再转发给 A；A 发出去的包也先到 TURN，再转发给 B
4. **全程所有媒体流量都经过 TURN 服务器**，本质是一个 UDP 代理

### DTLS

> **TLS 的 UDP 版本，在 WebRTC 里专门用来给 RTP 做密钥协商 + 身份校验；协商完密钥之后，后面媒体流走 SRTP 加密。**
> TLS 跑 TCP；DTLS 跑 UDP，适配 RTP/ICE 这种无连接 UDP 媒体链路（RFC6347）
> ICE 连通（STUN 探测通） → **DTLS 握手** → 协商出密钥 → SRTP 加密 RTP 媒体

## SRTP

> SRTP 是 RTP 的安全轮廓，负责给 RTP 媒体包做加密、完整性校验、防重放；它本身不会协商密钥，密钥由 DTLS 生成

## SFU

> SFU 是 WebRTC 媒体转发服务器；只做 RTP 包复制转发，不解码、不混音、不重新编码，根据订阅关系选择性把流发给谁
> SFU 本身不做信令；信令是独立的 WebSocket 服务，负责房间、SDP、ICE 候选交换

| 类型     | 原理                                         | 上行                 | 下行     | 服务器 CPU         | 适用场景                     |
| -------- | -------------------------------------------- | -------------------- | -------- | ------------------ | ---------------------------- |
| Mesh P2P | 每个人直接连所有人                           | N-1 路（人多上行炸） | N-1 路   | 0                  | 2~4 人小通话                 |
| SFU      | 所有人只推一路给 SFU，SFU 复制转发           | 1 路上行             | N 路下行 | 很低（只是包转发） | 直播连麦、几十人会议（主流） |
| MCU      | 收全部流 → 解码混音合成一路画面 → 重编码下发 | 1 路上行             | 1 路下行 | 极高（编解码）     | 老旧硬件会议机，现在很少用   |

> SFU 为什么流行：上行只需要推 1 路，手机弱网上行友好；可以做 Simulcast 多码流分层，给不同观众发不同清晰度，不转码，成本低、延迟低

#### SFU感觉有点像MQ

```
表面上看：生产者推给中间节点、中间节点分发给订阅者，这个分发模型很像 MQ；
但**MQ 是面向离散可靠消息的排队系统；SFU 是面向 UDP 实时媒体的流量复制器，优先低延迟，允许丢包，不做消息堆积持久化，还有反向的拥塞 / 丢包反馈链路**。
RabbitMQ：我发一条 “订单创建” 消息，哪怕消费者暂时离线，消息可以存着等他上线再消费。
SFU：主播的视频包，如果观众网络卡暂时收不到，**过了抖动缓冲窗口的旧帧直接扔掉，不会缓存下来等后面补发**，补发只补最近关键帧，不会缓存整条历史流。

一个 PeerConnection 里面可以承载**多个 track**（主播视频、嘉宾视频、音频），不是一个 track 一条连接。
```

# HLS vs SFU（

**SFU 是 WebRTC 的媒体转发服务器，走 UDP SRTP，双向、亚秒级延迟，适合连麦互动；HLS 是基于 HTTP 的分片播放协议，单向拉流，延迟高，靠 CDN 海量分发，适合纯观看观众。**

> HLS 是**协议**；SFU 是**服务器架构**（承载 WebRTC）

### HLS

编码器输出视频流 → 源站切成 2~10s 的 TS 分片，生成 m3u8 清单。播放器不停请求 m3u8，按顺序下载分片播放。
连麦的几个人走 WebRTC + SFU；SFU 输出合成一路画面，转封装 HLS 送入 CDN，给几万几十万普通观众看

```
主播、嘉宾 ↔ SFU（WebRTC，300ms内，双向连麦）
        ↓ SFU输出混合流，转码打包
源站 → HLS分片 → CDN边缘节点 → 海量观众（2~10s延迟，只看不说）

```

### 主播推流是 RTMP，连麦是 WebRTC，为什么不统一全部 WebRTC？

主直播流追求**稳定、可追溯、方便录制、转码、CDN 链路打通**，RTMP+TCP 成熟稳定；
WebRTC UDP 在国内复杂运营商弱网上行，主直播流容错、日志、旁路录制链路更难做；
连麦优先低延迟双向交互，才选 WebRTC。

### 观众能不能走 WebRTC 看直播？抖音为什么不这么做？

技术上可行，但成本不可接受。100w 观众 = 100w 条 WebRTC 连接，每条连接 ICE/DTLS/SRTP 状态、定时器、内存开销巨大；而 FLV/HLS 是 HTTP 静态分片，CDN 边际成本极低。

## SFU 多人通话完整流程（重点，口述重点）

角色：多个参会端、**信令服务、SFU 媒体服务器、STUN/TURN**

1. **创建房间，信令通道建立（WebSocket）**
   某人创建房间，分配 roomId；其他人通过 roomId 加入房间。
   信令负责：进房、退房、上报在线成员、交换 SDP、ICE 候选、控制指令（静音、关闭摄像头、权限）。

> 信令只管控制，**不传输音视频媒体**。

2. **每个参会者：只 Publish 一路音频 Track + 一路视频 Track 给 SFU**
   不管房间里有 5 个人还是 20 个人，**每个人只往 SFU 推 1 路音频、1 路视频**（1 路上行）
   - 采集 → 编码 H264/VP8/AV1 + Opus 音频
   - 和 SFU 建立一条 WebRTC PeerConnection
   - 交换 SDP、ICE 连通、DTLS 握手、SRTP 加密
   - 推流到 SFU，SFU 给这个流打上 SSRC、标记所属用户
3. **SFU 做订阅路由**
   SFU 维护一张「房间 - 用户 - Track - 订阅关系表」
   A 加入房间，需要看 B、C、D：A 向 SFU 发起订阅 B 的 audio/video、C 的 audio/video……
   SFU 收到订阅请求之后：**把 B 的 SRTP 包复制一份发给 A，C 的 SRTP 包复制一份发给 A**

> SFU 不混流！A 收到的是**多路独立的 SRTP 流**：B 视频、B 音频、C 视频、C 音频……

4. **客户端本地做渲染、混音**
   重点！这个是很多人面试踩坑点：
   - 视频：客户端拿到多路视频流，分别解码出 YUV，前端自己做布局（大窗、小窗、九宫格）
   - 音频：客户端拿到所有人的 Opus 音频包，解码成 PCM，**本地混音**，再送到扬声器
     ✅ SFU 不混音、不拼画面！
5. **弱网反馈闭环（RTCP）**
   每一条媒体流都带 RTCP 反馈：NACK 丢包重传、PLI 请求关键帧、Transport-CC 带宽估计
   SFU 透传 RTCP，反馈回对应的推流端，推流端自适应降码率。
6. **Simulcast（多码流，多人通话必备优化）**
   推流端同时输出高 / 中 / 低清晰度三路流发给 SFU。
   比如手机性能差、带宽差的参会人，SFU 直接给他下发低清那一路，**不用重新编码**，减少下行压力。

> SVC 是另一种分层方案，VP9/AV1 支持，国内用得比 Simulcast 少。

7. **成员上下线处理**
   - 新用户进房：信令通知房间里所有人；其他人按需订阅新人的 Track
   - 用户退房：停止 Publish；SFU 删掉这个 Track，给所有订阅方停止转发这个流，释放资源

### 一个webrtc连接一个goroutine ??

成熟 Go SFU（LiveKit、Pion、SRS webrtc 模块）的主流方案：**事件驱动 + 协程池 + 定时器合并**

Pion（Go 最主流 WebRTC 库）底层模型：

- **PeerConnection 是状态对象，不绑定专属 goroutine**
- 包到达（UDP 读）：从 UDP IO goroutine 读到包，分发到对应 pc，触发回调
- 回调函数在**IO 协程池里执行**，处理 RTP/RTCP、状态变更
- 定时器：**合并定时器，而不是每个 pc 一个 Ticker**；用一个时间轮（time wheel）统一调度所有 PC 的定时任务（ICE 保活、RTCP 发送、BWE）

```
UDP Read Goroutine（少量，比如4~8个，绑定CPU核）
        ↓
包路由：根据SSRC/五元组找到对应的PeerConnection
        ↓
回调处理（worker pool，固定几十~几百个goroutine）
        ↓
PeerConnection对象（纯状态，无绑定协程）
时间轮协程（1个或少数几个，统一驱动所有定时任务）
不。Go goroutine 虽然轻，但上万 goroutine + 独立定时器会带来调度和 GC 压力。采用 IO 多路复用读 UDP 包，包路由到对应 PeerConnection，协议处理放到固定大小 worker 池；定时任务用时间轮统一管理，PeerConnection 只是状态载体，不独占 goroutine。
```

### 大码流实时预览核心思路

大码流（4K/8K、H.265/H.266、几十 Mbps~ 上百 Mbps）的痛点不是 “能不能解码”，而是**带宽拥塞、解码 CPU 爆掉、队列堆积、延迟持续上涨、丢帧卡顿**。
核心原则：**硬件解码优先、队列控深、大小流分流、协议选低延迟 UDP 流、渲染直接上显存**，不能用软解 + 大缓存的播放器套路。

## 大小流双码流架构（工业监控标配）

- **大流：主码流，高分辨率、高码率（4K@25fps，20~80Mbps）**，用来录像、抓拍、AI 分析，**预览端默认不直接拉大流**
- **小流：子码流，720P/1080P 低码率（2~6Mbps）**，专门给实时预览窗口、多画面分割预览
- 用户双击放大查看细节时，**临时切换拉大流**；退出放大切回小流，保护带宽和解码性能阿里云帮助...

> 很多人预览卡顿就是直接全窗口拉 4K 大流，多路同时预览直接打满网卡和解码器。

### AI边缘盒子

IPC 输出 RTSP (H.264/H.265)→硬件解码分流（预览走子码流、AI 推理取主码流）→本地 YOLO 类目标检测→告警 MQTT/HTTP 回调推送云平台；**预览流不经过 AI 推理，大小流分离规避大码流卡顿**；支持 Docker、自定义算法接入。

### TOPS

**TOPS = Tera Operations Per Second，每秒万亿次运算（INT8 定点）**
边缘 AI 盒子标的一般都是 **INT8 TOPS**（不是 FP32）
**是 NPU 算力**，专门跑 YOLO、目标检测这类 AI 推理。
只是一个理论峰值上限，实际要扣：解码开销、内存带宽、后处理、队列调度、码流分辨率。4K 大流推理会吃掉大量带宽，实际能跑的路数会缩水。

# 实时路数是什么

**实时路数：这个网关同时稳定做 AI 分析的摄像头数量**
比如 V3 写 12~16 路：

- 代表同时接入 12~16 路 IPC，**每一路都持续解码 + 抽帧 + NPU 推理 + 告警后处理**
  工业标准做法：IPC 开双码流
  主码流（高清大流）→ 送到网关做 AI 识别
  子码流（低清小流）→ 流媒体服务给页面 / 上位机预览，不占用 NPU 算力

### MediaMTX vs ZLMediaKit

**MediaMTX 是 Go 写的「流路由器 / 协议转发代理」，它不做解码、不做 AI 推理、不转码；只做 RTP 包透传 + 协议互转**，这是它和 ZLMediaKit 最大的分水岭。

> 重点：它**只搬运裸 H264/H265 RTP 包，不碰码流内容**，没有解码开销，这就是它在边缘盒子上轻量的根源。

```
IPC摄像头（双码流）
├─ 主码流（4K大流，H265） → 推/拉给【AI网关（C++底层：FFmpeg硬解 + NPU YOLO推理）】 → 告警MQTT/HTTP上报
└─ 子码流（1080P/720P小流） → 送入【MediaMTX（Go）】
        ↓
MediaMTX 内部一份流，多协议分发：
        ├─ RTSP → Qt C++上位机（硬件解码预览，就是你前面问的大码流预览）
        ├─ WebRTC → 网页平台预览（低延迟，适合云平台）
        ├─ HLS → 回放/移动端
        └─ 控制API：Go业务服务控制拉流启停、鉴权、状态监控

```

### 切画质

不是网卡主动切画质，是 WebRTC 的 BWE（带宽估计，Transport-CC） + 编码器配合，在探测到带宽不够的时候，主动降码率、降分辨率 / 帧率，表现出来就是画面变糊、变成低画质。网卡只是搬运包，它不懂画质
重点区分两件事：
✅ **码率自适应（ABR，最常见）**：分辨率不变，调 QP，画面变糊，码率压下来
✅ **分辨率自适应**：直接降到 1080p/720p，改动更大，很多编码器 / SDK 是可选开关，不是默认一定切分辨率
✅ **Simulcast（多流并发）**：推流端同时发高 / 中 / 低三路，SFU 直接切流，编码器不用动态改分辨率（LiveKit、MediaSoup 常用这个方案）

### hls是什么？cdn分发怎么做的？ rtmp是啥

**OBS / 编码器 → RTMP 推流到源站 → 源站转封装成 HLS (m3u8+ts 分片) → CDN 全网边缘节点缓存分发 → 用户 HTTP 拉 HLS 播放**

> RTMP 主打「推流上云」，HLS 主打「海量用户播放分发」；WebRTC 是另外一条低延迟互动路线，**原生不适合大规模 CDN 分发**

## RTMP（Real-Time Messaging Protocol）

- 底层：**TCP 长连接**，端口默认 1935，Adobe 老协议
- 核心定位：**推流协议（第一英里 Ingest）**，现在几乎不用来给浏览器观众播放
- 原理：把音视频、元数据切成小 chunk，在一条 TCP 连接上持续发送，有序可靠传输
- 延迟：GOP=2s 时一般 1~3s
- 优点：
  - OBS、FFmpeg、硬件编码器全部原生支持，生态极强
  - 推流稳定，自带控制信令（publish/play）
- 缺点：
  - 浏览器原生不支持（Flash 已经淘汰）
  - TCP 队头阻塞，弱网下延迟持续累积
  - 并发百万观众分发不适合 RTMP，CDN 对 RTMP 播放支持差

> 补充：RTMPS = RTMP over TLS，加密推流，现在平台都推荐用这个

## 2. HLS（HTTP Live Streaming，苹果提出，RFC8216）

- 底层：**纯 HTTP/HTTPS，无长连接**，分片文件下载
- 两个核心文件：
  1. `.m3u8`：UTF-8 文本索引清单
     - 主 m3u8：同时列出 4K/1080p/720p 多路不同码率子流（ABR 自适应）
     - 媒体 m3u8：列出一串 ts 分片 URL
  2. `.ts`（MPEG-TS）分片：一般 2~10s 一段独立音视频片段；**必须等整个分片编码完成，才会写入 m3u8**
- 流程：播放器先 GET m3u8 → 解析分片地址 → 循环 HTTP 下载 ts、解码播放，每隔一段时间重新拉 m3u8 拿到新分片
- 延迟：标准 HLS **10~30s**；LL-HLS（低延迟 HLS）支持 partial segment，压到 2~4s
- 优点：
  - 全平台原生支持：iOS、安卓、小程序、浏览器 video 标签直接播放
  - 天然适配 CDN（本质就是一堆静态小文件），海量并发成本极低
  - 带宽自适应 ABR：网速差播放器自动切低清分片，和你前面问的 BWE 有点像，但**是播放器侧基于下载速度切换，不是发送端闭环控码率**
- 缺点：
  - 标准 HLS 延迟很高，**不适合连麦互动**
  - 分片有最小粒度，延迟下限由分片时长决定

> 区分：HLS 是**分发协议**，不是推流协议；主播一般不会直接推 HLS 给 CDN

## 3. CDN 怎么分发 HLS 直播？

CDN = 遍布全国的**边缘节点 PoP** + 调度 DNS + 回源链路，直播 HLS 是**动态缓存**模式：

1. **主播 RTMP 推流到【源站】**：源站转码、打包，持续生成 m3u8 和 ts 分片
2. 源站把分片持续推 / 拉到 CDN 上层父节点
3. 用户播放：DNS 调度根据用户 IP、运营商、负载，分配**离用户最近的边缘节点**
4. 边缘节点判断：
   - ✅ 缓存命中：分片已经在本机，直接 HTTP 返回给播放器，**不回源**（绝大多数请求是命中）
   - ❌ 未命中：边缘节点向上回父节点 / 回源站拉这个分片，返回用户，同时缓存这个 ts 分片给后面观众
5. 直播 m3u8 是动态清单，边缘节点会短期缓存 m3u8，定时回源刷新最新分片列表

> 重点：
>
> - CDN 节点**不解码、不解析视频内容**，它只把 ts/m3u8 当成普通静态文件做 HTTP 缓存转发
> - 海量观众压力被分摊到全国成千上万个边缘节点，源站压力很小，这就是为什么抖音、B 站直播用这套
> - 和 SFU 对比：SFU 转发 SRTP UDP 包；CDN 分发 HLS 是 HTTP 文件缓存，完全两套分发模型

## 整条 WebRTC 链路串起来（完整时序）

1. ICE 探测 → 选出可用 UDP 通路
2. **DTLS 握手**（在这条 UDP 上跑）→ 校验 SDP 里的证书指纹，ECDH 算出主密钥，导出 SRTP 密钥
3. 后续音视频全部打包成 **SRTP/SRTCP** 在这个 UDP 上传输

> 端口上的包复用区分规则（经典考点）：
>
> - 首字节 0/1 → STUN
> - 20~63 → DTLS 握手包
> - 128~191 → RTP/SRTP 媒体包IETF

## SIP vs SDP

| 技术                | 核心定位                          | 主要用途                                                                                                     |
| ------------------- | --------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| SIP（会话初始协议） | 多媒体**信令控制协议**（RFC3261） | 发起、修改、挂断音视频会话；寻址、呼叫、会话状态管理；**不传输音视频裸流**，消息体里携带SDP                  |
| SDP（会话描述协议） | 媒体参数**描述格式**（RFC8866）   | 媒体协商：告诉对方我支持什么编码(H264/AAC)、RTP端口、IP地址、带宽；SIP的body，offer/answer模型做媒体能力对齐 |
| RTP                 | 媒体传输协议                      | 真正传音视频数据包                                                                                           |

- **SIP = 打电话的控制信令**：“我要呼叫你、振铃、接通、挂断”，管**什么时候建立会话**、找谁；
- **SDP = 通话的技术协商清单**：“我发 H264，我在 192.168.1.100:5004 收 RTP”，管**音视频用什么格式、往哪发**；
- 真正的画面声音，走 **RTP**，不走 SIP/SDP。

### 典型流程（VoIP / 视频会议）

1. A 发 `INVITE(SIP)`，消息体内带上 SDP（offer：我的能力）
2. B 回复 `200 OK(SIP)`，带上自己的 SDP（answer：协商好的编码端口）
3. A 回 `ACK(SIP)`，信令握手完成
4. 双方直接用 RTP 互相推音视频流

### 直播 + 连麦整套流程

角色：主播、普通观众、连麦嘉宾、**信令服务器、SFU 媒体服务器、STUN/TURN**

1. **主播加入房间，发布流（Publish）**
   - 主播采集音视频，编码 H264/VP8
   - 和 SFU 走信令交换 SDP、ICE 候选
   - ICE 连通探测 → DTLS 握手 → 生成 SRTP 密钥
   - 主播向上推**一路 SRTP 流给 SFU**
   - SFU 保存主播这个 Track，房间内所有人可以订阅
2. **普通观众进来，只订阅主播流（Subscribe）**
   - 观众和 SFU 建立一条 WebRTC 连接
   - 向 SFU 订阅主播 Track；SFU 把主播的 SRTP 包复制一份发给观众
   - 观众端解密 SRTP、解码渲染；**观众不推流，只有下行**
3. **观众点击【连麦】，变成连麦嘉宾（重点）**
   - 连麦请求先走**信令**发给主播 / 后台，主播同意
   - 这个观众现在要**Publish 自己的音视频 Track 给 SFU**（新增一路上行）
   - SFU 收到嘉宾流之后：
     - 推送给主播（主播订阅嘉宾）
     - 推送给房间里其他所有人（其他观众自动订阅嘉宾流）
   - 现在房间里有两路源：主播 Track、嘉宾 Track；SFU 分别复制分发
4. **弱网反馈由 RTCP 在这条链上跑**
   - 客户端发 NACK / PLI / Transport-CC 给 SFU
   - SFU 透传 RTCP 反馈回推流端；主播 / 嘉宾自动降码率、重传
   - Simulcast：推流端同时发高 / 中 / 低三层码流，SFU 直接切层，不用转码

> 链路串联回顾：
> 采集编码 → RTP → SRTP → UDP (ICE 打通) → SFU（只转发 SRTP 包，不解密！SFU 不解密是默认模式；转码 SFU 才会解密）

## RTSP interleaved 报文格式（固定 4 字节头，就是你要解析的 `$` 帧）

```txt
 0      1        2-3
$ | ch |  length (big-endian)
- `$`：魔字 `0x24`，这就是验收说的 `$` 帧标记
- ch：通道号（interleaved=N-M，N 一般 RTP，M RTCP）
- length：后面 RTP/RTCP payload 长度，**不含这个 4 字节头**
```

### RTSP、RTMP 都无法在浏览器原生播放。前端播放有几条主流路线：

1. WebRTC：底层同样基于 RTP，但是需要 SDP、ICE、DTLS；优势是低延迟，适合实时监控预览，开发复杂度高；
2. HLS：把音视频切成 TS 切片，浏览器原生支持，适合高并发、回放场景，延迟高；
3. HTTP-FLV，配合 flv.js，是折中方案，延迟中等。
   我当前 RTSP/RTP 项目，可以把 RTP 解包后的 H264/AAC 裸帧，转成上面任意一种；业务上经常组合使用：WebRTC 做实时预览，HLS 做录像回放。也可以交给 ZLMediaKit 这类网关，一路 RTSP 输入，多路输出不同协议给前端。

## HTTP-FLV HLS

1. **FLV：封装容器（盒子）**，里面装 H264 + AAC；
2. **FLV 解封装（demux）**：把 FLV tag 拆开，取出里面的 H264 NALU、AAC 裸帧（和你 RTP 解包拿裸帧是一类工作）；
3. **HTTP-FLV**：**在 HTTP 长连接（chunked）上持续流式下发 FLV**，前端靠 flv.js + MSE 播放；
4. **HLS**：切片成 TS 文件 + m3u8 索引，**封装是 TS，不是 FLV**，浏览器原生 video 标签支持。

ANNOUNCE 范式（你现在这个分支）：ffmpeg 先发 `ANNOUNCE` 带 SDP，宣告自己要推的媒体轨；之后再 SETUP、RECORD。

## HLS m3u8文件可以直接note打开

HLS（HTTP Live Streaming）的核心就是**分成两类文件**：

1. **m3u8 索引文件（文本）**：记录分片 ts 文件名、时长、码率、加密信息、序列编号等；播放器先拉这个文本，读完清单再依次去下载每一个媒体分片。
2. **.ts 媒体分片（二进制）**：真正装音视频数据，H.264/H.265 + AAC 这类。
   打开记事本看到的内容示例：

```txt
#EXTM3U
#EXT-X-VERSION:3
#EXT-X-TARGETDURATION:10
#EXT-X-MEDIA-SEQUENCE:0
#EXTINF:9.960,
0.ts
#EXTINF:9.960,
1.ts
#EXT-X-ENDLIST
```

- `#EXTM3U`：固定头部，代表这是 HLS 索引
- `#EXTINF`：后面是这个分片的时长
- 下面一行就是分片地址（相对 / 绝对 URL）
  `.m3u8` 本质就是一个遵循 `EXTM3U` 标记规范的文本清单，不是二进制。

1. **主 m3u8（多码率自适应）**
   里面不直接写 ts，而是指向**子 m3u8**（不同清晰度）：

```
#EXTM3U
#EXT-X-STREAM-INF:BANDWIDTH=800000,RESOLUTION=640x360
360p.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=1500000,RESOLUTION=1280x720
720p.m3u8
```

播放器先拉这个主索引，根据带宽自动选一路子流。

#### 播放器请求 m3u8（文本索引）→ 解析拿到所有分片地址 → 循环请求一个个 ts 分片 → 解码播放。

## RTSP、信令：协商两端的媒体参数

一个流：RTP媒体端口，RTCP控制端口

### Jitter（抖动）：接收端的内存队列。

1. 缓存一段RTP包
2. 利用序列号对乱序包排序
3. 等待包，凑齐一帧再送给解码器

时间戳：媒体采样计数器，单位：采样点
H.264：90000 Hz
每采样一个样本，时间戳+1
H.264 FU分片所有包TS一样

CSRC：贡献源，混音场景，把多路音频混合成一路输出，CSRC用来记录原始各路的SSRC

### RTCP报文

SR发送报告：一个SR对应一个SSRC

- SSRC：这份报告属于哪个流
- NTP timestamp：绝对世界时间
- RTP timestamp：RTP时间戳
- SPC：发送总包数
- SOC：发送总字节数

RR接收报告：

- fraction loss：丢包比例
- cumulative：累计丢包
- Seq：收到的最大序列号
- jitter：抖动
- LSR：上一次收到SR的NTP时间
- DLSR：距离上次收到SR过去了多久
- RTT = 当前NTP − LSR − DLSR

抖动计算公式：
$$D_i = (R_i-R_{i-1})-(S_i-S_{i-1})$$
$$J_i = J_{i-1} + \frac{|D_i|-J_{i-1}}{16}$$

# WebRTC 流程笔记

1. **信令交换：SDP（offer / answer）**
   内容：双端协商“通信信息”
   WebRTC 不绑定信令协议，可以用 WebSocket、HTTP 等。

2. **NAT穿透 / ICE：解决内网设备互相找到对方**

- ICE：自动收集所有可用网络地址（内网、公网IP、中继地址）
- STUN：获取自己的公网IP
- TURN：穿透失败时的中继服务器，走转发

3. **Peer 连接成功**
   底层走 SRTP（加密的RTP），直接收发音视频

- Offer：发起方发送的 SDP，描述自己编码、媒体、地址
- Answer：接收方回复的 SDP，做协商，同意连接
- ICE Candidate：网络地址（ip+port，双向连接），发给对端
- SDP：描述音视频编码、媒体轨道、RTP信息

# SDP + RTSP + WebRTC 笔记

SDP：会话描述协议
RTSP DESCRIBE 返回 SDP 媒体描述；
告诉播放器：媒体是什么编码、用什么端口、怎么组包。

SDP 每行都是 `key=value` 格式

- `v=`：版本，固定为0
- `o=`：发起者，会话标识
- `s=`：会话名
- `c=`：连接信息，媒体服务器IP
- `m=`：媒体描述，音视频、端口、传输协议、负载类型
- `a=rtpmap`：编码信息，PT值+编码名
- `a=fmtp`：编码参数，H264 里面放 SPS、PPS
- `a=control`：轨道标识，SETUP 时使用，`trackID=xxx`

流程：
`DESCRIBE` → 拿到 SDP，解析出 track
`SETUP` 使用 track 里的 control

编码示例：`96 H264`、`8 PCMA / PCMU`

## WebRTC

WebRTC：浏览器实时音视频通信技术
浏览器之间点对点，直接音视频/数据，底层基于RTP

- `getUserMedia`：获取摄像头/麦克风
- `RTCPeerConnection`：P2P连接，音视频
- `RTCDataChannel`：任意数据/文件

## RTSP 与 WebRTC 对比

- RTSP：客户端 ↔ 服务器（拉流）
- WebRTC：浏览器 ↔ 浏览器（P2P直播）
- WebRTC 优势：NAT穿透，适合公网/内网穿透

# RTSP 笔记

RTSP：实时流控制协议，**只负责控制，不传输媒体数据**
端口：554 / TCP

- 客户端：拉流、播放、暂停、停止（播放器/平台）
- 服务端：摄像头、NVR、流媒体服务

信令通道：RTSP 命令基于 TCP 长连接

- TCP 模式：RTP 数据混在 RTSP TCP 端口内，防防火墙拦截
- UDP 模式：单独端口传输，延迟低，是安防摄像头主流

## RTSP 方法

- OPTIONS：查询服务端支持哪些方法
- DESCRIBE：获取媒体信息（SDP、编码、分辨率、RTP端口）
- SETUP：建立 RTP 传输通道，协商端口、传输模式
- PLAY：正式开始推送音视频流
- PAUSE：暂停流
- TEARDOWN：断开连接，释放资源

## 关键头部字段

- CSeq：请求序列号，请求和响应一一对应
- Session：会话ID，SETUP之后生成，后续操作携带
- Transport：指定传输方式（UDP/TCP，客户端端口）

## 标准流程

1. OPTIONS 握手探测
2. DESCRIBE 获取 SDP 媒体描述
3. SETUP 绑定 RTP 收发端口
4. PLAY 开始播放，服务端推送 RTP 音视频
5. 客户端接收 RTP 流
6. TEARDOWN 结束会话

## SDP 的作用

DESCRIBE 响应携带 SDP，描述媒体轨道、H264/H265、采样率、RTP负载类型、IP端口；
没有 SDP，客户端不知道怎么解析 RTP 包。
