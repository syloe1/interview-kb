## 一、HTTP/2.0 扩展设计练习

今天上课想到了之前的 Reactor net 项目，想扩展增加一个 HTTP/2.0（二进制快、而且多路复用）。

### 背景与模糊想法

- TCP 字节流按照行读，处理粘包、半包，然后 http1.0 有个解析机专门处理。
- 只能想到一个很抽象模糊的想法：实现一个 http2.0 的解析机是不是就行了？不能拆成一个个小块。

### HTTP/2.0 要点

```text
HTTP/2：二进制帧协议，不再是文本换行。
最小单元：Frame（帧），不是行；每个帧有固定头部（9 字节）+ 负载
多路复用：同一个 TCP 连接，多个 Stream 并行收发
HPACK 头部压缩：Header 不再是明文键值对，需要 HPACK 编解码
流状态机：每个 stream 有独立状态（idle/open/half-close/closed），还要处理流控窗口 WINDOW_UPDATE
预定义 SETTINGS 帧、PING、GOAWAY、RST_STREAM 等控制帧
```

### 想不清楚的问题

- Http2 解析机是挂在 TcpConnection 下面？还是替换 HttpParser？还是和 HttpParser 并列？
- TcpConnection 的 buffer 要不要改？
- http1 和 http2 能不能共存，同一个服务既支持 http1 又支持 http2？
- HPACK、stream、流控，属于解析机内部，还是外面独立模块？

### issue：拿到一个大功能直接想最终成品，而不是拆成可验证的小里程碑

### solu

1. 画出当前数据流
2. 写出新协议（HTTP2）期望的数据流
3. 识别：哪些是【必须新增】，哪些【修改原有】，哪些【禁止改动】
4. 切分任务
5. 识别未知风险点，列出自己不会的清单

### 看代码 vs 做扩展设计

> 看代码：是顺着执行流走，别人已经把模块切好，你跟着调用链读就行。
> 做扩展设计：是逆着数据流思考——新增的数据从哪里进来？经过哪些模块？输出到哪里？哪些老模块需要增加接口适配？哪些不能动？怎么划分新增类的职责？

### 照着教程学 vs 自己做扩展

> 看教程项目：问题先行，方案是别人已经推导好的，你接收结论。
> 自己做扩展：没有现成问题摆在面前，需要你自己发现问题、定义问题、再推导方案。

```text
看教程 = 学习别人的输出结果
架构能力 = 练习推导过程
```

### 训练建议

- 增加自己定义约束、自己抛出问题、脑补备选方案、权衡取舍的训练。
- 项目先做 MVP，用 agent 做要收敛问题规模。
- 能跑 → 一个可复用的计算结构。
- 需要一个进度跟踪和监督的东西。
- 一个东西：构思 → 实现 → 交流。

## 二、AI 时代的焦虑与定位

现在 AI 和 agent 不断升级，作为一个应届本科生，我很焦虑。虽然专业知识有积累，也学习了一些项目，但是设计能力还是很弱，而且编码也不可能编过 agent。如果我天天让 agent 干活，那我存在的价值呢？老板为什么还要招人？

### 不让 AI 全盘输出，人做拆解任务

人做拆解任务、定约束，把切分的子任务给 AI 编码。

```text
AI 能干：
- 把明确需求翻译成代码、写脚手架、写单元测试、调库 API、修复简单编译 bug、生成 MVP。
- 给你多种实现方案，做语法层面的改造。

人：
1. 判断需求要不要做
2. 理解系统上下文，识别隐藏风险
   [其实我感觉多 agent 协同可以做，但是 token 太烧了，学生玩不起]
   给 Agent 一个小模块，它写很漂亮。但放到你现有微服务、数据库、RPC 链路里，
   会不会破坏一致性？会不会引入死锁？会不会引发 OOM？会不会老版本不兼容？
3. 拆解模糊问题，把人话变成可执行任务
   把一团混沌的问题拆成可以丢给 AI 的子任务。
   "做一个文件网盘，要支持分享"
   ---> 数据库表怎么设计？鉴权怎么做？大文件分片？存储怎么限流？怎么防恶意上传？
```

### 调整行为模式

```text
1. 人先思考：整体架构、模块划分、边界、约束条件，写出提纲。
2. 把小的、明确的子任务丢 AI："基于这个结构体，写这个 RPC 处理函数，注意这 3 个约束"。
3. AI 输出代码，你做评审：逐段读，判断逻辑对不对，有没有坑，哪里不符合项目规范。
4. 自己改，补边界 case，写测试；遇到 bug，自己主导定位，AI 辅助排查。
5. 复盘：刚才 AI 哪里写错了？为什么会错？把这个经验变成自己的。

用 AI 产出 MVP 之后，强迫自己做一轮 review：
"AI 写的这个模块，边界合理吗？如果并发上来会不会出问题？有没有隐藏风险？"

AI 可以快速造 demo，但维护长期、复杂、要稳定线上运行的系统，需要人的判断力。
```

### 价值定位

- 纯"执行层"的初级岗位确实会减少，竞争会更激烈。但这反而抬高了"有完整交付能力"的应届生的相对价值。
- 过去招聘应届生写 CRUD，不是因为写 CRUD 有价值，而是因为没有更便宜的办法。现在 agent 能把这块吃掉，暴露的不是"你没用了"，而是"这部分本来就不值钱"。
- 关键问题是"谁对一个东西能不能 work 负责、出了问题谁负责"。
- 现在 agent 帮你把编码时间压缩到十分之一，你反而有更多的"项目吞吐量"去练设计。
- 从"写代码的人"升级成"负责把事情做成的人"。

> 面对一个模糊的问题，你能不能判断应该做什么，并且让最终系统可靠地跑起来。

```text
结果负责人：agent 生成的代码谁验证？出了问题谁负责？
判断力：agent 能给你 10 个方案，选哪个、砍哪个。
上下文理解：这个需求为什么这么提、业务部门真正想要什么。
```

## 三、人机协作工作流

### 用 agent 加速做完整项目

> 每个项目都逼自己写设计文档、画架构图、复盘取舍。

以一个例子说明：**"我们要做一个支持 QQ、微信、GitHub、Google 登录的系统。"**

一个初级程序员可能想："OAuth2 怎么写？" 然后开始搜 "OAuth2 Go example"，然后让 Agent "帮我实现 OAuth2 登录"。Agent 给你：

```text
oauth/
├── provider.go
├── github.go
├── google.go
├── qq.go
└── wechat.go
```

代码写得漂漂亮亮，然后你："卧槽，AI 真强。" —— 但这时候真正困难的问题还没开始。

**用户身份怎么统一？** 各平台返回的标识不同：

```text
GitHub 返回：github_user_id = 123
Google 返回：sub = xxx
微信返回：openid = xxx
```

你是不是要设计：

```text
users
oauth_accounts
```

然后：

```text
user
  │
  ├── github account
  ├── google account
  ├── qq account
  └── wechat account
```

**那绑定规则呢？** 用户 GitHub → 注册，之后 Google → 登录，发现 Google 邮箱和 GitHub 邮箱一样，能不能自动合并？如果不能为什么？如果能会不会出现账户接管？

**OAuth 回调怎么办？**

```text
Browser → Gateway → OAuth Provider → Callback → OAuth Service → User Service → Session / JWT
```

谁负责什么？Gateway 是否应该知道 OAuth Provider？还是：

```text
Gateway → Auth Service → Provider
```

再往下：如果 QQ 登录成功但 User Service 超时怎么办？OAuth provider 已经成功了但本地用户创建失败怎么办？重复 callback 怎么办？state 怎么防 CSRF？token 放哪里？刷新怎么办？服务之间怎么鉴权？日志记录什么？敏感信息不能记录什么？

你会发现：**Agent 非常擅长回答"怎么实现"，但工程里最贵的问题往往是"我们到底应该实现什么？"**

老板需要的是一个能够对结果负责的人。比如老板说："我们的接口最近经常超时，你解决一下。"

```text
你：定义需求      → Agent：调研方案
你：判断架构      → Agent：实现模块
你：Review       → Agent：补测试
你：跑 benchmark → Agent：分析结果
你：决定是否上线
```

## 四、评判标准与能力模型

### 评判标准

- 如果没有 Agent，我能不能看懂它为什么这么设计。
- 如果 Agent 给了我三个方案，我能不能判断哪个更合理。
- 如果需求改变，我能不能重新设计。

### 自查清单

```text
架构 → 并发模型 → 网络 IO → 内存 → 生命周期 → 异常 → 性能 → 测试 → benchmark → 线上问题模拟
```

然后再拿 Agent 来帮你：

- "提出 20 个可能的设计问题。"
- "Review 我的 Reactor 架构。"
- "故意找出其中 10 个潜在并发 bug。"
- "给我设计 benchmark。"
- "模拟面试官追问我。"

这样 Agent 不是在削弱你的能力，而是在给你提供一个以前一个本科生很难拥有的东西：一个随时可以陪你进行代码 Review、架构讨论、Debug、反驳和模拟面试的高级工程师。

一个会使用 AI、懂系统设计、懂业务、会 Debug、会判断技术取舍的工程师，把原来需要 5 个人做的工作做掉了。

### 能力模型

```text
计算机基础 + 工程经验 + 系统设计 + 问题拆解 + Debug 能力 + AI Agent

             你
              │
      ┌───────┴───────┐
      ↓               ↓
  判断/设计          Agent
      │               │
      │          写代码/测试/
      │          调研/分析
      └───────┬───────┘
              ↓
           工程结果
```

我负责思考和设计，Agent 负责执行，我负责 Review 和最终决策。
