### FreeRTOS 跑在单片机上，专为嵌入式实时场景设计：

### FreeRTOS 只是个**内核（Kernel）**，只有最核心的东西：

- 任务调度（多线程）
- 任务间通信（队列、信号量）
- 同步（互斥锁）
- 没有文件系统、没有网络、没有图形界面

> 类比：FreeRTOS ≈ 只有 Go runtime 调度器 + channel + mutex 这部分，其他全要你自己写。
> 没有 FreeRTOS 的时候，单片机是 "裸机"：你写一个 main 函数，while (1) 里把所有逻辑按顺序跑，就像单线程程序。
> 有了 FreeRTOS：你可以同时跑多个 "线程"（任务），内核帮你调度，就像 Go runtime 帮你调度 goroutine。

- 支持优先级抢占式调度
- 任务切换延迟µs级别，时间行为可预测
- 中断响应快，适合工业控制、传感器采集、伺服驱动等对时间响应有严格要求的场景

| 运行环境               | 调度单元  | 调度延迟    | 实时性定位                 | 风险说明                                                               |
| ---------------------- | --------- | ----------- | -------------------------- | ---------------------------------------------------------------------- |
| Linux（通用内核）      | 进程/线程 | 毫秒级(ms)  | 非实时；CPU抢占不受控      | 后台业务可用，工业硬实时场景不达标，延迟抖动大，极端情况会引发工业事故 |
| Go goroutine           | GMP M协程 | ms ~ 几十ms | 用户态协程，依托OS线程调度 | 调度受操作系统影响，协程本身不具备硬实时能力，延迟抖动大               |
| FreeRTOS（单片机裸机） | Task任务  | 微秒级(µs)  | 轻量硬实时RTOS             | 可满足工业精确时间响应，中断+任务抢占，调度延迟极小，时间确定性强      |

## 关键要点

1. Linux 本身是分时操作系统，CPU资源可以随意抢占，内核有大量不可抢占区域、缓存、调度抖动，**没有硬实时保证**。即使加上PREEMPT_RT补丁，也只是软实时增强，和单片机RTOS确定性仍有差距。

#### 今天跑的双LED

```go
package main

import (
    "fmt"
    "time"
)

func taskLED1() {
    for {
        togglePA0()  // 翻转PA0
        time.Sleep(500 * time.Millisecond)  // 相当于 osDelay(500)
    }
}

func taskLED2() {
    for {
        togglePA1()  // 翻转PA1
        time.Sleep(1000 * time.Millisecond)
    }
}

func main() {
    go taskLED1()  // 相当于创建TaskLED1
    go taskLED2()  // 相当于创建TaskLED2

    select {}  // 相当于 osKernelStart()，阻塞住
}

```

- 学 FreeRTOS，本质上就是**把你已经会的并发概念，搬到一个只有 20KB RAM 的小芯片上**。

1. **消息队列** = Go 的带缓冲 channel
   - ADC 采集到一个电压值 → 丢进队列 → 另一个任务读出来打印
   - 就像 `ch <- value` / `value := <-ch`
2. **互斥锁** = Go 的 sync.Mutex
   - 两个任务都要用串口打印，不加锁会输出乱码
   - `mu.Lock()` / `mu.Unlock()` 一模一样
3. **优先级翻转** = 后端很少遇到的问题
   - 高优先级任务等低优先级任务放锁，中间被中优先级任务插队
   - FreeRTOS 的互斥锁有 "优先级继承" 机制，自动解决这个问题

## 裸机 vs FreeRTOS 对比

### 裸机（没有 FreeRTOS）

```c
while(1) {
    按键扫描();
    传感器采集();
    串口发送();
    LED闪烁();
    // 必须按顺序跑，一个慢了全卡
    // 比如传感器采集要100ms，那按键就100ms才能响应一次
}
```

### 用了 FreeRTOS

```c
任务1: 按键扫描 → 每10ms响应一次，不被别的任务卡住
任务2: 传感器采集 → 100ms采一次，不影响按键
任务3: LED闪烁 → 按自己的频率闪
// 每个任务各干各的，互不耽误
```

## 一句话总结

> **裸机 = 一个人干所有事，排队干**
> **FreeRTOS = 招了好几个人，同时干活，老板（调度器）安排谁先干谁后干**

### 树莓派 vs 单片机

## MMU（内存管理单元）

这是为什么树莓派能跑 Linux、STM32 不能跑的根本原因。

- **有 MMU（树莓派）**：可以给每个程序分配独立的地址空间，程序 A 崩了不会影响程序 B，就像你电脑上的 Chrome 崩了，微信不会崩。Linux 必须要 MMU 才能跑。
- **没有 MMU（STM32）**：所有程序共用同一块内存，一个任务踩内存了全片死机（你今天踩的栈溢出 HardFault 就是这个）。这种只能跑简单的 RTOS。

> 类比：
>
> - STM32 = 一个大开间，所有人挤在一起坐，一个人打翻桌子全桌遭殃
> - 树莓派 = 每个人都有独立办公室，互相不影响
