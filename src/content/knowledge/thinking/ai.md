## AI 联调

> #### 第一轮：只诊断前端，先报告后改

你现在只读审计，不要改代码。请分析 frontend/ 的渲染性能，给出问题清单，按“影响 × 改动成本”排序，并对应到具体文件/行。重点排查：首屏包体积与拆包、长任务与 INP、不必要的重渲染（memo/useMemo 误用/上下文穿透）、路由懒加载、图片/字体加载、列表虚拟化、轮询与重复请求、WebSocket/缓存策略、构建配置（sourcemap、压缩、tree-shaking、browserslist）。最后给出每项的“改前证据 → 改法 → 改后怎么验证”，验证需包含可复现命令（如 build 命令与 Lighthouse 阈值：LCP<2.5s、INP<200ms、CLS<0.1）。确认清单后我再让你逐条修改。
要点：先让它出审计报告并和你确认，再让它动代码；每次改动要小而可回滚，说明原因。

> #### 第二轮：后端诊断与优化（同样先报告后改）

只读审计 backend/，不要改代码。按优先级列问题并定位到文件/行，重点：接口 P95/P99 时延与慢查询（N+1、缺索引）、连接池/超时/重试、缓存与失效、序列化与字段裁剪、并发与阻塞 IO、日志与错误处理（是否吞异常）、鉴权与限流、敏感信息是否进日志/代码、依赖与配置（用 .env.example 脱敏）。输出：问题清单 → 根因 → 修复方案 → 验证方式（如压测命令、慢查询日志、P95 对比阈值）。确认后再逐条修改。
注意：真实密钥/数据库连接串别贴，给示例值。

> #### 第三轮：前后端联调

现在做端到端联调：以 backend/ 的真实本地地址启动，跑通 frontend/ 的核心流程。逐项核对并输出“联调清单”：请求/响应契约（字段名、类型、分页、空值、错误码结构）、CORS、鉴权（登录、token 过期刷新、401/403 处理）、超时/重试/取消、Loading/Empty/Error 三态、并发请求与竞态、日期与金额精度、上传下载。对契约不一致处，优先在边界层（前端 API 适配层 / 后端 DTO）收敛，并给一组冒烟脚本或最小 e2e 用例，确保改完后能一键回归。
验收标准（写进每轮提示词里）
前端：LCP/INP/CLS、首屏 JS 体积预算、无首屏未压缩大图、关键路由懒加载。
后端：核心接口 P95 时延目标、慢查询清零、错误不吞且可追踪。
联调：核心用户路径一键跑通，契约有一致性检查，失败有明确错误提示。

- 别让 AI 一次“大重构”：要求小步提交，每条改动附理由与验证，发现问题随时回滚。
- 每轮结束让它交付：改动说明 + 验证命令 + 性能对比截图/数值，没有对比就当没优化。

## VibeCoding开发流程

- 1.  Plan Mode
      检查环境，分析需求、技术风险和实施步骤。不改代码。

- 2.  编写 SOP.md 和 task.md
      固定开发规范，明确任务边界和验收标准。

- 3.  按任务实现
      一个 Task 一个小改动，测试通过后再进入下一项。

- 4.  验收与复盘
      审查 diff、验证边界条件、记录技术决策，再合并或提交。

## Codex使用

> 需求拆解、技术选型、任务依赖、测试验收、分阶段交付

#### 1. 项目规划

```txt
 给系统身份
    你是一名资深 Go 工程师，请协助我xxx.
 给项目背景
    开发环境：
    技术栈：
描述你要的东西
指定工作目录
做AGENTS.md
```

### 2. 工程化要求

```txt

1. 需求边界、使用场景和异常情况。
2. 技术方案及关键技术决策。
3. 项目目录结构及各模块职责。
4. Windows、Git Bash、终端交互以及 Neovim 子进程调用方面的兼容性风险。
5. 测试策略，包括单元测试、集成测试和手动验收。
6. 任务拆解、任务依赖关系、每个任务的验收标准。
7. 实现顺序、主要风险以及后续可扩展方向。
```

### 3. 工作方式

```txt
当前处于 Plan Mode。

**现在只进行分析和规划，不要修改代码，不要安装依赖，不要执行具有副作用的命令。**

请先检查当前工作区已有的文件、Go 版本、项目结构和相关配置（如果可以安全读取）。

如果项目目录尚未初始化，不要擅自初始化或创建文件，而是在计划中说明后续需要执行的步骤。

在给出方案前，请重点审查以下问题：

- `filepath.WalkDir` 遇到权限错误、符号链接和文件遍历错误时的行为。
- 在 Windows Git Bash 下，TUI 是否能正常接管终端，并在退出后恢复终端状态。
- 如何处理 Neovim 不在 PATH 中、文件路径包含空格、没有搜索结果等情况。
- 是否应该忽略 `.git`、`node_modules`、`vendor` 等目录，以及忽略规则应该如何设计。
- 当搜索结果很多时，如何避免不必要的性能开销。
- 如何确保测试不依赖真实用户目录或真实 Neovim 安装。

```

### 4. 约定输出格式

```txt
请按以下结构输出：

1. 项目目标与非目标。
2. 需求清单及验收标准。
3. 技术方案与关键决策。
4. 目录结构设计。
5. 风险清单及应对措施。
6. 测试策略。
7. 分阶段实施计划。
8. 推荐的任务拆解方式。
9. 需要我确认的关键决策。
每个实施阶段都要明确：目标、输入、输出、依赖、完成条件。

请优先采用简单、可维护、适合小型项目的设计。不要为了体现架构能力而人为增加层次。

完成计划后停止，等待我的确认。
```

### 5. 切换执行模式

```txt
请根据已经确认的项目计划，在当前项目仓库中编写两份工程文档。

### 文档一：SOP.md

记录本项目的标准开发流程，至少包含：

1. 项目开发原则和范围约束。
2. 每个 Issue / Task 的标准处理流程。
3. 编码前的分析要求。
4. 实现、测试、代码审查的顺序。
5. Git 分支、Commit 和 PR 的建议规范。
6. 错误处理、日志和跨平台兼容性要求。
7. 完成任务前必须执行的检查。
8. 任务失败、需求变更和发现新问题时的处理流程。
9. Definition of Done（任务完成标准）。

SOP 应当是后续任务可以反复遵守的操作规范，而不是项目介绍或空泛的开发原则。

### 文档二：task.md

将已经确认的实施计划拆解为可以独立执行和验收的任务。

要求：

- 使用 Markdown 复选框。
- 每个任务使用唯一编号，例如 TASK-001。
- 每个任务包含目标、具体工作、前置依赖、交付物、验收标准和测试要求。
- 明确哪些任务可以并行，哪些必须串行。
- 优先拆分为小型、可审查的提交。
- 每个任务尽量对应一个独立 Issue 和一个 PR。
- 不要把整个项目拆成大量没有实际价值的琐碎任务。
- 区分必须完成的 MVP 与可选的后续增强功能。
- 任务必须可验证，避免使用“优化代码”“完善功能”这种没有验收条件的描述。

### 执行约束

1. 先读取并遵守仓库已有的 AGENTS.md、README 和其他相关约定。
2. 不要修改业务代码。
3. 不要擅自引入新依赖。
4. 不要虚构已经执行的测试结果。
5. 文档必须与实际确认的技术方案保持一致。
6. 写入后检查两份文档是否存在任务遗漏、依赖冲突和验收标准不明确的问题。

完成后汇报新增或修改的文件、任务总数、任务依赖关系和需要我确认的问题。

之后按task一个一个实现。 每次只让Codex只处理一个任务
请读取项目中的 AGENTS.md、SOP.md、task.md 以及相关源代码。

本次只执行任务：TASK-XXX。

要求：

1. 先检查该任务的前置任务是否已经完成。
2. 说明当前代码状态、任务目标和实施方案。
3. 如果任务存在重要歧义或风险，先提出问题，不要擅自扩大需求。
4. 严格遵守 SOP.md 中的开发流程。
5. 只修改完成本任务所必需的文件。
6. 为新增或修改的行为编写对应测试。
7. 执行适用的测试、格式检查和静态检查。
8. 检查 Git diff，确认没有无关修改、临时文件或意外变更。
9. 更新 task.md 中的任务状态，但只有在验收条件实际满足后才能勾选完成。
10. 不要擅自开始其他任务，不要自动提交或推送代码。

最后汇报：

- 实现了什么。
- 修改了哪些文件。
- 做出了哪些技术决策。
- 执行了哪些测试及其真实结果。
- 尚存的问题和已知限制。
- 是否满足该任务的全部验收标准。
- 下一项可以开始的任务编号及其依赖关系。
```
